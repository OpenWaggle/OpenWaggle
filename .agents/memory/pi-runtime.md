Pi SDK integration: built-in extensions, settings overlay, run contract and events,
prompt caching, Pi JSONL session files and entry ids, bundling Pi for packaged apps, Pi TUI
components, Waggle inside Pi, and tool-schema shapes providers accept.
Load when touching `src/main/adapters/pi/`, `packages/pi-*`, a Pi upgrade or a Pi-registered tool.

## Pi Runtime Memory

- Pi 1.0 built-ins (`codemode`, `tool_search`) load through `pi-built-in-extensions.ts` as `builtin:<name>` replaceable inline extensions, like the Pi CLI, so Pi's `-builtin:<name>` still disables one. Automation sets `noExtensions`, which skips built-ins, so automation names them as explicit `builtin:` extension paths. `OPENWAGGLE_AUTOMATION_PI_EXTENSIONS` (path-delimited) loads named QA fixture extensions under automation; jiti caches a fixture module per process, so restart the QA app after editing one.
- OpenWaggle settings with a Pi equivalent (`codemodeEnabled`, `cacheWarming`) are overlaid on Pi's global settings layer in memory (`openwaggle-pi-settings-app-overlay.ts`) and stripped on write when Pi left them as reported. OpenWaggle first, then Pi: `Settings.piRuntimeSettingsChosen` records which keys the user stored; `openWagglePiAppSettingsFrom` reads the global Pi `settings.json` again (`piUserAppSettings`) for the others each time a runtime is built, then OpenWaggle's default (the store also resolves them at load, for display, through `configurePiUserRuntimeSettingsReader`, installed by `runtime-pi-integration.ts`); the overlay appends `+codemode`/`-codemode` last in `defaultTools`, so the effective choice wins over the global list. Cache warming `idle` needs the Run's Pi session to outlive the Run: `pi-idle-cache-warming.ts` keeps it as a warming session (extensions shut down, so no MCP connection; never reused for a Run) while Pi's warmer is active, at most 8 and 31 min. It is ended before anything opens the Session's Pi file again (`createPiRunSessionRuntime`, `withPiSession`, `createPiSessionRuntime`), by the Session removal hook (`runtime.ts`, before archive or deletion touches the file), on Host stop, and when the authoritative `cacheWarming` leaves `idle` (Pi's SettingsManager keeps the value it was built with); context-usage and snapshot reads borrow it instead of opening the file. It also ends as soon as the Pi file's size or mtime differs from what the Run and its own refreshes left (poll, `borrow`, and a guard wrapped around the session's `appendUsage`, whose throw Pi's warmer swallows): a refresh is parented on the warming session's stale leaf, so after `pi --resume` appended, it would become the last entry and resume the old branch. Its `usage` entries alone leave the Pi-file freshness check `unchanged` (`readSnapshot` gets `projectedPiEntryCount`), so warming never re-projects or reorders the sidebar. The same usage-only rule (`onlyUsageAppendedAfter`) keeps the resume position valid after refreshes; `resumeSelectedPosition` then leaves the leaf alone when it follows the selected node through `usage` entries only, so the next message chains onto them as in Pi (branching back made the refresh a sibling and the tree reported a second branch). Branch derivation (`branch-derivation-nodes.ts`) also drops `usage` nodes that end a path and maps an active node on one to the conversation node above, which repairs older files on their next snapshot. Each Run re-applies the warming mode its runtime resolves (`prepareRun`), since a Pi `settings.json` change reaches no settings listener. `installPiRuntimeIntegration` runs from `initializeAppRuntime` and the in-process agents/MCP CLIs, never on import. Faux tests need `promptCache` on the model, costs, a reply queued per refresh, and a `cache_warming_decision` handler returning `warm`.
- Virtual models: assistant messages name the physical model; `session.model` is the virtual one. Look context windows up by the response's provider/model (`modelRuntime.getPhysicalModel`) and tag `context_usage` with `routedFrom` so the meter, which filters by the selected model, accepts it. The renderer provider store must keep `ModelDisplayInfo.virtual`; it rebuilds model records field by field. Pi's `session.routedModel` names the latest response even if it came from before a switch, so projection tags each assistant node's metadata with `selectedModel` (nearest `model_change` on its path, `entry-model-selection.ts`) and the routed label only counts responses made under the current selection.
- pi-tui `Input.setValue` keeps the cursor where it was (start for a new Input); prefilled inputs enter the value as a bracketed paste so typing appends. `parseKey(' ')` is `"space"`, so a plain character must be taken as itself before `parseKey`.
- Pi 0.84.4 emits `agent_end` with `willRetry: true` for a transient assistant error, then `auto_retry_start`. If the retry delay is stopped, Pi emits `auto_retry_end` with `finalError: "Retry cancelled"`; this is cancellation, not a provider failure. Preserve `willRetry` and cancellation separately in transport events, and give the run's aborted state priority over any error retained in Pi history. Pi's default HTTP idle timeout is five minutes; Undici may report a stalled or closed streaming connection as `terminated`, which Pi considers retryable. Classify that as a provider connection failure while retaining the raw detail.

Load `.agents/skills/pi-integration/SKILL.md` for details.

- Prompt cache and Bedrock patches (v1 performance, October 2026; each has a test in `adapters/pi/__tests__/`). The pi-ai Bedrock transport keeps one `BedrockRuntimeClient` per configuration (region, endpoint, profile, user agent, hashed static credentials or bearer token, request handler; LRU 8, closed after 10 min idle), so the SSO credential fetch and the HTTP/2 session happen once: time to first byte went from ~1.25 s to ~0.69 s per call on EU Haiku. A client unused for 30 s closes its handler's connections before its next request (a silently dead pooled connection would hang it until TCP gives up), pooled HTTP/2 sessions keep the SDK's 300 s idle bound, and a request AWS refuses outright (`UnrecognizedClientException`, bad signature, access denied) drops the cached clients without a retry, since the SDK memoizes static credentials per client. The tools cache point is written for Claude model references only, even under `AWS_BEDROCK_FORCE_CACHE`. Per-request middleware goes on the command, never the shared client. Pi's cache warmer reads `model.promptCache`, and the generated Bedrock catalog had none, so `cacheWarming: streaming` never kept a Bedrock cache alive during long tools or `hive wait` (most of the 5-minute TTL misses); `amazon-bedrock.models.js` now declares them for the Claude models Bedrock caches, the warmer derives them for Bedrock models from other catalogs, and budget-thinking Claude on Bedrock is not replayed (its budget follows `maxTokens`). Bedrock gets four cache points: tools, the system prompt before section `cwd` (`systemCacheBoundary`, set by Pi's SDK), the rest of the system prompt, and the last user message; a second Session with another tail read 17.7k of 18k prefix tokens from cache. Per-Session text therefore belongs after `cwd` ("The first-turn prefix is a budget" below). Collapsed tools keep the leading system message's order and sort later additions by name, so a reconnecting MCP server no longer reorders them. Bash shows the model at most 16 KB (first and last 8 KB); codemode no longer appends "resolves to a string" to every declared tool.
- Agents learn about the installed OpenWaggle docs bundle (`Resources/openwaggle-docs`, dev `build/openwaggle-docs` from `bun run docs:generate`) only through the Pi-native `openwaggle_docs` tool (`openwaggle-docs-tool-extension.ts`, list/search/read over `listDocsDiscoveryView`, global and Session-project extension docs included). Its `promptGuidelines` carry the pointer, and name the bundle root only when `index.json` loaded for the Run (`availableBundlePath`); a missing bundle never fails a Run, the tool returns an error naming the expected path. Discovery lists every extension's docs whatever its trust, and only checks containment when it hashes the file (a symlink out of the package keeps its path with `contentHash: null`). The tool therefore offers only extensions the Run loads (`listRuntimeEnabledPackagePaths`, which also honors the project override) whose docs have a non-null hash, and `read` re-checks the realpath against the package and the hash before returning content; any other consumer that reads extension doc content needs the same checks. Pi's own `<docs>` block points into `app.asar` in packaged builds: Electron's asar fs patch lets Pi's `read` and `ls` tools open those files, but shell commands and the spawned `find`/`grep` tools (fd, rg) get "Not a directory", so the guideline points at the bundle's plain-file `topics/pi/` copies.
- Since Pi 1.2.0, `sendCustomMessage({ triggerTurn: true })`, which starts every Waggle turn, prepares the run as `prompt()` does (`_prepareRun`: `before_agent_start`, prompt sections, tool loadout, kept on the turn's later requests; `BeforeAgentStartEvent` is then `messageType: "custom"` with `message`, not `prompt`). Pi 1.0.4 did not, so OpenWaggle's patch had `_runCustomMessageTurn`; on 1.2.0 the patch keeps only `_prepareNewTurn` (auth refresh and the pre-prompt compaction check, after `before_agent_start`) and the failed-preparation run: a custom-message preparation that throws still ends as an error turn and `agent_end` (`PreparedRunError` in `_startRun`), since `pi.sendMessage` only reports its rejection to the extension error listener, which `bindSessionExtensions` logs; a Waggle Run fails on it (`onExtensionTurnStartFailure` ends the loop through its `fail`), a classic Run does not, since Pi finishes its turn itself. Once `before_agent_start` has run, the failed turn keeps the turn's prompt and loadout, so Pi's automatic retry sends them. pi-waggle advances a turn on `agent_settled`, not `agent_end`, which Pi also emits for a failed request it is about to retry, after overflow compaction, and before a queued continuation, each with only that attempt's messages: `onPiWaggleSettledAgentEnd` (`settled-run.ts`) gathers every `agent_end` of the run and drops failed attempts a later response replaced; the default extension a Pi TUI user loads uses it too, with a pi-ai classifier (`default-turn-error.ts`), which imports pi-ai lazily: pi-ai is ESM-only and the package's CommonJS build (checked by the package consumer smoke in `bun run check`) must load without it. OpenWaggle runtimes never load an installed `@openwaggle/pi-waggle` package (`pi-waggle-package-dedupe.ts`, `extensionsOverride`): its default extension filters every Waggle request and turn message out of `context` and would run a second loop. pi-waggle's stop policy takes a host error classifier (`summarizePiWaggleTurnMessages(messages, { isRecoverableError })`); OpenWaggle's (`waggle-turn-error.ts`) uses Pi's `isRetryableAssistantError` and `isContextOverflow`, so an error no later turn recovers from (rejected sign-in, missing model, quota or billing, uncompactable overflow) stops the collaboration and the Run ends with it, while transient errors stay recoverable. A failed response's `errorMessage` is hydrated as `Message.metadata.error` (not for an attempt a `context_edit(…, null)` drops: `omittedFromContext`), live too through `message_end.errorMessage`; a Waggle turn row shows the error of its last response only (`withWaggleTurnFailures`), and the Run's last failed turn leaves it to the Run error row while that shows. A response takes its Waggle turn from the nearest `pi-waggle.turn` past earlier responses, tool results and context edits (`waggle-turn-metadata.ts`) (`docs/pi-runtime-upgrades.md`; upstream bug to report). `before_agent_start` therefore fires on every Waggle turn: OpenWaggle's handler only sets sections and the tool filter, and Pi's MCP handler waits once (bounded) for direct servers to connect and sets `mcp_servers`, so both are idempotent; the Run identity is decided once per Run in `context`. `waggle-turn-system-prompt.integration.test.ts` checks it with real Pi, a file-backed session, and a faux tool call.
- Pi 1.2.0 run contract (checked in the 1.2.0 upgrade): the session counts as busy from the moment a run starts preparing, `before_agent_start` included, so `ctx.isIdle()` is false there, `pi.sendMessage()` queues into the starting run, `pi.sendUserMessage()` then needs `deliverAs`, and an abort requested meanwhile aborts the run once it exists. `agent_settled` carries `aborted` (1.1.0) and `tool_execution_end` `durationMs`. OpenWaggle's `before_agent_start` handler only writes sections and narrows tools, so running it for custom-message runs too adds nothing twice; pi-waggle's `input` handler checks `isIdle()` before any run starts, and its default extension sends its continuation prompt a tick after the run settled. Pi no longer lists MCP resources on connect (`pi mcp list --json` says `resources: true`); OpenWaggle's inspection lists tools only and MCP Apps read `ui://` resources directly, so neither depended on it.
- Pi extension commands (`pi.registerCommand`) run when a message starts with `/name`: Pi's `prompt()` runs them instead of prompting the model. The slash menu lists a Session's commands through `agent:list-extension-commands` (Host UI revision 24): the warm session's or a read-only Pi session's, plus those its latest Run had (`run-extension-commands.ts`, recorded in `createPiSessionForRun`), since some extensions load only in a Run. Pi's MCP `/mcp` is deliberately not registered: it is a terminal menu, and OpenWaggle manages MCP in Settings > MCP (`forOpenWaggleMcpSurface`, `mcp-openwaggle-surface.ts`, which also rewrites Pi's "Run /mcp to fix/sign in" and "Run /login <provider>" wording in notices and tool results to name Settings > MCP / Settings > Connections). A first message that invokes one is not used for the title (`invokesExtensionCommand` in the Run preflight).
- Pi 1.0 prompt caching: never return `systemPrompt` from `before_agent_start` for per-Session context. Mutate `event.systemPromptOptions.sections` instead (`agent-run-context-extension.ts` writes `openwaggle_agent_definition` and `openwaggle_session_identity`), and keep those sections byte-stable across Runs. Changing a section mid-Session does not protect the cache on most providers: `supportsMidConvoSystemMessages` defaults to false, so pi-ai collapses every later system-message patch into the leading prompt (`collapseSystemMessages`). Values that change per Run (runId, Session title, Hive role, Worker count, Delegation state) therefore go in the `openwaggle-run-identity` Run identity. It is stored once per Run, only when it differs from the latest one, as a plain `custom` entry (`pi.appendEntry`), never a `custom_message`, so `pi --resume` never sends OpenWaggle's Run metadata; it is written once per Run on the Run's first `context` call, whose messages hold the message that started the Run, and names it: the latest user message or `pi-waggle.user-request` after the last answer (never a Waggle turn message, since every turn adds one), else the first message after the last answer, such as the custom message of an extension command's `pi.sendMessage(..., { triggerTurn: true })`. A user message is matched by timestamp and content digest; a custom message by custom type and digest, since reloaded from the file it carries its entry's time; each identity is placed by branch order: it counts the matching prompt entries the branch sent after it (k) and takes the k-th-from-last matching message, so an older identity never moves onto a later identical message without one (a pi CLI turn) and an identity whose message was compacted away is dropped (`agent-run-identity.ts`); the `context` handler sends each stored identity as a hidden custom message right after that prompt, where Pi used to put the message, so earlier Runs' request prefixes and their prompt cache stay the same. Never place it by time: Pi's entries and messages are stamped in milliseconds, and a fast Run puts the identity, prompt, answer, and next Run's identity in one millisecond (the first time-based version misplaced it about one run in four). Older files keep their `custom_message` identities. The Session tree hides the entry (`node-hydration.ts`). `session-run-execution-profile.ts` splits `identityContext` (Session-level) from `runIdentityContext` (Run-scoped). `agent-run-context-prompt-cache.integration.test.ts` uses a real Pi session to check that the leading prompt, raw and collapsed, stays identical across Runs.

- Pi TUI Waggle continuation turns should be scheduled after the current Pi run settles, then append the visible `pi-waggle.turn` custom message and call `sendUserMessage(..., { deliverAs: 'followUp' })`. Pi ignores `deliverAs` while idle, which it is after settling, and Pi 1.2 refuses `sendUserMessage` without it while a run is starting (busy-while-starting); never queue continuation prompts during `turn_end`, which can leave them waiting for user confirmation. Pi 1.1+ settles a run the user aborted (Escape) with `agent_settled.aborted`: `onPiWaggleSettledAgentEnd` then drops the run's messages and calls `onAborted` instead of judging the turn; `createPiWaggleExtension` resolves `done` there, and the default extension restores the inherited model and says the Waggle stopped. Stop pressed in the `setTimeout(0)` gap between turns aborts no Pi run, so nothing settles as aborted: the default scheduler's `canStartNextTurn()` check then calls `onComplete`, or `done` (which OpenWaggle's Waggle Run awaits before its `finally` and durable active-run cleanup) would never settle. The default extension advances on `agent_settled` (`onPiWaggleSettledAgentEnd`), with every `agent_end` of the settled run gathered and attempts a later response replaced dropped; never on `turn_end`, which also ends a failed attempt Pi is about to retry. Its pi-ai turn-error classifier loads lazily: a literal `import()` in the ES module build (which Pi's extension module mapping serves), and in the CommonJS build, where TypeScript compiles `import()` to `require()` and pi-ai's `import`-only exports refuse it, a real `import()` built with `Function` (`esm-import.ts`, created on use). - User-authored input during an active Pi TUI Waggle run must stop automatic Waggle continuation and be resent with `sendUserMessage(..., { deliverAs: 'steer' })`; otherwise Pi rejects it with “Agent is already processing” because normal prompts during streaming need an explicit streaming behavior.
- Pi custom TUI components must use `@earendil-works/pi-tui` keyboard helpers such as `matchesKey`/`parseKey` instead of raw escape-sequence comparisons; Kitty keyboard protocol encodes Enter, Esc, Space, and Ctrl+C as CSI-u sequences, so raw checks can trap users inside custom menus.
- Pi custom TUI components must never return strings containing embedded `\n`/`\r`; normalize dynamic labels/details to single terminal lines before rendering. They must also truncate rendered lines with `truncateToWidth`/`visibleWidth`, not string length, clamp scroll windows to `items.length - visibleRows`, and reserve fixed blank slots for scrollable lists/details. Embedded newlines, overflowing lines, or shrinking terminal output can corrupt Pi TUI's differential cursor math and leave duplicated-looking rows. Prefer Pi's built-in `ctx.ui.select` for modal menus unless custom rendering is clearly needed, so the Pi footer/status remains visible and interaction steps do not visually jump.

## Pi entry ids are only unique within one file (ADR 0049)

`session_nodes.id` is a global key and node ids are Pi entry ids. Pi's stock eight-character ids collided across Sessions once the database held ~80k nodes: one reused id made every later snapshot of that Session fail with `UNIQUE constraint failed: session_nodes.id`, shown as "This response couldn't be saved", and the projection stopped at the collision while the Pi file kept everything. The Pi patch now mints full UUIDs. `persistSessionSnapshotWithSql` checks for ids held by other Sessions first and fails with `SessionNodeIdConflictError` (names the id and its owner); the Session repository then renames those entries in the Pi file through the `SessionTranscriptRepair` port (`repairForeignSnapshotEntryIds`) and saves again. The rewrite refuses unparseable files and files that changed meanwhile, and only re-projects changed entries. Anything that reads a node id from the snapshot after saving (turn-checkpoint anchors) must resolve it against the saved tree. Never key anything new by a Pi entry id alone, and scope every `session_nodes` write by `session_id`.

## A Session's recorded Pi file is only a hint until its first run settles

Preparation records the file of a manager it creates in the opened checkout, but Pi writes a file only on the first assistant message, and the first run opens its own manager in the run directory (the worktree, for a worktree Session), so Pi writes a differently named file elsewhere. That file is recorded only when the run's snapshot is saved. A Host that stopped during a Session's first run left it pointing at a file that never existed, and the next run started an empty transcript under the same Pi session id, silently dropping the conversation. `createSessionManagerForSession` now looks for `*_<piSessionId>.jsonl` in the Pi session directories of the run directory, the recorded path, the Session's checkout and its worktree before starting fresh, and logs a warning, once per Session, when a Session that already has an assistant reply still has no file. It does not merge Sessions that already started over on a second file before this fix; the newest file wins. Deleting a Session removes every `*_<piSessionId>.jsonl` in those same directories (`findPiSessionFiles`, through the `SessionTranscriptFiles` port), not only the recorded file; the deletion journal records the newest copy for a Session with no recorded file, because after the Session row is gone that file name is the only record of its Pi session id. A discovered Session's files are never removed this way: a cleanup that journals no staged path keeps the file and every copy (ADR 0051). Discovered nodes carry a `<sessionId>/` prefix, so the ADR 0049 rename never applies to them. The directories come from `piSessionDirectoryFor`, which honours a configured Pi session directory.

- Since Pi 1.0.4 (unchanged in 1.2.0), main's #282 streaming-argument test for OpenAI Responses ends the normal case with `output_item.done` (empty arguments), then `completed`: Pi refuses a toolUse message whose call never got `output_item.done`, so the old ending is now tested as refused, and `finishStreamingToolCalls` runs after that refusal.

## Runs project only what Pi appended (v1 performance D6, October 2026)

`session_nodes.content_hash` (migration 80) is sha256 of `content_json` + `metadata_json`; snapshot persistence selects light columns + hash and reads content only where the hash differs or is null (old rows, filled lazily on the Session's next persist). The reconcile writers keep it; trigger `session_nodes_content_hash_guard` clears a hash another writer left stale. `pi_session_file_projections.tail_*` (migration 81) records where the projected entries end (offset, last line start, digest of the first 64 KiB + that line, entry id, count, leaf), only when the file's last line is the snapshot's last Pi entry. While the file only grew (`piSessionFileStillHasTail`), a Run's snapshot keeps the earlier entries as lazy nodes (`retainedPiEntryNode`, kind/role from the stored rows) marked in a WeakMap with the projection revision (`retained-snapshot-nodes.ts`); `persistPiSessionSnapshotWithSql` trusts them only if that revision is still current and a tail is recorded, and then updates only their tree columns. Entries whose context-edit omission changed are projected again. The tail also records the entry-projection version (`tail_projection_version`, migration 84); `projectPiSessionSnapshot` ignores a base from another version, so bump `PI_ENTRY_PROJECTION_VERSION` whenever `projectPiEntry` output changes, or stored rows never get the fix. Copying a node (`{...node}`) drops its mark (correct, just slower) and forces its lazy content. A refresh reads only the bytes after the tail: usage-only appends are `unchanged` without parsing the file. Pi's own `SessionManager.open` still parses the whole file per Run: its constructor is private and preloading would keep every parsed entry in Host memory between Runs. Measured on a synthetic 95 MB / 16k-entry Session: refresh after a warming append 130 → 0.9 ms, Run projection 145 → 48 ms, existing-node select 117 → 34 ms (0 content bytes read for an unchanged Session).

## Filed under "Pi Compaction Memory"

- Pi session file reuse (D6, October 2026): `SessionManager.open(..., { reuseParsedFile: true })` and `setSessionFile(file, { reuseParsedFile: true })` (patched; `REUSE_PARSED_PI_FILE` in `agent-kernel/constants.ts`) keep a module-level parse per file (at most 4 files / 64 MiB of file bytes, 10 min idle) and parse only the appended tail when device, inode, and the first and last 4 KiB before the cached end are unchanged; a shrunk, replaced or rewritten file (`pi --resume`), an old-version file, or an unfinished last line takes Pi's full load. A 174 MB file reopened after a Run's appends took 454 ms -> 1 ms, but its parse held 566 MiB of heap (parsed entries take 1.2-3.4x their file bytes), so the bound was lowered from 256 MiB after review: a file over 64 MiB is parsed whole on every open again. Parsed entry objects are shared between managers, so never mutate an entry or message loaded from a Pi file; each manager gets its own array. `clearParsedSessionFileCache()` releases it (an idle Host should call it).

## Filed under "Renderer And Session Memory"

- Pi reopens a session file at its last entry and keeps tree navigation in memory, and OpenWaggle opens a fresh Pi session for every operation. A branch switch or a no-summary retry is a separate Pi operation from the run that follows, so runs used to continue whichever branch was written last: the message landed on another branch than the one on screen and the model answered from that branch's context. `SessionDetail.resumePosition` carries the projection's `last_active_node_id` plus the Pi entry count it was derived from (agent-loop audit nodes excluded), and `createSessionManagerForSession` branches to it only while the file still has exactly that many entries; a file with unseen entries (host loss, a failed snapshot) keeps its own position.

## Filed under "Session Host authority and subscriptions are live boundaries"

Agent tool processes get `TMPDIR`/`TMP`/`TEMP` pointing at a per-Session 0700 scratch directory
through the Pi bash and PowerShell `spawnHook` in `pi-run-session.ts`, applied after the prepared
Workspace environment. Keep that path short: macOS limits a Unix socket path to 104 bytes and
`tsx`, Chromium, and others bind sockets under `TMPDIR`. A scratch dir under `os.tmpdir()`
(`/var/folders/...`) plus a UUID was 108 bytes and crashed `tsx`, so the pre-push verify and `git push`
failed from agent shells; it now lives at `<base>/ow-scratch-<uid>/<8-hex profile hash>/<12-hex
Session hash>`, where `<base>` is the user temp directory if the path fits 56 bytes, else `/tmp`. The profile hash (from the Host's user-data root) keeps each OpenWaggle
profile's Host from sweeping another's directories; the startup sweep
(`session-scratch-sweep-background`) removes directories of Sessions deleted or archived while no
Host ran, and another profile's namespace once the user-data directory named in its `.owner` marker is gone (unmarked namespaces: after a week unused). `prepareSessionScratchDirectory` touches
the mtime because the sweeps judge age by it. Screenshots meant for the user or another Session go to `$OPENWAGGLE_EVIDENCE_DIR` (`<base>/ow-scratch-<uid>/<profile>/evidence/<session>`, `utils/session-evidence-directory.ts`), which survives archiving and is an image capture root for every Session: a Worker's scratch directory is deleted when cleanup archives it, so a Queen could not render screenshots saved there. An OpenWaggle process started from an agent shell
restores `TMPDIR` from `OPENWAGGLE_HOST_TMPDIR` at startup (`restoreHostTemporaryDirectory`). Code that
must agree with the Host on a temp path (the Session Host socket fallback in `local-session-paths`)
reads `hostTemporaryDirectory()`, which prefers `OPENWAGGLE_HOST_TMPDIR` exported next to the
scratch `TMPDIR`. The Host deletes the directory from `session-host-events.ts` on
`session-list-changed` `archived`/`deleted`, but a Run holds it (`withRetainedScratchDirectory`), so
an archive mid-Run defers the removal to the Run's end. Tests that run `runPiAgentKernel` must mock
`utils/session-scratch-directory` or they create directories in the real temp directory.

A schema copied with `{ ...schema }` loses TypeBox's non-enumerable `~kind` and `~optional`, and
`Type.Optional` then adds `~optional` as a visible key that reaches provider payloads. Copy with
`Object.getOwnPropertyDescriptors` when decorating a TypeBox schema.

Providers speaking the OpenAI-completions shape (GLM via OpenRouter confirmed) silently return
tool-call `arguments: "{}"` for any tool whose parameter schema is a root-level `anyOf`/`oneOf`
union; flat object schemas work, including nested property unions and `action` literal-union
discriminators. First-class Pi tools must therefore register flat object schemas and enforce
per-action required fields and enums at run time (see `sessions-tool-flat-schema.ts`, PR #219 /
issue #218). When `pi.validateToolArguments` reports `Received arguments: {}`, suspect the
provider dropping arguments for the schema shape before blaming parsing or permissions; the
cheapest discriminator is a raw REST probe of the provider with the exact tool JSON.

Other providers reject a root union outright rather than dropping arguments. Pi 0.87 sends
`tool.parameters` verbatim unless strict constrained sampling is on, so a root `anyOf` reached
Bedrock as `toolConfig.tools.N.toolSpec.inputSchema.json` ("type must be one of: object" on the
first turn) and OpenAI via OpenRouter as "schema must be a JSON Schema of 'type: \"object\"', got
'type: \"None\"'" (gpt-4.1/gpt-4o-mini; gpt-5.x routes tolerated it). The culprit was
`preview_resize`, tool 8 after Pi's four built-ins and four earlier preview tools; every MCP
server in the user's config already served object roots. Every tool parameter root must be
`type: "object"` with no root `anyOf`/`oneOf`/`allOf`/`enum`/`not`/`const`/`$ref`.
`provider-tool-schemas.unit.test.ts` pushes every OpenWaggle tool through Pi's real Bedrock and
OpenAI-completions request builders (`onPayload` throws before the network) and checks that rule.
MCP tools are now registered by Pi's MCP extension (ADR 0051), which only forces an object root,
so OpenWaggle repairs MCP input schemas in its transport layer instead: `tools/list` results are
rewritten with `providerToolParameters` before Pi's MCP client sees them (the server still
validates the arguments; the old call-time re-validation in `provider-tool-parameter-relaxation.ts`
is gone). `providerToolParameters` also repairs MCP sampling tools, which Pi does not validate.
