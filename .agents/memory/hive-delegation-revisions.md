# Hive Delegation revisions

How a parent's revision request, reopen or task change reaches its Worker: the revision
Follow-up, who may send it, settlement and submit hold-backs while it waits, and its known gap.
Load when touching `delegation-revision-*`, `sqlite-delegation-revision-*`, Delegation review or
amend/dependency outcomes, or Worker settlement of a revision.

## A revision request queues the Worker's next Run (#454, ADR 0030 amendment, November 2026)

- Bug: `delegation_request_revision` (and `delegation_reopen`) left the Delegation `revision_requested` / `nextActor: worker` and queued nothing, so an idle Worker sat for hours until the parent sent a `follow_up`. A revised specification did not help either: `enqueueDelegationSpecificationUpdate` only fills the `delegation_specification_updates` outbox, which a Run reads at `session_start` or a live Run gets steered; nothing starts a Run for it. Amendments and dependency changes had the same gap.
- Fix: `delegationRevisionFollowUp` (`domain/session-control/delegation-revision-follow-up.ts`) builds a `follow-up` on the Worker, keyed `delegation-revision:<operation>:<review key>` (the operation, because a caller may reuse one key for a revision request and a later reopen, and both Follow-ups have operation `follow-up`), whose text starts `OpenWaggle Delegation revision request, sent as your parent's Follow-up.` (not "Host-authored": it arrives as the reviewer's user-role Follow-up, and any agent could send the same text) and holds JSON with `delegationId`, `parentSessionId`, `submissionRevision`, optional `specificationRevision`, `feedback`). `sendDelegationRevisionToWorker` (`application/delegation-revision-delivery.ts`) runs it from `executeSessionControlMutation` after the review returns, outside the parent's serialization, as the reviewer with its caller/authority, and publishes the response. Skipped for a replayed review. The command service passes itself as `execute` to avoid an import cycle.
- Why a Follow-up and not the specification outbox: the Follow-up queue already starts a Run when idle and queues behind a busy Run, and `settleWorkerDelegation` skips capture while a Follow-up is scheduled, so a busy Worker's current Run is not taken as the revision. The outbox also has `UNIQUE (delegation_id, specification_revision)`, which a feedback-only revision (no new specification revision) would collide with.
- Authority: an immediate Follow-up start is not re-checked for `sessions:message` (only the transport checks the original command, which needed `delegations:review`). So the review itself is refused, inside its transaction, by `revisionDeliveryRefusal` (`sqlite-delegation-revision-admission.ts`, through `workerMessageRefusal` in `sqlite-session-delegation-support.ts`): `worker_message_denied` (kind `authorization`) when `liveCallerMessageBlockReason` blocks the reviewer on the Worker. That is the queued Follow-up delivery check (`messageCallerBlockReason`) plus, for a live caller with `profileAuthority`, `authorizeSessionTargetForCaller(caller, worker, ['sessions:message'])`: the stored check returns undefined for a `transient-mcp:` caller and reads a `--profile` server's profile without its `--grant` narrowing, so without the live check an MCP server holding only `delegations:review` could start Worker Runs with any text (found in review). The live `caller` is threaded `executeSessionControlMutation` → resource dispatch → `executeSessionDelegationMutation` → `SessionDelegationRepository.execute`. It also refuses with `parent_concurrency_limit_reached` / `host_run_ceiling_reached` when the Worker is idle (no active Run, queue not paused) and `workerRunAdmissionRefusal` would refuse the Run: an idle Worker's Follow-up at a limit is rejected, not queued, so the review would otherwise commit with nothing queued. Decided with the maintainer: a clear refusal beats a recorded review that leaves `nextActor: worker` with nothing queued, because agents cannot read Host logs. The delivery checks again (`SessionDelegationRepository.messageBlockReason`) for the moment between commit and Follow-up, and only logs then. That check decodes the reviewer's execution profile, so a fixture profile without `thinkingLevel` now fails the review (`sqlite-session-lifecycle-test-support.ts` got one).
- Settlement race (found in review): the change commits before its Follow-up is queued, and settlement skipped capture only while a Follow-up was queued, so a busy Worker Run settling in between had its stale reply captured as the revision (then the revising Run could not submit from `ready_for_review`). `loadWorkerDelegation` (`sqlite-session-control-worker-settlement.ts`) now reads `revisionFollowUpOwedSql` (`sqlite-delegation-revision-owed.ts`): the Delegation is `revision_requested`, a completed send-back command of its parent (`session_operations`, scope `delegation:<id>:actor:<parent>`, outcome `revision_requested`, and for amend/dependency a `revisionRequest`) is newer than the settling Run, and no `follow-up` row with its `delegationRevisionKey` exists on the Worker; `settlesWithReply` then captures nothing. A first version compared against any `revision_requested` review or transition time, which a third review round showed broke three cases: a retry Run after a failed revision Run (the Host's `needs_attention → revision_requested` transition is written at activation, after the Run's `created_at`), an amend on a still-`working` Worker that had submitted, and a revision request promoted into the busy Run. Keying on the owed Follow-up holds back only the race window.
- Explicit submit (round-4 review): a busy Worker's current Run could still `delegation_submit` while the revision request waited, turning the stale result into the revision and leaving the revising Run unable to submit (`ready_for_review` is contributable only to a Hive wake). `revisionPendingForSubmittingRun` (`sqlite-delegation-revision-owed.ts`) refuses a `session-agent:<worker>:<run>` submit (a requested Waggle's `waggle-of-<run>` mapped back with `durableSessionRunId`, found in round 6) with `delegation_revision_pending` (kind `conflict`) when `revisionPendingForRunSql` holds: owed for that Run, or a revision request of the parent still queued on the Worker whenever the Run started (`session_follow_ups.intent_json` `idempotencyKey`, matched to the send-back's caller by `authorCallerId` ?? `callerId`, since `queue-adopt` rewrites `callerId`). The queued branch has no time comparison (round-5 review): a Run that starts on the Worker between the review's commit and its Follow-up's enqueue is newer than the send-back but still never saw the feedback (`delegation-revision-run-gap.integration.test.ts`). A request promoted into the Run is recorded and no longer queued, so that Run may submit. The Hive host test harness clock (`hive-worker-cleanup-host.test-harness.ts`) is now `Date.now()`, as in production: with the old fixed `now: 5000` every Delegation command looked older than any Run, which hid this ordering.
- Known gap, accepted with the maintainer: the change and the Follow-up are two commands, so a Host crash between them leaves the Worker idle in `revision_requested`. If it shows up in practice, the agreed fix is a repair at Host start (queue the revision request again for a `revision_requested` Worker with no Run and no Follow-up, after rechecking that the reviewer may still message it), not one transaction across the delegation and Follow-up writes.
- Task changes (decided with the maintainer): `delegation-amend` and `delegation-dependency` send the same Follow-up (reason as feedback, the new `specificationRevision`) only when the Worker had submitted and waits for its parent (`ready_for_review`, `needs_attention`, `waiting`: they move any submitted Delegation to `revision_requested`, so a `needs_attention` Worker would otherwise be left `nextActor: worker` with nothing queued), which they report as the outcome's optional `revisionRequest` (`taskChangeRevisionRequest` in `sqlite-session-delegation-support.ts`; `parentSessionId` + the set-aside `submissionRevision`). On a Worker still on the task they send nothing, so it never gets a second Run; the specification outbox delivers the change. `taskChangeMessageRefusal` refuses them with `worker_message_denied` only in the case that would send a Follow-up.
- Agent guidance lives in `sessions-tool-revision-guidelines.ts`: the system prompt gets only `REVISION_STARTS_WORKER_RUN`, a few words after "request revision", because the first-turn prefix budget (`scripts/perf/first-turn-prefix`, an integration test outside `src/`, so run it when the system prompt changes) had about 30 tokens to spare; longer reviewer and Worker lines failed it in CI. `help` has the full rule naming every action (so `help` with any of them as topic shows it) and, for a Session that may submit, what a revision request looks like.
- Tests: `application/__tests__/delegation-revision-{worker-run,worker-access,task-change}.integration.test.ts` (idle, revised specification, reopen, busy, blocked reviewer, amend, dependency, amend while working or `needs_attention`) and `delegation-revision-delivery` (a transient MCP caller without `sessions:message`, out of scope, and allowed; Workers per parent and Active Workers full for an agent; the person's review at a full limit; reopen of a cleanup-archived Worker) on the real SQLite Session Host store via `commandHostLayer(path, executor)`, plus `adapters/__tests__/sqlite-session-control-revision-settlement.unit.test.ts` for the settlement race (owed, recorded and promoted, a later Run, a task change that sent nothing back).
