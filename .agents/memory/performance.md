# Performance

Performance budgets and measurement: the first-turn prefix budget, what every process pays
before OpenWaggle code runs, the boot shim, the Docker token benchmark, and probe pitfalls.
Load when touching `scripts/perf/`, startup code, benchmarks or a performance budget.

## The first-turn prefix is a budget (v1 performance, October 2026)

An empty project's first request was 13.3k o200k (22k Opus) before any user text; it is now about 3.8k. What keeps it there: rarely used OpenWaggle tools (`preview_*`, `project_actions`, `source_control`, `openwaggle_docs`) register through `onDemandToolRegistration` as Pi `deferred` tools in the `openwaggle` namespace, announced by one rule each, with no prompt snippets or guidelines (they would change the system prompt when `tool_search` loads them). `hive` declares only its hot actions and keeps the rest behind `help` (`sessions-tool-hot-schema.ts`); Pi coerces only declared properties, so `parseSessionsToolActionArguments` drops optional nulls and runs `Value.Convert` against the action's own variant before checking it (a spread variant loses TypeBox's non-enumerable `~kind` and `Value.Convert` stops descending: copy variants with property descriptors). An Agent definition allowlist that names a deferred OpenWaggle tool gets it declared directly (`allowedToolLoadout`), since the allowlist filters out `tool_search` and codemode; its `<rules>` are `sessionsToolEssentialGuidelines`, the full set is help output. PowerShell is declared only on Windows: Pi's `getPowerShellConfig` throws "only available on Windows" elsewhere, so offering it where `pwsh` was on the PATH (as the first v1 cut did) handed macOS and Linux models a tool that failed on every call. Per-Session text (scratch, evidence and visualization directories, the Session identity) lives in custom sections Pi renders after `cwd`, never in Pi's `addendum` or in `<rules>`, so everything before `cwd` is shared by a project's Sessions (the Bedrock `systemCacheBoundary` cache point in "Prompt cache and Bedrock patches" above). The skills listing is rewritten in `before_agent_start` only (relative/`~` paths, 160-character descriptions that keep the "Use when…" trigger sentence and shorten the opening before it); never change `skill.filePath` in `skillsOverride`, since Pi reads and expands skills from it. Hive results are compacted and capped at 32 KB with the whole result in `<scratch>/hive-results/<toolCallId>-<suffix>.json` (providers reuse ids such as `call_0`); a page always keeps at least one item, cut to a preview when it alone is over the cap, and verbose results page under `response.outcome`.

## What every process pays before OpenWaggle code runs (v1 performance, October 2026)

package.json `main` is `out/main/boot.js` (`src/main/boot.ts`, built by `scripts/vite/main-boot-entry.ts`). It enables Node's compile cache (per user and Build channel under `~/Library/Caches/OpenWaggle`, `%LOCALAPPDATA%\OpenWaggle\Cache` or `XDG_CACHE_HOME`, never userData or TMPDIR, skipped for AppImage; `OPENWAGGLE_COMPILE_CACHE_DIR` moves it, so keep one across throwaway measurement homes), answers `--version`, `--help` and usage errors itself, and otherwise requires `./index.js`, then flushes the cache at once (Node writes into a `v<node>-<arch>-<flags>-<uid>` subdirectory, so each Electron upgrade starts a new one; the window and the Host touch theirs after the first write and remove siblings unused for 14 days): Electron's `app.exit()` and a killed Host never let Node write it, and V8 makes a module's cache data when it compiles it, so a later flush adds nothing for that file. With `codeSplitting: false`, Rolldown hoists every static import of an external to a top-level `require()`, even inside a lazy `__esmMin` module, and nearly every module's init still runs at startup, so a hoist fix alone is not laziness. `scripts/vite/lazy-external-requires.ts` routes externals through lazy CommonJS stand-ins, pure-JS many-file packages are bundled (`BUNDLED_DEPS`), and natives or WASM readers load on use (`lazyModule`, `sharp-module.ts`; the updater IPC handlers load the updater on the first check). `bun run check:main-bundle` parses the bundle and fails on any top-level require except Electron and Node built-ins; since a `require()` inside a lazy stand-in still runs at startup when an initializer that runs at startup calls it, it also evaluates the bundle in Node with recording stubs for every external (`scripts/main-bundle-startup-externals.ts`: `--version`, `run`, `host start`, `session-host-internal`) and fails if anything but Electron loads before the bundle returns, or if the start throws under the stubs. The main bundle stays one file on purpose: split with Rolldown code splitting (A-F6, after the GUI composition root) the GUI's startup graph fell from 15.8 to 2.5 MB, yet the packaged app was slower at every startup milestone, because one compile-cached file loads faster than the 100-155 chunks each process reads from `app.asar`. A November re-measurement on packaged apps kept it (`docs/performance/main-build-split-2026-11.md`). The window was ready 156-262 ms sooner cold and 53-72 ms sooner warm. The Host listened 138-162 ms later cold and 62-70 ms later warm, loading 213 chunks (10.6 MB), and chat ready was not consistently better. Revisit once the Host's startup work is lazy; `check:main-bundle` budgets the bytes each process loads (`scripts/main-bundle-graph.ts`, from `out/main/.vite/main-chunks.json`) either way. Main, the boot shim (54.5 → 24.8 KiB, names kept; its top-level compile 0.50 → 0.25 ms) and renderer are minified with `sourcemap: 'hidden'`: the maps stay out of the app (`!out/**/*.map`; `packaged-app:smoke` refuses them), `check:main-bundle` requires one for `boot.js` and per main chunk, and the release workflow keeps them as `<platform>-source-maps` artifacts for 90 days (the publish job downloads only `*-artifacts`). Renderer-only packages are devDependencies (electron-builder ships only `dependencies`), and `packaged-app:smoke` fails if onnxruntime-web, better-sqlite3 sources, tesseract `*.wasm.js` builds or a renderer-only package ships again (`scripts/electron-builder-runtime-trim.ts`).

## The boot shim launches the desktop app's Host (v1 performance W11, October 2026)

A cold start used to reach the Host launch only after the GUI had read, compiled and evaluated the 15.8 MB main bundle and Electron was ready (350-500 ms), and the Host then needed as long again to listen. `src/main/boot/session-host-prelaunch.ts` launches it from the boot shim instead, for a desktop-app route on macOS/Linux whose profile has no Host socket and no legacy store to move; it hands the process to the GUI on `globalThis` (`session-host-prelaunch-handoff.ts`), which waits for it (`waitForPrelaunchedLocalSessionHost`) instead of launching another, and falls back to its usual launch if it ended. Everything it imports must stay free of `env.ts`, the logger and Effect (`session-host-launch-command.ts`, `local-session-host-layout.ts`, `detached-process.ts`). With a prelaunched Host the GUI must skip its own cutover: the Host creates its database meanwhile, and the GUI's `validateCompletedTarget` read the half-made file (`no such table: session_host_schema_metadata`: the startup error screen, intermittently). It skips it only while that Host lives: one that ended without answering leaves the store to move, so the lifecycle runs the usual cutover check before it launches a Host itself. The shim judges a legacy store with `legacyDatabaseFileStateSync`, the Host's own rule: a 0-byte `openwaggle.db` whose `-wal` holds frames is a store to move, and prelaunching for it made the Host take the single-instance lock for the cutover (it shares the GUI's userData), so either the Host failed on every start or the GUI quit as a second instance. Measuring tips: the harness profiles live under a long TMPDIR, so the socket sits in the temp-directory fallback; Chromium's `--trace-startup=... --trace-startup-format=json` works on the packaged app and shows the main bundle's cold `V8.ParseProgram` (≈165 ms) and `V8.CompileSerialize` (≈42 ms) in both the GUI and the Host, both gone with a warm compile cache (navigation 750 → 290 ms). Neither the Host nor the GUI waits for its login-shell probe (`zsh -ilc env`, 110-540 ms on the maintainer's machine, up to 5 s; the harness's empty HOME hides it): each hydrates in the background, and work that starts the user's tools (a Run's Pi session, terminals, project actions, git, stdio MCP servers) awaits `desktopShellEnvironmentReady()` (`desktop-shell-environment-process.ts`). The last result is cached in `user-data/shell-environment.json` (0600, keyed by platform, shell and HOME, probe-allowlisted names only) and applied at once on the next launch; a refresh is applied over the launch environment, not over the cached one. The refresh probe must also *run* in the launch environment (`ShellEnvironmentCommand.env`, a snapshot taken before the cache applies): a login shell keeps the PATH it inherits (`path_helper` appends it, `.zshrc` prepends to it), so a probe that inherited the cached PATH echoed every cached entry back and a venv `bin` from one terminal-launched Host stayed in every later launch. A name the refresh no longer reports goes back to its launch value, and a cached desktop-session name (`DBUS_SESSION_BUS_ADDRESS`, `XDG_SESSION_*`, `XDG_CURRENT_DESKTOP`) never replaces one the launch has. Only the desktop app writes the cache: a Host can be started by `openwaggle …` from a terminal or an agent shell, whose PATH would otherwise become every launch's. A Host the app launched (the shim or the GUI sets `OPENWAGGLE_SHELL_ENVIRONMENT_REFRESHED_SINCE`, which the Host takes out of its environment) waits up to 12 s for the app's refresh in the cache instead of running a second login shell, and probes itself (without writing) only if it does not come, or at once when the app marks that its refresh found nothing (`refreshFailedAt` in the cache file, which keeps the last good result; V1 P3-3); a launch runs one login shell, not two. The app caches only the PATH entries its shell produced: an entry its own launch PATH had is dropped unless it is a default session directory (launchd's, systemd's) or the previous cached result had it, so a GUI started from a terminal never caches that terminal's venv or `node_modules/.bin` (V1 P3-2). The Host also fills `DBUS_SESSION_BUS_ADDRESS` from the runtime directory before Electron is ready (`linux-session-bus-environment.ts`), since it no longer inherits a hydrated environment and Electron's `safeStorage` reads it at ready. A spawn that bypasses those chokepoints may still see the unhydrated PATH for the first ~0.5 s of a launch without a cache. Measuring it needs a real-ish HOME: the harness gives every run a new HOME, so a cached run must rewrite the cache's HOME (a template `.zshrc` with `sleep 0.3` moved Host listening 885 → 561 ms and the shell 991 → 673 ms). Started together on a loaded machine, the prelaunched Host's cold path stretches from ≈450 to ≈750 ms because both processes parse the same bundle at once.

`src/renderer/index.html` holds the startup frame (kept identical to `StartupSkeleton` by a component test), so the window paints before the renderer's scripts run. It sits outside React's root, over the window (`#startup-frame`, aria-hidden), until the app shows the shell or an error/update screen (`useStaticStartupFrameUntil`): Chromium drops an image as the LCP candidate when its element leaves the DOM before the paint is reported, so letting React replace the page's frame made the late shell the LCP on a busy renderer. Its welcome mark is inlined (`?inline`) and is the launch screen's largest image, so LCP is the first paint; `WelcomeScreen` imports the same inlined mark so it never blinks. The frame has no text, so the shell's first layout used to load the UI fonts (a 116 ms forced layout); React's copy of the frame lays out invisible text in the shell's faces while the Host starts (not in index.html, where it would delay the first paint). The page's one inline script applies the cached interface scale before that paint; its hash is in the CSP (`STARTUP_APPEARANCE_SCRIPT_HASH`, a unit test recomputes it from the file and `bun run check:renderer-csp`, inside `check:renderer-bundle`, from the page the build wrote, so a build step that rewrites the script fails `bun run check`). The window's OAuth lifecycle check used to run at once and load Pi's SDK plus a ModelRuntime (≈95 ms) in the window process while it opened; it now first runs 15 s after start.

## A measuring instrument that reads innerText measures itself

A probe that polled `log.innerText` every 8ms to detect a rendered transcript reported roughly 1,000ms for every session switch, suspiciously constant. `innerText` forces synchronous layout, so on a 50,000px subtree the poll loop was the cost being reported. A `MutationObserver` on the same element put the real figure at 221-267ms.

Two symptoms mark this mistake: a number that barely varies across different inputs, and a blocked-time total that does not add up to the wall clock. When the timings look suspiciously flat, suspect the instrument before the application. Use `MutationObserver`, `PerformanceObserver` or a CDP trace, none of which read layout.

## Filed under "Pi Runtime Memory"

- First-turn injection is measured through OpenWaggle's own Run composition, not bare Pi: `bun run perf:first-turn-prefix` (in-process, every first-party extension, faux provider, o200k per section and per tool; also the CI ratchet budget in `scripts/perf/first-turn-prefix/first-turn-prefix-budget.ts`; `run-composition.ts` builds the Run with the Host's own builders, `classicRunInlineExtensions`, `createRunSessionsExtension`, `createRunTrustedExtensionFactories` and `runSystemPromptAppendices`, so add Run extensions there, not beside them; the prefix varies by about ±10 between runs because the temporary project path is random) and `bun run perf:first-turn-prefix:packaged` (a packaged app's real `openwaggle run` request to a local recording provider; `--setup maintainer` adds heavy MCP, skills and AGENTS.md). On beta.27 an empty project's first request was ~13.3k o200k (~22k Opus; about 3.8k after v1, see "The first-turn prefix is a budget" below) and a maintainer-like setup ~32.7k o200k (~54k Opus); the old `benchmark-first-turn-tokens.ts` (1,609 tokens) measured the bare Pi SDK and was removed. Pi still discovers user skills from `~/.agents/skills` (agentskills.io convention) even with a fresh agent dir. Historical (pre-v1) container results, superseded by the v1 rerun in `scripts/benchmark-docker/results/`: Equal-footing OpenRouter/z-ai-glm-5.3-flash comparisons (2026-09-02, pristine pinned Docker containers via `scripts/benchmark-docker/run.sh`, wire-truth from the logging proxy): Pi CLI 0.84.4 1356, OpenWaggle bundled 0.81.1 1576 via its native provider (1319 when routed as a raw openai-completions endpoint), Reasonix 1.35.0 5279 on the wire (its CLI reports 10558 because it re-sends the conversation to a completion validator - report the wire), opencode 1.18.26 7054, Codex CLI 0.150.1 9957 (Responses endpoint needs `model_reasoning_effort` set or OpenRouter rejects the bare `reasoning.summary`), Claude Code 2.1.247 17608 (a run against the real user home measured 22260 - installed plugins alone added ~4650 tokens, which is why the container harness matters; native Bedrock opus via `cc-w` measured 16911). Cross-harness turn-1 injection varies ~13x with the same model. Routing notes: Codex needs a custom `[model_providers.*]` with `wire_api = "responses"` AND `model_reasoning_effort` set, because OpenRouter's Responses endpoint rejects a bare `reasoning.summary`; opencode takes an `@ai-sdk/openai-compatible` provider in an isolated `XDG_CONFIG_HOME`; Gemini CLI 0.31 cannot be routed (auth types are Google-only and the user's Code-Assist-for-individuals tier is deprecated); Cursor CLI is login-walled and speaks Cursor's proprietary protocol, so it cannot be pointed at OpenRouter. A local forwarding proxy in front of OpenRouter is the reliable way to observe per-call prompt_tokens when a harness aggregates or rewrites usage; it must stream chunks through incrementally (buffering whole SSE responses makes agents time out and retry ~13x, which poisons CLI-reported sums). The full reproducible harness (pinned-version Dockerfile, per-agent configs, streaming proxy, results parser) ships in `scripts/benchmark-docker/` and feeds `website/src/data/benchmark-results.json` -> `benchmarks.ts` for the docs page at `/docs/using-openwaggle/token-benchmarks` (a decision demoted the section off the landing page: aider at 587 and DeepSeek Harness sdk-minimal at 1115 beat OpenWaggle's 1609 on turn-1 injection, so no superlative claim is defensible; OpenWaggle stays in the lean tier, 6-11x lighter than Codex and Claude Code). A task-efficiency benchmark (same model, same small self-judging tasks, tokens-per-solved-task, e.g. on aider's exercise set) was scoped and parked as a possible v2. The repository-standards guard forbids the legacy vendor runtime name; benchmark files are recorded as exempt in `scripts/standards/forbidden-references.ts` because the benchmark must name its subjects. Measuring headless agents requires isolated homes: `PI_CODING_AGENT_DIR`, temp `CODEX_HOME` with a symlinked `auth.json`, and `--setting-sources`/`--bare` break Claude's OAuth refresh, so only `--disable-slash-commands` plus `--strict-mcp-config` is safe there.

## Filed under "Syntax And Workspace Editing Memory"

- Chromium long-task entries measure wall time, not renderer CPU time. A hidden Electron renderer on a shared GitHub-hosted Windows VM can be descheduled for several seconds during the roughly 40-second 1 MiB source scenario and report the pause as one long task. That one uncalibrated absolute assertion is therefore disabled only for hosted Windows; the scenario still enforces first paint, skeleton-before-tokenization, bounded DOM/worker/transfer work, completion, and renderer errors. Local, macOS, Linux, diff rendering, and shorter Windows interaction windows retain their absolute long-task budgets.

## Filed under "Startup compatibility needs persisted-profile tests"

Performance probes must not subtract independent process wall clocks. Hosted macOS produced negative renderer-keydown-to-main-write samples. Sample the renderer's monotonic clock again after the real main handler returns `written`; the extra return trip is a conservative upper bound under the same 16 ms budget. Native PTY prompt probes must send carriage return for Enter, because Windows console line input does not submit on LF. PTY test fixtures must await both latched process exit and resource drain before removing temporary HOME directories, or Bash can recreate history during recursive removal.

## Packaged app size and idle processes (Electron best build, November 2026)

`scripts/bench/electron-bench.ts` (workflow `bench-electron.yml` on throwaway `bench/electron-best-*` branches) measures the packaged app the way the Electrobun proof does. What it found:
- Windows backend-ready was 7-8 s, and about 4 s of that was the Session Host running `powershell.exe` five times at startup (`secureWindowsUserOnly`), each compiling the C# pipe-security helper with `Add-Type`. Now only a batch with a pipe target compiles it, and `prepareLocalSessionHostPaths` secures the directory and the existing capability in one run. The SQLite ownership lock is not the cause: a probe on `windows-2025` acquired it in 2 ms right after another process released it, and Defender real-time protection is off on hosted runners.
- The Session Host is a full Electron process that renders nothing, yet Chromium started a GPU process and a network service for it (about 90 MB on macOS). `in-process-gpu` plus `NetworkServiceInProcess2` in `disableHardwareAcceleration` fold both in. The GUI keeps both out of process, because its network stack parses arbitrary Browser preview sites.
- Chromium's audio service starts with the first Notification sound and never exits, even after the `AudioContext` closes (45 MB on macOS, about 80 MB on Windows). The GUI runs it in process with `--disable-features=AudioServiceOutOfProcess`. Electron 43 has no quit-timeout switch for it.
- electron-builder ships the full production closure, including every package the main bundle already inlines (about 80 MB: Effect, Pi, provider SDKs). `scripts/packaged-runtime-packages.ts` computes what the externals need at run time, and `unshippedPackagePatterns` leaves out the rest. Pi still reads README, docs, examples, `dist/core/export-html` and its themes from `PI_PACKAGE_DIR`.
- electron-builder's schema rejects `dmg.format: 'ULMO'`, so the dmg-builder patch maps `compression: 'maximum'` to ULMO (120 MB, against 146 MB for bzip2 and 178 MB for zlib). The NSIS payload ignores `compression`: differential-aware 7z uses 1 MB dictionaries.
- `electronLanguages` was left alone on purpose. Chromium falls back to en-US when the locale's `.pak` is missing, and that changes `app.getLocale()`, the renderer's default Intl locale and the Accept-Language that Browser preview pages receive.
- A `--dir` build next to an older DMG in `dist/` installs the older DMG: the bench installer prefers `*.dmg`. Remove stale artifacts first.

## Session data budgets (perf budgets file, November 2026)

`scripts/perf-gate/__tests__/session-data-budgets.integration.test.ts` writes the `sessions.*` metrics of `performance/perf-budgets.json`: a project of 3,000 Sessions plus one 2,000-message Session in the real store, then the renderer's reads served by `dispatchLocalSessionCommand` (bytes of each JSON reply, better-sqlite3 statements and rows through a prototype wrap in `sqlite-work-meter.ts`). The renderer's page and window sizes live in shared (`SESSION_CATALOG_PAGE_SIZE`, `SESSION_DETAIL_MESSAGE_WINDOW`, `TRANSCRIPT_WINDOW_PAGE_ENTRIES`) because tsconfig.scripts.json cannot resolve renderer `@/` imports, so the test mirrors the renderer's call sequence rather than running it. What it found: opening the sidebar does not scale with the project (two 100-Session pages, the pins by id, three exact counts: 37 statements, 868 rows, 166 KiB), but opening a long Session moves 1.06 MiB and reads 10,012 rows for a 400-message detail and a 200-entry transcript window: `getSessionDetail` loads the whole Session before `sessionDetailView` slices it (6,005 rows), and the workspace reply carries the full tree, 775 KB of its 949 KB. Seeding 3,000 Sessions through `createSession` and `updateSessionTitle` took 15-26 s on a loaded machine (one fsync'd transaction per call), so the workload writes their rows in one transaction; it measured the same values as the per-call seed. The Host coalesces concurrent reads of one Session (the Pi file refresh is shared while in flight), so the reads run one after another to keep the counts independent of timing.

## The Performance Gate (perf-gate, November 2026)

`.github/workflows/perf-gate.yml` is the required `Performance Gate` check: deterministic budgets in `performance/perf-budgets.json` plus an A/B timing job (`scripts/perf-gate/`, `.agents/verification.md` for how to read a failure and reproduce it).

- Labels. `perf-budget-increase` accepts a budget higher than main's. `perf-regression-accepted` accepts a timing or memory regression, or a loosened `thresholds.json`. Each counts only when a user with the admin or maintain role added it last, after the workflow run's first attempt was created (`gate.ts labels` reads the issue events, the run's `attempts/1` and the actor's permission): re-running the failed job keeps the label, a new push needs it again. The gate, thresholds and reporter always come from main: a pull request cannot loosen its own judge. `perf-report.yml` (`workflow_run`) posts the comment from main's code and treats the artifact as untrusted (`report-data.ts`).
- Noise. Six base-vs-base runs of 10 pairs on ubuntu-24.04, unpackaged under xvfb. The worst paired median was 2.6% / 43 ms for a timing (cold backend ready), 0.6% / 3.7 MiB for memory, 1.5 IPC calls on a cold launch and 0 processes. With 6 pairs cold chat ready reached 9% (155 ms), so the gate runs 10. Thresholds: timing 6% / 60 ms, memory 3% / 8 MiB, processes exact, IPC calls 10% / 3 (`performance/perf-gate/thresholds.json`). The job takes about 11 minutes: install 41 s, display 16 s, both builds in parallel 49 s, measuring 434 s for 22 launches.
- IPC calls until chat ready race the milestone. On cold launches it is 19-23 and on warm ones 17-37, depending on whether git, skills and project-config calls land before chat ready. That is why it has a floor of 3 and is not in the budgets file. A single extra startup call is under that floor. A burst shows up, and `ipcChannelsUntilChatReady` in the artifact names the channels.
- Demonstrations, from throwaway `bench/perf-gate-*` branches judged at the final thresholds. A 300 ms `Atomics.wait` at main startup measured +260 to +282 ms on all six readiness metrics and failed. An extra `ELECTRON_RUN_AS_NODE` child at startup failed processes (+2 idle, +3 after a turn) and main RSS (+208 MiB, counted under `main`). A doubled sidebar payload with the budgets file regenerated failed `sessions.sidebar.bytes`, 169984 -> 322560. All six noise runs passed.
- A merge base from before the Bun move installs and builds with pnpm. The workflow reads each checkout's `packageManager` field.
- Windows and macOS timings run nightly in `bench-electron.yml` (`ab` job), comparing main as it was 24 hours earlier with main now. They gate nothing.
- `OPENWAGGLE_PERF_BUDGETS_WRITE` is a directory for measurement fragments, not a flag: `=1` writes `./1/`.
