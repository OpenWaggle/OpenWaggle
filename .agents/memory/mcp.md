# MCP

MCP on Pi's built-in MCP extension: configuration files, the connection pool and its
memory cost, OAuth sign-ins, approval, sampling and elicitation, the hardened fetch, the
Registry installer, conformance tests and binary payload handling.
Load when touching `src/main/adapters/mcp/`, Settings > MCP or `bun run test:mcp:conformance`.

## MCP Runtime Memory

- Never put keychain access (`safeStorage`, the MCP vault, the encrypted OAuth store) on the Host start path: with a scratch HOME, `safeStorage` stalled the main loop for 90-185 s, and Host start awaited the ADR 0051 migration's sign-in step. File migration (`migrateOpenWaggleMcpFilesOnce`) is keychain-free and awaited at start; the sign-in step (`migrateOpenWaggleMcpSignInsOnce`) starts after the Host listens (`startServicesAfterListening`), and only MCP connect and sign-in paths wait for it. The MCP vault uses `safeStorage`'s async API through the SecureStorage port's async members (`decryptStringAsync` opens `encryptString` output, same `v10` format, verified with `--use-mock-keychain`). 704754061 forwarded only the synchronous members, so every vault read and write went back to the main thread until the port carried the async ones; `encrypted-mcp-secret-vault-async.unit.test.ts` now fails if the production default loses them, and the sign-in step reads the old sign-ins it needs between two queued passes, outside the migration queue and lock (none once recorded), so a stall there leaves the Host responsive. The encrypted OAuth store is still synchronous (Pi's backend contract): moving an old sign-in into it and every OAuth connection block the main loop while the keychain stalls. An overridden profile (`OPENWAGGLE_USER_DATA_DIR`) sets `app.setAppLogsPath(<userData>/logs)` in `configureAppStoragePaths`, so QA logs, the Host's included, stay out of `~/Library/Logs`.
- MCP runs on Pi 1.0's built-in MCP extension (ADR 0051); `docs/mcp-runtime.md` is the map. SDK sessions do not load Pi's built-ins, so `pi-agent-kernel-run.ts` adds `createOpenWaggleMcpExtensions()` (`src/main/adapters/pi/mcp/`) to every Run's `extensionFactories` as the `builtin:mcp` inline extension (replaceable, like `builtin:codemode` and `builtin:tool-search` from `pi-built-in-extensions.ts`), so Pi's `-builtin:mcp` in the `extensions` setting turns MCP off as in the Pi CLI. Like other first-party factories, it is dropped in hidden automation unless `OPENWAGGLE_AUTOMATION_FIRST_PARTY_EXTENSIONS=1`; then `pi-provider-resources.ts` also names `builtin:mcp` explicitly, because `noExtensions` skips built-ins that are not named.
- Pi's MCP extension notifies "MCP servers are still connecting; their tools become available once connected." (`info`) from its `before_agent_start` wait whenever a direct-tool server misses `startupWaitMs`, which in OpenWaggle meant a toast on nearly every new Session. `forOpenWaggleMcpSurface` (`mcp-openwaggle-surface.ts`) wraps the factory and drops only `info` notices from `before_agent_start` handlers; the launch step already shows the server connecting. Failures still notify: Pi's `session_start` reports "MCP servers need attention" (`warning`) once every server's first connect settles, which the wrapper keeps (with its "Run /mcp to fix" line pointed at Settings > MCP); it is lost only when a server fails after the Run already ended (session_shutdown aborts the report). `mcp-openwaggle-surface.integration.test.ts` checks Pi's unwrapped extension still sends the connecting notice (so a Pi upgrade that moves it fails the test) and that a server that fails to connect still warns.
- Pi's plug-in points need symbols Pi 1.2.0 still does not export from its root: `McpOAuthCredentialStore` (the `credentials` option is that class, nominal through its private members), `signInMcpServer`, `createMcpAuthProvider`, `validateMcpServerConfig`, `mcpNamespace`, `getMcpToolExposure`, `resolveConfigValueOrThrow`, `resolveHeadersOrThrow`. The pi-coding-agent patch adds exports only (own commit); re-add them on every Pi upgrade. Without a `credentials` store Pi reads and creates `~/.pi/agent/mcp-auth.json`.
- OpenWaggle disposes the Pi `AgentSession` after every Run (`withPiSession`), so `createTransport` returns a lease on the Session's pooled connection (`adapters/mcp/pool/`): repeated `initialize` is answered from the cached handshake, `initialized` is forwarded once, request ids and progress tokens are renumbered upstream (every Pi client restarts at id 1), and closing a lease detaches instead of closing. Expired HTTP sessions and auth-required errors discard the upstream so Pi's own reconnect opens a fresh one. Pi only captures stderr when the transport `instanceof StdioTransport`, so the pool appends the stderr tail to start and handshake errors itself.
- The leak this fixes: connections used to close only after settings/auth/vault changes, and a measured install held 9 copies of four `npx` servers (~700–900 MB per Session that ran a turn). Now a Session's connections close 5 minutes after its last Run (`beginRun`/`endRun` around `runPiAgentKernel`), on archive/delete through `runSessionRemovalHooks` in `withSessionDesktopRemoval` (covers Hive Worker auto-archive), at Host stop (`disposeAppRuntime`), and under an LRU cap of warm Sessions (now 3; Sessions with a Run are never evicted). pi-mcp's `StdioTransport` spawns servers in their own process group and kills the group (`taskkill /T` on Windows), which stops `npx`/`uvx` wrappers with their server; `pi-mcp-transport-layer.integration.test.ts` proves it with a real wrapper process.
- MCP memory and start cost (v1 performance, October 2026): besides the warm cap of 3 Sessions above, a Worker whose Delegation is `ready_for_review`/`accepted`/`cancelled` closes its servers 60 s after its Run (`mcp-settled-worker-idle-policy.ts`). Each pooled connection records its server's `initialize` + `tools/list` pages in `<userData>/mcp/tool-catalogs/` (key: identity, connection fingerprint with `cwd: ''`, project); a catalog < 24 h old answers a lease's `initialize`/`tools/list`/`ping` at once, and a stdio server starts only on the first other request (`mcp-connection-lazy-start.ts`), replaying the client's `initialize`, then re-lists and sends `notifications/tools/list_changed` if tools differ. A failed lazy start forgets the catalog. URL servers stay eager. Servers without a `description` get the first line of their cached `instructions` in `loadConfig`, so `<mcp_servers>` is byte-stable. npx/npm exec/pnpm dlx/bunx launches spawn the bin the runner resolved (background probe `--package=<spec> -- node -e …` printing PATH and execPath; `<userData>/mcp/package-runner-bins.json`, 24 h for tags, 7 d pinned; Check connection passes `refreshPackage`). Measured: wrapper tree 274 MB and 1.3–3.3 s to `initialize` vs direct 93–169 MB and 0.34–0.40 s (chrome-devtools-mcp); 6 Sessions × 2 npx servers 31 processes / ~2.0 GB → 7 / 0.47–0.73 GB when 2 Sessions call a server.
- R5 review fixes to the above (October 2026): package-runner resolutions are keyed by a `file:` spec's resolved folder and the content of the nearest `.npmrc` / `pnpm-workspace.yaml` too (one project's `file:./x` spawned another project's package); the probe never goes through Node's `shell: true` (on Windows `cmd.exe` split its source at `||`, so the bypass never worked there): it runs `cmd.exe /d /s /c` with one cross-spawn-style escaped line (`windowsCommandLine`), and a failed probe is not retried for a day unless Check connection refreshes it. A probe that times out has its whole tree killed (`createExecProbe`: its own process group on POSIX, `taskkill /T /F` on Windows); `execFile`'s timeout killed only `cmd.exe`/`npx`, and their `node` and install ran on (V1 P3-1). `node <bin>` is used only for a plain `node` shebang; other shebangs run the file itself on POSIX and keep the runner on Windows, and `bunx --bun` keeps the runner. A stdio server's `env` values (`!command`) are resolved once per spawn (`openPreparedPiMcpUpstream`). A connection serving its catalog is not `isReady` and is left out of `connectionStates`, and served `tools/list` pages carry `{ served: true }` so they record App tools but never the status registry (a failed check stays failed). Check connection, sign-in/out, and turning a server off forget its catalog (its own handshake lacks OpenWaggle's client capabilities, so its pages are not written instead). A lazy start OpenWaggle interrupts by closing (`closedByOwner`) keeps the catalog. Catalog and bins files are 0600 in 0700 directories, the bins file is renamed into place, and a Host's first catalog write prunes catalogs past the TTL. The catalog-fill and runner-probe waits each take a third of the server's Pi `timeout` (60 s default), capped at 30 s. The first-request unknown-App wait stops for a server whose leased connection failed (`pool.connectionFailed`) or that a check or listing saw `failed`/`needs-sign-in` since the Run started; an older identity-wide state is not used to skip it (it has no project, and may predate a fix: V2 P3-2). A file's `direct` stays `direct` in a Run where codemode cannot reach MCP tools (`mcpCodemodeReach`: a `codemode` tool with `reachesTools` registered, and `autoEnableCodemode` or already active), by maintainer decision; `openwaggle mcp add --exposure direct` stays refused (exit 2). `knownMcpAppTools` asks the project catalog before the identity-only status registry. The settled-Worker idle policy reads `SessionDelegationRepository.delegationStateOf`, injected at Host start.
- Configuration is five files folded in order (`~/.pi/agent/mcp.json`, `~/.openwaggle/mcp.json`, `.mcp.json`, `.pi/mcp.json`, `.openwaggle/mcp.json`) by `domain/mcp/config/mcp-config-merge.ts`, a port of Pi's `loadMcpConfig` that applies Pi's project-override rule to every file after the first. Pi's `loadConfig` is synchronous, so the config (vault references resolved) is loaded before the Pi session is created. Pi rejects `type: "sse"` and `ws:` URLs; OpenWaggle accepts them, gives Pi a plain URL entry, and keeps the transport kind in a side map for `createTransport`.
- Sign-ins: `McpOAuthCredentialStore` over `mcp-oauth-state-backend.ts`, a synchronous `AuthStorageBackend` (Pi's contract is sync) that merges Pi's `mcp-auth.json` (read-only) under OpenWaggle's encrypted `<userData>/mcp/oauth-states.json` (per build: dev and release have different safeStorage keys; a decrypt failure leaves the file untouched and refuses writes, only a parse failure sets it aside; the old shared `~/.openwaggle/mcp/oauth-states.json` and `vault.json` are copied once by the build that can decrypt them). Removing a Pi-only key writes a tombstone with the hash of Pi's value, so a later `pi mcp login` shows through. A refresh of a Pi-file token in OpenWaggle stores the rotated tokens in OpenWaggle only; a server that rotates refresh tokens then invalidates the copy Pi's CLI still holds.
- Runtime MCP exposure (ADR 0051 amendment): OpenWaggle runs a file's `direct` (server or `toolExposure`) as `codemode` in `loadMcpRuntimeConfig` (`withOpenWaggleRuntimeExposure`); `merged` and the files keep `direct` for `pi`. MCP App tools stay declared: known ones (Session `mcp-app-registry`, else status registry by identity) become exact `toolExposure` `direct` in Pi's `loadConfig`, which is also the only thing that now makes Pi's 1.5 s startup wait apply; newly listed ones are re-registered `direct` by `withOpenWaggleMcpExposure`'s `registerTool` proxy, which relies on Pi's MCP tool `namespace.aliases[0]` = server and label `<server>/<tool>` (`pi-mcp-runtime-exposure.integration.test.ts` fails if Pi changes that). Registered (extension) servers only get the stable `direct` rewrite in `getMcpServers`: Pi reconnects a registered server whose config JSON changes. Settings offers codemode/hidden (+ `deferred` only while a file sets it).
- Approval: the companion extension's `tool_call` handler raises an authorization for every `mcp__*` call, including codemode children (`parentToolCallId`), keyed `{ requesterId: mcpServerIdentity(name, command|url), resource: Pi tool name }`. Pi's resource tools are not gated (read-only).
- Sampling and elicitation are answered in the pool (`handleServerRequest`) through the interactions of the Session's live Pi session (attached at `session_start`); between Runs they are refused. MCP Apps: Pi strips `_meta` from tools and results, so the pool's `observeResult` records `tools/list` `_meta.ui.resourceUri` per Session and server, the companion `tool_result` handler adds `details.mcpApp`, and `mcp:read-resource`/`mcp:call-app-tool` go over the Session's pooled connection (opened on demand with the current config). The App descriptor's `serverInstanceId` is the server name and `serverConfigHash` the server identity. The frame's CSP allows the origins the resource declares in `_meta.ui.csp` (ADR 0053; before it the grant list was always empty, so CDN-loaded Apps such as Atlassian's Jira App rendered as an empty 320 px box). Most real Apps are a stub HTML that loads a module script from the server owner's CDN; the sandboxed frame has an opaque origin, which works because those CDNs send `Access-Control-Allow-Origin: *`. A `srcdoc` App frame inherits the renderer's page CSP (no network scripts), so App documents are served from `openwaggle-mcp-app://frame-<uuid>/document` (`mcp-app-frame-protocol.ts`, registered over `mcp:register-app-frame`) with their own CSP header; the frame is `allow-scripts allow-same-origin` on that unique origin (Atlassian's App reads `document.cookie` and IndexedDB and throws in an opaque origin), and the origin's storage is cleared on unregister. OpenWaggle's theme is the `data-theme` attribute, not a `dark` class; Apps were told `light` until `use-mcp-app-frame-layout.ts` read it. The frame starts 1 px high (not 0: Chromium throttles rAF in zero-area cross-origin frames, and the ext-apps `autoResize` measures in rAF), takes the App's reported height, and shows a note after 15 s without a handshake.
- Opening Settings > MCP must not start servers. It reads `mcp:get-server-statuses` (warm pooled connection by server identity, else the in-memory last check per identity, else not checked) and only **Check connection** calls `mcp:inspect-server`. The pool's `connectionStates(identity)` is read-only: no request, no recency change, no connection handed to another Session; tools come from the `tools/list` results `observeResult` saw. Before this, every open spawned every enabled stdio server once (useQueries over `inspect-server`).
- `bun run test:mcp:conformance` drives pi-mcp's `McpClient` through a pool lease and OpenWaggle's hardened fetch. The script is `.mts` because pi-mcp and pi-coding-agent are ESM-only and tsx, which ran scripts before ADR 0064, loaded `.ts` scripts as CommonJS; it must not import modules that import `@earendil-works/pi-coding-agent`.
- The hardened HTTP fetch (`mcp-server-fetch.ts`) pins DNS per request and bounds bodies and SSE events at pi-mcp's 16 MiB; the configured server may be plain HTTP or private (Pi parity), other hosts (OAuth endpoints) must be public HTTPS, and redirects may not change host. Pi's MCP tool registration only forces an object root (`toParameters`), so the transport layer's `adaptResult` hook rewrites every `tools/list` result with `providerToolParameters` (`adapters/pi/mcp/mcp-tool-schema-repair.ts`) before Pi's client reads it; `pi-mcp-tool-schemas.integration.test.ts` pushes a root-`anyOf` server tool through Pi's real Bedrock and OpenAI request builders.
- MCP Registry install (`adapters/mcp/registry/`) writes a plain Pi entry through `McpConfigurationService.addServer`. Pi resolves `$NAME`, `${NAME}`, and a leading `!command` in every `env` and `headers` string when it creates the transport, so any value taken from the Registry or an MCPB manifest is escaped (`$` → `$$`, leading `!` → `$!`); otherwise a remote server's declared header default could run a local command. Registry secrets become `{ "secret": NAME }` vault references, which is why installs only write OpenWaggle's files. The public Registry (`/v0.1/servers?search=`) took 0.5–13.5 s per search when measured, so requests get 30 s.
- Datadog's `datadog_mcp_cli` 0.2.8 (stdio proxy to `mcp.datadoghq.<site>/api/unstable/mcp-server/mcp`) can get stuck (trigger not pinned down: failures followed a 401 retry or a reconnect after the server's ~60 s idle GOAWAY, but a standalone probe with OpenWaggle's `initialize` and 5–120 s gaps never reproduced it): a request comes back `HTTP 400 Accept must contain both 'application/json' and 'text/event-stream'`, and it answers "Internal error" (-32603) to every request for the rest of the process's life. The proxy's own log is `~/Library/Logs/Datadog/datadog_mcp_cli.log.<date>`. Because the Session pool keeps the process warm across Runs, every Run warned "datadog: failed: Internal error". `McpUpstreamReplacement` now replaces a process whose listing fails with an internal error and sends the listing again (once a minute at most, only when nothing else is open; tool calls are never resent). `pi-mcp-stuck-server.integration.test.ts` reproduces it with a real child process. Datadog also deprecates that endpoint in its `initialize` instructions; `--endpoint-path v1/mcp` works with the same proxy.
- Never serialize MCP binary payloads into model-facing tool text. Base64 tokenizes at ~1.6 characters per token, so one Chrome DevTools screenshot (433,816 characters) added ~271k tokens and overflowed a 458,752-token window in a single tool step; Pi's chars/4 estimate predicted only ~108k, so the pre-sampling threshold could not catch it. Pi's MCP extension now converts results itself (`convertMcpResult`): images become native image content, other binary resources are saved to temp files and named by path, and text over 20 KB is cut in the middle with the full text saved. `src/shared/utils/mcp-binary-payload.ts` remains only for MCP App draft text; a change that puts raw MCP content into model-facing text must keep this rule.
