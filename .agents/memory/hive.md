# Hive

Hive coordination: the `hive` tool and CLI naming, Agent definitions offered to agents,
tool defaults, next-actor grouping, waking an idle parent, the run ceiling for Workers,
parents showing running Workers, Worker cleanup and the Hive panel.
Load when touching `hive-*` application code, `features/hive-panel`, `features/agent-definitions`
or Worker authority.

## The coordination surface is named `hive` (ADR 0053, October 2026)

The Pi tool, CLI group and MCP tool are `hive`, `openwaggle hive` and `openwaggle_hive` (`@shared/constants/hive`). The former `sessions`, `openwaggle sessions`, `openwaggle delegations`, `openwaggle agents list|search` and `openwaggle_sessions` names are refused, not aliased: the top-level router answers "It is now 'hive'", the Hive CLI and `openwaggle agents` name the replacement subcommand, and an Agent definition listing `sessions` gets `unknown-reference`. A transcript keeps its recorded `sessions` calls; the renderer shows them as an unrecognized (`other`) tool. Each tool action is the `hive` subcommand and MCP operation of the same name with `-` for `_`, so the CLI routes flat names (`delegation-submit`, `queue-withdraw`, `exports-wait`, `authorization-set <id> inherit`), and `mcpSessionCliOptionsV2` passes the MCP operation through as the CLI command unchanged; `hive-action-vocabulary.unit.test.ts` fails if a tool action or MCP operation has no subcommand. Scheduled tasks keep `openwaggle schedules` and have no MCP operation; `openwaggle_hive` also carries `agent-definitions-list|search`, answered in the MCP server process for a project inside the caller's workspace grants (ADR 0053 amendment). Both it and `hive agent-definitions-list|search` apply the project's `agentDefinitionTogglesByProject`, as the tool does, so they never list a definition spawn and launch refuse. `resolveAgentDefinitionProject` (`agent-definition-project.ts`) first maps the caller's directory (CLI `--project`/cwd, MCP grant; as given and its realpath) by the Host's `projectOfWorkspace` rule, shared as `projectOfWorkspacePath` in `adapters/workspace-project-authorization.ts`: an opened project is itself, a ready managed worktree stands for its Session's project, and (discovery only, `insideManagedWorktrees`) so does a directory inside one. A plain subdirectory of a project is its own project, because `create`/`launch` take projectPath as given and an MCP `--workspace /repo/src` grant must not read /repo. Without the worktree mapping a worktree matched no toggle entry. Settings are read first, so a Settings failure lists nothing. The vocabulary test lists these exceptions explicitly. App migration 71 (`hive-tool-name`) rewrites `sessions` to `hive` once in stored `session_execution_profiles.profile_json.tools` and `resolved_agent_snapshot_json.tools` (a fork intersects with the snapshot), because a Session created from a definition listing `sessions` would otherwise silently lose the Hive tool while its identity still lists `sessions:*` capabilities; that is Host-authored data, not an accepted alias. The snapshot's `contentDigest` is a SHA-256 of the parsed definition, so migrated snapshots no longer match it; nothing checks it, and a future integrity check must accept them. Internal module and identifier names (`sessions-tool-*.ts`, `sessions-cli-*.ts`, `SessionsTool*`) were left alone, and so were the `sessions:*` capabilities and the `openwaggle:sessions` export-authorization requester id, because they name the Session concept or persisted keys, not the surface. No contract revision changed: the Host protocol, Session Control/Query v2 and CLI `schemaVersion` 1 payloads are identical; only the front-door names moved.

## Agent definitions reach the agents that start Sessions (#405, November 2026)

The Hive panel's `Bot` glyph for a definition Worker is an amendment to ADRs 0020 and 0054; every other surface keeps the pickaxe for every Worker.

Agents ignored them: one Hive spawned ~25 hand-written "independent code reviewer" Workers next to a `reviewer` definition, because nothing in the prompt named the definitions, spawn's `agent` was undeclared in the hot schema (no description), and the only guideline said "do not assume named roles exist". Now `createRunSessionsExtension` composes the hive tool with `available-agents-prompt.ts`, which writes an `available_agents` custom section (after `cwd`, read once per Run, so byte-stable) listing the project's enabled, valid definitions (name + description, 24 max, 280 chars each, XML-escaped) for a Session that can spawn/launch/create and whose allowlist allows `hive`; an empty catalog adds nothing, so the empty-project first-turn budget is unchanged. `agent` is one shared described schema (`sessionsToolAgentDefinitionName`) declared for hot spawn; a different `agent` schema anywhere (the schedule launch target had one) turns the declared property into an undescribed union. After a spawn without `agent`, `suggestAgentDefinition` (`domain/agents/agent-definition-suggestion.ts`) adds a `suggestedAgent` text block only when the objective states its own role in so many words, the first clause starting within 240 characters, outside quoted text (double or single quotes, inline code, ``` or ~~~ fences, indented and blockquote lines; a quoted word inside the phrase drops it), that opens with "You are", "You're", "Act as", "Serve as" or "Work as", whose noun phrase has the definition's name, as written or plural, as its head. The phrase may start with an adverb (now, again, still; "also" marks a second role and drops it) and one determiner, holds up to five words, and ends at a preposition, a comma, "not" or a contraction ("who's"); a possessive ("the reviewer's assistant", "the reviewers' pair") or a second role, joined by and/or, `&`, `+` or `/` ("the reviewer and fixer") or after a comma, a dash, "as well as" or "then" ("the reviewer, and the fixer", "the reviewer as well as the fixer", "the planner, implementer and tester"), drops it. Text after a line ending in a colon, emphasis around it allowed ("…each with this objective:", "**Worker objective:**") is someone else's and is not read, and so is text after an inline colon following an introducing word ("each with this objective: …", "Each Worker gets: …"), unless it is an own-role label ("Role:", "Your task:", `OWN_LABEL`); a leading own label ("Objective: You are…") is read past. Only that first statement counts, one after a lead-in or given by a label included ("For this ticket, you are the implementer", "Role: implementer", "Your role is…" name no role and stop the scan, an own label before them included), and a role over "your own" work ("Act as the reviewer of your own diff", but not "of your teammate's change") is a self-check, not a role, and an "… as" one followed by a separate subject ("Act as reviewer, I found…") is the speaker's. The rules live in `agent-definition-role-statement.ts`, with direct tests of each rule's main case; only the first 4096 characters are read. A bare "As" or "Acting as" is no opener: "As the reviewer of PR #405 found, fix…" is a conjunction far more often than a role. Every word before the head must be a name word or one of a closed list of role modifiers (`ROLE_MODIFIERS`: independent, senior, second, code, fresh, …), so "You are helping the reviewer", "coordinating three reviewers", "the implementer after reviewers" and "no longer reviewer" name no role. Name words are kept whole, short ones included (`ux-reviewer`, `qa`), and >=25% of its description stems (the name's own left out) appear in the title or objective; a name the phrase states more words of wins first (`code-reviewer` over `reviewer` for "an independent code reviewer"), and a near tie suggests nothing. Each looser rule failed review with real objectives: the whole objective flagged implementers that "spawn a reviewer", a 240-character opening flagged "Fix the tests, then hand off to the reviewer", a first clause or title flagged "Address the reviewer's findings" fix-ups, an unanchored "you are" flagged "the bug you are seeing … the reviewer", a determiner allowed anywhere flagged "You are helping the reviewer", filtering short name words made `ux-reviewer` match any reviewer, and stemming made `tester` match "the tests". Against 800 local spawns and a `reviewer` definition it hints 172, all review spawns; it misses those that say only "review" or never say "You are …", acceptable for a hint whose false positive would give the next Worker the wrong instructions. The section, guideline and `agent` description say "give it only the task", not "objective", because `create` takes no objective and would drop one. Prompt and hint discover with `ALL_AGENT_DEFINITIONS` and drop invalid definitions before cutting, so a broken file never takes a valid one's slot. `agent_definitions_list|search` used to accept `projectPath` and drop it (TypeBox objects admit unknown properties, and the variant did not declare it), reading the caller's own project: it is now declared (`sessions-tool-agent-definition-actions.ts`). Another project needs `sessions:create` and `sessions:discover` (the guideline offers `projectPath` only then), then a Host `list` probe (`agentDefinitionProjectProbe`, `limit: 1`, that `projectPath`, archived included; `session-tool-cross-project-authority.unit.test.ts` runs the exact payload): capabilities alone are wrong, because the Host lets only a root Session whose Run reaches every project name another project (`assertSessionAgentLifecycleProjectKnown`, `sessionAgentRunReachesEveryProject`), so a root launched by a project-scoped caller gets the Host's `target_scope_denied`, the same answer for a project and any other existing path. A Worker never holds `sessions:create` (`GRANTABLE_CHILD_CAPABILITIES` leaves it out), so it gets the tool's `capability_denied` before the Host is asked; the Host check is defense in depth for it. A caller in scope is then refused only when the path is neither `known` to `resolveAgentDefinitionProject` (Settings or a managed worktree) nor has a Session; a missing directory is refused before the Host is asked, which, like `list`, tells a caller only whether it exists. The grant is the Run's, so a root whose CLI profile later lost `sessions:create` can still read names and descriptions where it can list Sessions (accepted). The Hive panel shows `lineage.agentModelId`/`agentThinkingLevel` (from `profile_json`, set only with `agentDefinitionName`) as the row's identity line, with the composer's level labels (`THINKING_LEVEL_LABELS`, now in `@shared/constants`) and "No thinking" for off, which beside a definition name would read as the definition being off; they are the current values (the model picker and a Run's thinking level rewrite `profile_json`), not the creation-time ones.

## Hive tool defaults before 1.0 (issue #352, October 2026)

- A catalog query's `workingPath` (the tool's and CLI's default `current` scope) means the caller's whole project. `resolveCurrentProjectQuery` (`sqlite-session-query-current-project.ts`) rewrites it to `projectPath` in the query repository, after authorization: a query without `projectPath` is unscoped discovery bounded by the caller's scope, so a Worker (reach = its Hive) sees its Hive's Sessions in every worktree of the project. Sending `projectPath` instead would be target-authorized and refused for a Worker (`target_scope_denied`), which is why the tool sends `catalogScope: project` for the caller's own project as `workingPath` too. The mapping matches `projectOfWorkspacePath` with `insideManagedWorktrees`: a ready managed worktree (or a directory inside it) stands for its Session's `project_path`; any other path is itself. The SQL-level `working_path` branches in list/search/delegation queries stay for direct callers but are not reached through the repository.
- The tool and CLI send `archived: false` on `list` by default (the SQL default still lists both, for the renderer). `delegations-list` SQL already listed every state when `states` is empty (`['working']` there only keeps `sql.in` non-empty).
- Hive cleanup kept a Worker the user had visited because `browser-preview-owner-leases.ts` released an owner retained by an active Run only on the next acquire or release, and the Host had no trigger once the Worker was finished. The leases now re-run `releaseIdleOwners` when `activeRunIds` or browser tab groups change, and the background `HiveWorkerCleanup` layer (`hive-worker-cleanup-layer.ts`, `hive-worker-cleanup-retries.ts`) re-checks a Worker kept for desktop state (`open-in-app`, `open-terminal`, `running-service`) on a 15 s to 5 min backoff, bounded to 256 tracked Workers. Every keep reason is logged at info. Evidence: the beta.25 QA Worker's new-worktree child had a visit receipt from during its Run and none after, while the share-parent child was never visited.
- Run settlement no longer turns a Worker's own `needs_attention` into a host-captured submission. "Own" is read durably: `delegation_contracts.attention_cause = 'worker_request'` (since #380) and the latest transition, to `needs_attention`, was written at or after the settling Run's `session_runs.created_at` (a later Run, after the parent answered, settles as usual). A Host-set `needs_attention` still resolves to review when a later Run completes with text, and since #380 it is cleared when the next Run activates anyway.
- Queue outcomes renamed `followUpIds` to `remainingFollowUpIds` and a withdraw adds `withdrawnFollowUpIds` (kept through `deliverAfterQueueDecision`). Stored outcomes with `followUpIds` are upgraded in `decodeStoredSessionControlMutationOutcome`, so replays still decode. Clients decode responses exactly, so this and the other additive fields (`queueState`/`pauseReason` on queued Follow-ups, summary `depth`, spawn `title`, list `parentSessionId`) took Local Session protocol revision 27.
- The tool offers only permitted actions; `prepareArguments` (Pi runs it before schema validation) refuses another action with the capabilities it needs, and an unknown action by name. To return the raw arguments untyped, the tool registers as `registerTool<TSchema, unknown>`, and `assertSessionsToolActionArguments` is an assertion function that narrows them. `sessionsToolPromptGuidelines` composes each line from permitted actions only.
- Pi records the assistant message a Stop or interrupt cut off. One that streamed nothing is projected as a raw `custom` node (role null), keeping the Pi tree linkage, so the transcript and `items` show no empty reply.

## The Hive groups Workers by who acts next (ADR 0059, #380, October 2026)

- One rule, `hiveNextActor` (`src/shared/domain/hive-next-actor.ts`), answers `user | parent | worker | none` plus a reason. The renderer calls it through `hiveMemberNextActor` (`queries/session-hive-next-actor.ts`) for the Hive panel's groups and labels, the tree roll-up, the rail dot, the Queen's sidebar line and the Session Summary; the Host calls it for the query outcomes' `nextActor` (`withHiveNextActor` in `sqlite-session-query-next-actor.ts`, applied only when the dispatcher passes `pendingRequests`) and for the tree page's `needsYouCount` (was `attentionCount`). Do not add another "needs the user" predicate; `hiveStateNeedsAttention` and `hiveDelegationGroup` are gone.
- Facts: `delegation_contracts.attention_cause` (migration 74, `run_failed | worker_request`, read only while the state is `needs_attention`; null on old rows reads as `run_failed`); `parentWillAct` is derived at read time (`parentWillActSql`: the parent has `active_run_id`, or a running queue with a pending Follow-up), so "Stuck" is never stored; parked requests come from the in-memory `agent-loop-interaction-broker` (`hivePendingRequestsBySession`; an authorization confirm is an approval, any other non-notify interaction a question). In the window, the live status store wins over the catalog's `pendingInteractionKind`: `awaiting-input` means a request is parked, any other known status means none.
- Clears: `clearRunFailedAttention` runs in the Run lifecycle's `activate` and `startExternal` transactions (every Run passes one), returns the Delegation to `revision_requested` when the Host's failure transition came from it and to `working` otherwise, and the coordinators publish `session-list-changed` for parent and Worker (`publishDelegationAttentionCleared`). `clearWorkerRequestOnParentDelivery` runs in `executeMutation` (follow-up, message, start) and in the operation journal's `complete` (steer, promote, replace) when the caller is `session-agent:<parent>:…`; that clear rides on the delivery's own `session-state-changed`. A revision request cannot reach a `needs_attention` Delegation (it requires `ready_for_review`). Host failures and clears write `delegation_state_transitions` rows authored `session-host`, so `delegations-read` keeps the history.
- Freshness: the Hive queries are read again on `session-state-changed`/`session-list-changed` and on transport `agent_interaction_request`/`agent_interaction_resolved` (`session-hive-events.ts`); the sidebar catalog re-reads a parent's loaded `needs_attention` Workers whenever the parent's state changes (`withStuckCandidateWorkers`), because their `parentWillAct` was read with them.
- Query outcomes are not decoded exactly (`isSessionQueryResponse` is a shallow guard), so the additive `nextActor` kept Local Session protocol revision 27. Mutation outcomes are stored for replay and do not carry it. Desktop notifications (ADR 0062) later gate on Needs you as well: a Worker's Needs you and Stuck notify, its other outcomes do not.
- The panel's grouped view is `by-next-actor` in `useHivePanelViewStore`; version 1 of `openwaggle:hive-panel:v1` maps a stored `by-state` to it.

## Hive wake: an idle parent is woken when its Workers report (ADR 0030 amendment, November 2026)

- Bug: a Queen said "I'll report back when the Workers are done", ended its turn, and six Workers submitted 20–50 minutes later; no Run started. Two causes. `submitDelegation` (and a Worker's own `delegation-state` `needs_attention`) recorded no `session_orchestration_updates` row: only `settleWorkerDelegation` did, and it skips a Delegation already `ready_for_review`. And `deliverPendingToActiveRun` returned when the parent had no active Run, by ADR 0030's original design. Diagnose from the Host DB: a Delegation with an `agent-submitted` submission and no update row is the first bug.
- Recording: `recordWorkerOrchestrationUpdate` (`sqlite-session-orchestration-update-insert.ts`) names the Worker's latest Run; all inserts go through `insertOrchestrationUpdate`, which on the `(delegation_id, source_run_id, state)` unique key re-arms the row under the new id as `pending` (a submit, a revision request mid-Run, then a Run-end reply would otherwise fail the settlement).
- Waking: every former `deliverPendingToActiveRun` call site calls `notifyParentOfOrchestrationUpdates` (`application/hive-parent-wake-request.ts`), which asks for a wake when no live Run took the update; a Run that settles with nothing scheduled also asks. The request module is separate from `hive-parent-wake.ts` because the wake imports `executeSessionControlMutation`, which imports the coordinator. The Host handler (`session-host/hive-parent-wake-installer.ts`, installed in `startHostBackgroundServices`) runs wakes through `hive-parent-wake-scheduler.ts`: one per parent at a time, and parents a Run limit deferred are retried on every later request (≤256, a warning when full).
- Delivered means read: the orchestration extension uses `installDurableContextDelivery` with `acknowledgeWhen: 'model-request'`, so an update is marked delivered at the next `turn_start` whose session holds its entry. Pi defers a `triggerTurn: false` custom message sent mid-turn to that turn's end, so an update that reached the parent during its final turn used to be appended after the last answer, acknowledged at `agent_end`, and never read (`orchestration-update-acknowledgement.integration.test.ts` proves both cases on a real Pi session). Peer reports and specification updates keep the `persisted` default. A timestamp rule ("delivered after the settled Run's `terminalEventAt`") was tried first and missed this window and the Waggle one. A classic Run that requests a Waggle hands the updates still pending when it ends to the Waggle (`session-control-run-dispatch.ts`), so one its final turn put on the branch is acknowledged at the Waggle's first model request instead of waking the parent afterwards. During a requested Waggle the Session's active Run id stays the classic one, so `deliverOrchestrationUpdates` falls back to the `requestedWaggleRunId` sink (peer reports and specification updates still use only the classic key). An unreadable post-classic list falls back to none, and live delivery skips an id already on the branch, so nothing is sent twice. A live orchestration sink takes nothing before its `session_start` (Pi's loader `sendMessage` throws until `bindCore`), and the Pi delivery services wrap the synchronous `deliver*` in `Effect.try`, so a throw is a failed delivery, never a defect in the command that recorded the update. Peer-report and specification sinks have no such gate: `installDurableContextDelivery` holds what they offer before `session_start` in a Map keyed by item id and sends it then. Each live delivery re-offers every pending item, including those the Run started with, so `deliver` de-duplicates by id (it once sent the same report several times in one message).
- Eligibility is one SQL (`sqlite-hive-parent-wake-candidate.ts`): idle, unarchived, no Follow-up rows, latest Run `completed`/`failed` (a user Stop is not overridden), and a pending update that is newer than the latest Run, or older than a latest Run that completed and was not a wake (it missed an update committed after its `listPending`). A wake Run created after an update ends its claim, which is the loop guard. The pi-CLI-wrote-last check mirrors Heartbeats.
- Authority: the wake is not a bare `executeSessionControlMutation` as the caller id, which would skip the caller's ceiling (an ask-for-approval profile's Run on a yolo Session would wake as yolo). `resolveHiveWakeAuthority` (`session-host/hive-parent-wake-authority.ts`) runs `messageCallerBlockReason` (the Follow-up delivery check, exported from `session-follow-up-authorization.ts`) and runs in ask-for-approval when the latest Run's `runAuthorizationOverride` or its `runInitiatorCeiling` is ask-for-approval, else in the Session's mode (a yolo override is never carried: it was for that Run only). The `start` re-checks inside its transaction (`hiveWakeRefusal` in `sqlite-hive-wake-admission.ts`, code `hive_wake_not_needed`, read as `not-needed`), because the Host's first check is outside the parent's serialization: the candidate SQL again, the same latest-Run caller, the ask-for-approval narrowing still carried when that Run asked for it, and `messageCallerBlockReason` again. Delivered-means-read reads `getBranch()`, not `getEntries()`: an entry on a branch the user left is sent again. Titles (`titleSourceMessages`), the tree's User-only filter and both Markdown exports (CLI stream and export file, via `sessionExportMarkdownHeading`) skip or relabel the wake row. Each orchestration update stores its cause in `trigger_caller_id` (migration 87 `hive-wake-cause`; the submitter or help-requester, or from settlement `session-agent:<worker>:<settled run>`, or whoever stopped a Worker Run that did not complete; null for older rows, treated as the Host's). The candidate returns `triggerCallerIds` for the updates it would act on, and both `resolveHiveWakeAuthority` and the in-transaction `hiveWakeRefusal` require one to pass (`wakeCandidateMayWake` / `workerChangeMayWakeParent` in `adapters/sqlite-hive-wake-trigger-authority.ts`). Checking at request time was not enough: an update handed to the parent's final turn stays pending and the parent's own settlement wakes for it. The rule: the `profile:` callers behind the trigger, followed through Run initiators with `walkRunInitiators`, must all be behind the parent's latest Run too, so a profile (or `transient-mcp:` client) that may only contribute to or message a Worker cannot wake a desktop user's Queen, directly or through a Worker Run it started, while a profile-started Hive still wakes its Queen. Unknown fails closed; the update then waits. Deliberately, only Run initiators count for steering and answers: a profile that steers or answers a Worker Run someone else started does not make that Run's outcome its own (ADR 0044 provenance). Stopping does: `recordRunInterrupter` (`sqlite-run-interrupter.ts`, from the repository and the operation journal) stores `session_runs.interrupted_by_caller_id` when a mutation moves a Run to `stopping`, and settlement uses it as the `trigger_caller_id` of a stopped Worker Run that did not complete. Only a `completed` settlement proves a late stop changed nothing, so that result keeps its own agent as the cause. A draining Host starts no wake (`hive-parent-wake-installer.ts`, checked before the wake and again in its authority step). Its drain-deadline stop dispatches as `HOST_SHUTDOWN_CALLER_ID` (`local-user:host-shutdown`), which `recordRunInterrupter` skips, so a drain-stopped Run keeps its starter as the cause even after a restart. Known gap: the updater's **Restart now** interrupts as `gui:local-user` before the Host drains, so a wake (or a due Scheduled task) can start in that settle window and is then stopped at the drain deadline. Migration 87 (`hive-wake-cause`) adds both columns; a dev Host database from an earlier build of PR #418 recorded 87 under another name and must be reset. A nested Queen whose wake acts for a profile is that profile's too (deliberate; the profile-behind check does not special-case wakes). The in-transaction re-check applies only to the mutation that starts the wake (`startsWake = startsNewRun && startsHiveWake`): a message, steer or queue op landing while a wake is `starting` is ordinary, and a parent's answer then still clears a Worker request. A failed wake's `run-settled` event carries `hiveWake`, through `agent:run-completed`, and the renderer marks that error (`hiveWakeRunError`) so the banner offers no Retry even when the wake failed before its notice row existed. A nested Queen whose Delegation is `ready_for_review` may replace that unreviewed result during a wake Run that started after it: settlement (`settlesWithReply` in `sqlite-session-control-worker-settlement.ts`) and `delegation_submit` (`wokenAfterResult`) accept it, so a mid-tier Worker's real result is not dropped behind its first "still waiting" answer. Only a reply replaces it: a failed, interrupted or empty wake leaves the result reviewable (`settleUnsuccessfulWorker` keeps `SETTLING_STATES`). Only the wake Run's own agent (`session-agent:<worker>:<that run>`, or its requested Waggle's `waggle-of-<run>`, normalized with `durableSessionRunId`) may submit over it; settlement capture replaces only a `host-captured` latest result, never an `agent-submitted` one. The wake also skips `clearWorkerRequestOnParentDelivery`: when the woken parent is itself a Worker, its latest caller is its parent's agent, and a wake is not that parent answering its help request. Settlement agrees: `explicit_needs_attention` counts a `worker_request` from any earlier Run when the settling Run is a wake, so the wake's reply is not captured as a result. The replacement check is shared (`wakeMayReplaceResult` in `sqlite-delegation-wake-replacement.ts`): `>=` the latest submission's time plus no submission from that Run by identity (`source_run_id` or `submitted_by`), since a wake can start in the millisecond the previous result was captured. Deliberately, a wake for a CLI client profile may replace that result too: the Worker agent's Hive tool capabilities come from its own Session, not from who started the Run, so any Run that profile starts there (a plain message) could already set the Delegation `working` and submit. A subset check on the wake alone (tried in PR #418 rounds 22–23) guarded nothing and dropped replies.
- The wake is a Session Control `start` as the latest Run's `callerId` with `hiveWake: true`; the intent field is Host-only (no command schema has it), stored in `session_runs.intent_json` and dropped from Follow-up intents. The kernel then prompts with `promptPiSessionForHiveWake`: `sendCustomMessage({ customType: 'openwaggle-hive-wake' }, { triggerTurn: true })` after the orchestration update the extension delivered at `session_start`; the title is not derived from it. That entry projects as a `user_message` node with metadata `hiveWake` and `HIVE_WAKE_NOTICE_TEXT` (`hiveWakeProjection`; live through `incorporatedCustomMessageDisplay`), which `MessageBubble` renders as `HiveWakeNotice`. It must be a user-role row: `turn-fold.ts` segments turns at user rows, so without one the wake reply joined the previous turn and folded the Queen's earlier answer away. Everything else that treats a `user_message` as the user's must skip it: the `/fork` targets (Pi refuses to fork at a `custom_message`), the tree's branch prefill, the error banner's Retry, and the tree role label (`SessionTreeNode.hiveWake`, "Hive").

## The run ceiling limits Workers, never the person (ADR 0030 amendment, November 2026)

- Symptom (beta.37, 2026-11-09): messages "went nowhere". The Host refused them with `host_run_ceiling_reached` (see `session_operations.outcome_json`), because several Hives kept 16 Worker Runs active and the one ceiling counted root and Worker Runs together. The renderer restored the composer without a toast, and the follow-up path left "Thinking" and Stop over the message. Read `session_operations` first when sends bounce: refused sends create no `session_runs` row.
- Rule: `sqlite-worker-run-admission.ts`. The ceiling counts active Runs of agent-made Sessions (`AGENT_MADE_SESSION`: a `session_spawn_lineage` child, or a root in `session_agent_origins`, which `recordAgentMadeSession` writes in the lifecycle transaction for a non-person `create`/`launch`/`fork`; migration 88 backfilled it from `session_operations` and from Session agents' Launch schedule runs; both are primary-key lookups, so never scan `session_operations` in admission). Since 2026-11-10 an agent's Run in a Session the person made counts and is limited too: `isAgentWorkRun` (not `isPersonStartedRun`, not a Hive wake) is stored as `session_runs.work_by_agent` when the Run is inserted (`persistRun`, lifecycle `launch`/`spawn`; migration 89), `countActiveWorkerRuns` counts `work_by_agent = 1 OR AGENT_MADE_SESSION`, and `workerRunAdmissionRefusal` skips the ceiling in a person-made root only for a person-started Run or a Hive wake. Both limits now pause with `parent-limit` (the ceiling's pause had no reason). The person's Follow-up never stalls behind agents' capacity: `deliverPersonFollowUpPastCapacity` starts the person's first pending item of an idle `parent-limit` queue ahead of agents' (after a completed settlement and after any delivering queue change), and `applyExplicitFollowUp` starts the person's Follow-up at once into such a queue. It skips the head-only ADR 0057 authority check, so the adapters call it through `deliverAuthorizedPersonFollowUpPastCapacity` (an item whose authority changed needs attention instead). After a failed, stopped or timed-out Run, an agent's refused retry lets only the person's own retry start (`planPersonRetry`; in queue delivery, `retriesAfter` from the deferred retry), and never relabels the failure's pause: `parent-limit` would make the person's pre-failure Follow-ups start on their own. A failure, stop, Host loss or profile revocation replaces a `parent-limit` pause with its own reason. A Hive wake passes agents' Follow-ups in a `parent-limit` queue (`selectHiveParentWakeCandidate`), or agents' held items would stop a Queen acting on reports; the person's pending ones, held included, still come first. Holds and deferrals are TEMP, so Host recovery relabels an idle `parent-limit` queue that still holds the person's pending Follow-up `host-lost` (`pausePersonFollowUpsPastCapacity`): nothing would deliver it otherwise. Do not let agents' heads pass the limit for the person's sake (an in-order exception let an agent reorder its items ahead of the person's and run past the ceiling). `queue-adopt` does not lift `parent-limit` (that started the agent's head past the limit); the adopted item is the person's and starts past capacity. #437 (closed) was an alternative per-Run design; its reports found #434's renderer settlement and task provenance more complete. `replace` is unchecked by design: it keeps the Session's slot. A `spawn` is always limited, whoever asks. Every Run-starting path uses it: `newRunAdmissionRefusal` (repository, queue delivery, Hive wake), `externalRunAdmission` (explicit Waggle), Run settlement's deferral, spawn's `hostActiveRuns`, and `launchTarget` for a non-person launch. Do not add a Run-starting path that counts `session_control_states.active_run_id` directly.

## A Session wait owns its own resynchronization (issue #370, October 2026)

With about 25 Hive Sessions streaming, the `hive` tool's `wait` returned `resync_required`
(`slow-consumer`) at once on three 30-minute waits in a row. `wait` and `exports-wait` hold a
filtered `SessionHostEventHub` subscription (256 events, 4 MiB each, 32 MiB across every
subscriber) and re-read status after each target event; events arriving during that read queue
up, and a burst, a large `toolcall_delta`, or a hub whose aggregate budget other slow subscribers
hold drops the subscription. The wait then handed the drop to an agent that has no cursor.
`waitForSessionHostCondition` (`application/session-host-condition-wait.ts`) now owns it: on an
unreplayable start cursor or a drop it subscribes again at the current cursor, then re-reads the
canonical state (subscribe first, read second, so nothing between is missed), and keeps the same
deadline. A delivered event discards the rest of the queue (`discardPending`), since they only ask
for the same read. Back-to-back resyncs back off from 50 ms doubling to 1 s: without it a drop on
every read is a microtask loop that starved the event loop (a 400 ms wait did 10,463 reads and an
abort could not land). The events stay wake-ups only: every answer comes from the read, which
re-resolves the caller's live authority, so a revoked caller still fails closed after a resync.
`resolveLocalSessionCommandCursor` drops a caller's unresolvable `after` (`hive wait
--after-host/--after-sequence`) instead of answering `resync_required`; `after` never changed what
a wait answers, only what woke it. `resync_required` stays in the shared error union for export
continuation, `hive watch` and `exports-watch`, which do hand cursors to their callers.
`session-wait-service-resync.unit.test.ts` forces each drop by lowering hub capacities.

## Filed under "Renderer And Session Memory"

- Hive cleanup archives a Worker only when its Delegation is `accepted`/`cancelled`, it is idle (no active Run, Follow-up, pending authorization, in-memory writer, or parked interaction), its own Delegations are terminal, and no user ever touched it. "User" means any non-`session-agent:` caller: the append-only `session_operations` journal under the Worker id *and* under `delegation:<contract>:actor:*` (a CLI accept/revision/reopen is a review), plus the agent-authored `spawn` row. Pins and branch edits are `local-ui-v1`, not journaled, and skip command serialization: a pin protects only while it exists, and the final archive re-derives the whole predicate plus `liveSessionAuthorityBlockReason` for the spawning caller inside its own write transaction (the Host's single SQLite connection serializes it against the pin). Unjournaled desktop state also counts as user activity and keeps the Worker: any terminal record for the owner (or a truncated snapshot), a registered browser-preview owner (the Session is open in the GUI) or live previews, and running `service` actions when the Worker is its Workspace's last active binding. Terminal/browser checks run inside the archive's desktop mutation fence via the `admit` hook of `withSessionDesktopRemoval`; the service check runs inside the Workspace action mutation. The broker answers `getActivitySnapshot`/`browser inspectOwner` offline only with native-free proof. Triggers: agent-caller delegation accept/cancel (a pass for the Delegation's parent, which also reaches a nested parent Worker), any Run settling with nothing scheduled, and the background layer's backoff re-check of a Worker kept for desktop state (issue #352). The archive key is `hive-cleanup:<delegation>:<updated_at>`, so a parent-agent unarchive replays instead of re-archiving. Any caller's (user or agent) accepted `message`/`start`/`follow-up`/`replace`/`steer` to a Worker whose latest archive-state operation is a cleanup archive unarchives it inside that command's serialization, attributed to the caller (`hive-restore:<key>`); a `delegation-reopen`/`delegation-request-revision` that lands in `revision_requested` does the same for the Worker, taking the Worker's serialization inside the parent's (parent before Worker; lineage is a tree). Explicit archives are left alone. An agent-restored Worker stays visible until a new terminal transition, because the old cleanup key replays. `HiveWorkerCleanup` is looked up with `Effect.serviceOption`; a runtime without `HiveWorkerCleanupServicesLive` silently disables cleanup and restore.
- A Session agent archiving its own Session (`session-agent:<S>:<run>` caller, target `S`, that Run still live) must not go through `withSessionDesktopRemoval` inline: it cancels the Session's Runs and waits up to 30 s for them, but Pi cannot end the Run while that tool call waits, so the archive timed out, and the gateway's outer interruptible fiber reported the timeout as "Session command was cancelled." with the Run aborted and nothing archived.
  - `organizeSession` answers `session-archive-deferred` (with the Run id). `session-self-archive.ts` forks a daemon holding `operation` Host liveness (admitted while draining) that waits for that Run's writer and registry entries to release (`waitForSessionRunEnd`), then re-reads `readSelfArchiveState` under the Session's command serialization.
  - It archives only if the request is still pending (a non-replayed `unarchive` withdraws it, `withdrawSelfArchives`; each request holds a token, so after unarchive and a new ask only the newer daemon archives), the Session is unarchived and not pinned (as **Archive finished runs** skips pins), has no in-memory work (`hasAnyActiveRun`), no active Run, no Run recorded after the asking one (by `rowid`; a fast Follow-up Run can already have ended), no queued Follow-up, no pending Worker update for it as a parent and no Delegation of it still `working`/`waiting`/`revision_requested`, or open with its Worker's Run, Follow-up or wake (a pending update for it) still to come (a wake skips archived Sessions, so a later report would go unread), and the asking Run has a `session_runs` row that `completed`. The checks run before the desktop teardown, not in the archive's write transaction, so a pin or Worker update that lands during teardown is not seen; any archive has that window. Waiting for Run end alone is wrong: the coordinator releases the Run at the hand-off to a scheduled Follow-up, so an unconditional archive killed it or hit the removal fence mid-hand-off.
  - A Worker that archives itself records an explicit agent archive, which a parent Follow-up does not auto-restore as it does a Hive cleanup archive. Hive cleanup keeps a Worker while `hasPendingSelfArchive`, and the daemon requests cleanup again when it skips, so cleanup cannot win the race and downgrade it.
  - The intent is in memory only: a Host restart before the Run ends drops it. The outcome never crosses the Local Session wire (only in-Host `session-agent:` callers get it, and it is not journaled), so it needed no protocol revision; a path that delivers it to an external client would. A CLI/MCP self-archive is not a `session-agent:` caller and still stops the Run inline.
  - `session-self-archive.integration.test.ts` drives it through a Run whose executor waits for the tool call like Pi does; `session-self-archive-liveness.unit.test.ts` covers the drain and liveness hold.
