# Release and CI

CI and releases: the per-PR gates after ADR 0033, the commit policy, native platform floor,
macOS signing and DMG trust, release publication and update metadata, release branches,
package releases, and runner quirks.
Load when touching `.github/workflows/`, `scripts/*release*`, signing or updater code.
Load `.agents/skills/release/SKILL.md` as well for release work.

## Merge queue removed (ADR 0033, September 2026, refines ADR 0029)

Releasing a feature felt slow mainly because the merge queue re-ran the Full gate (Windows + Linux Electron E2E + path-scoped rehearsals) on the speculative merge result (~15–25 min), on top of the PR run and the `push: main` run — and Windows E2E is the flakiest gate (~33% teardown-timeout rate). Decision: drop the `merge_queue` rule from the `main` ruleset so PRs merge directly once the required per-PR checks pass; leave all workflow code and release guards unchanged. A full t3code-style rewrite (lean 3-job CI + tag/nightly release) was scoped and rejected as-is: it is incompatible with OpenWaggle's deliberately security-hardened, test-pinned release machinery — `ci.yml`'s fail-closed supply-chain contract (`package-release-validator-*.ts` inside `bun run check`) requires the classify/prepare/candidate/gate jobs + SLSA provenance attestation that `package-release.yml` consumes, and `release.yml`'s human-approved app-release flow is enforced by `app-release-workflow.unit.test.ts` (never pushes to main, never auto-merges, publishes only a verified human-merged commit). Gutting either to fit a leaner shape removes real security for velocity; right-sizing the package-release apparatus (heavy for a v0.1 alpha with no external consumers) is a legitimate separate change deferred to its own decision. Consequence of removal: main can briefly go red from a semantic conflict between two green PRs. Follow-ups in the same PR: the Release Please version-bump PR (no source changes) now skips the app suite (unit/integration/component/MCP) via an identity-scoped job condition (`!(pull_request && head_ref == 'release-please--branches--main' && head.repo.full_name == github.repository)`, so a fork PR cannot name its way into a skip), accepted by a new fail-closed gate tier `release-pr` that still requires commit policy + `check` + the package candidate (so `prepare-package-release` still attests tarballs). Adding that skip required registering the three test jobs in `QUEUE_ONLY_JOB_CONDITIONS`, decoupling the blocking-job-contract `+if` allowance from the special-runner check in `release-ci-policy.ts`, setting the exact-release-branch `==` guard count to 6, and regenerating `CI_WORKFLOW_AST_CONTRACT` — the normal process for an intentional ci.yml change. Provenance attestation and human-approved releases stay intact. Also in the same PR: the entire Electron E2E suite (`e2e/`, `playwright.config.ts`, the three `electron-e2e-*` jobs) is removed — evidence from `pingdotgg/t3code` is that a shipping multi-platform Electron product runs CI on vitest unit+integration only and has no E2E (its `playwright-core` is an in-app browser-preview feature, not tests). OpenWaggle's 3-OS E2E was the dominant flake (Windows ~33% teardown-timeout). Per-PR gating is now commit-policy + static + unit + integration/component + MCP; the fail-closed gate/policy/AST-hash/tests were updated to drop the E2E jobs (kept the Playwright deps: `playwright-core` powers browser preview, `@playwright/test` powers package browser smoke + website screenshots + QA). A coverage audit (`docs/agents/e2e-removal-coverage-map.md`) found the E2E suite was almost entirely belt-and-suspenders over existing unit/integration/component coverage, so no functional behavior leaves the gate; the nightly cross-OS packaged canary (`.github/workflows/nightly.yml`) covers packaged build + native runtime load + the macOS syntax budget, while renderer boot/CSP/visual/timing have no automated CI control (local/manual only). `e2e/support/session-fixtures.ts` (used by QA seeding + website screenshots) was relocated to `scripts/support/` with an eslint override, since lint never covered `e2e/`.

## The commit policy was invisible to agents

Manual CI has no pull-request base SHA. Resolve its exact candidate's merge base
with the fetched `origin/main` before invoking Commit Policy, and fail on missing
or ambiguous ancestry. Queue runs use their event `merge_group.base_sha`. An empty
`--from` falls back to bootstrap history and loses
the ancestry needed to recognize already-released upstream package syncs.

`scripts/check-conventional-commits.ts` rejected a `mockup:` subject in CI after the agent pushed — the check was deterministic, ~1s, and documented nowhere agents read. Now `bun run verify` (commit policy vs the `origin/main` merge base + typecheck + lint + unit tests) runs in the husky pre-push hook for feature branches; `prepush:main` still guards pushes to `main`.

## Filed under "CI is tiered behind a merge queue (ADR 0029, September 2026 — superseded by ADR 0033; see "Merge queue removed" below. Retained for history.)"

Adding a reusable CI job requires a deliberate update to the stable job-name list,
caller AST contract, and exact local-workflow reference allowlist. Validate the callee's
AST through the production file validator too, including its immutable SHA preflight,
checkout, permissions, and required commands. Do not exempt reusable jobs generically
or accept their success without the selected gate dependency and result check.

## Filed under "Electron Runtime Memory"

- macOS `electron-updater` requires ZIP artifacts in GitHub release metadata; DMG-only mac releases can advertise an update but fail with "ZIP file not provided".
- Squirrel.Mac counts every process with the app's bundle id *and* bundle path as a running instance (`NSRunningApplication`, accessory/`UIElement` included): the detached Session Host and any `openwaggle` CLI process (`mcp serve`, `hive wait`) from `/Applications/OpenWaggle.app` block an install. ShipIt waits for the instances it sees at start, then re-checks after verifying the update and aborts with `SQRLInstallerErrorDomain -9 "App Still Running"` if any is there, which is exactly what reopening the old version during the install window does. Evidence lives in `~/Library/Caches/com.openwaggle.app.ShipIt/ShipIt_stderr.log` (local time) and `ShipItState.plist` (JSON despite its name; it survives a successful install). Every install path (Restart to update, `openwaggle update`, `install.sh`) therefore stops the Host first with a `purpose: 'update'` stop (ADR 0047). `install.sh` must run the installed CLI with `</dev/null` (under `curl … | bash` stdin is the rest of the script), so `host stop --update` asks on `/dev/tty` through `tty.ReadStream`; a plain `fs.createReadStream('/dev/tty')` keeps a pending threadpool read that can stop the process exiting. To check counting without a GUI, start an isolated Host from the installed bundle (`OPENWAGGLE_USER_DATA_DIR=<tmp> /Applications/OpenWaggle.app/Contents/MacOS/OpenWaggle hive list`, with `OPENWAGGLE_AGENT_RUN` unset) and enumerate `NSRunningApplication.runningApplicationsWithBundleIdentifier('com.openwaggle.app')` through `osascript -l JavaScript`.
- CI runs no Electron E2E (ADR 0033 removed the suite); every per-PR job runs on Ubuntu. The non-gating nightly canary (`.github/workflows/nightly.yml`) packages and smokes the app on macOS, Linux, and Windows. Linux Electron launches under Xvfb still need both `DISPLAY` and `XAUTHORITY` in the safe Electron child environment.
- **The Windows NSIS script is only compiled when electron-builder packages Windows, which happens in the release workflow, not CI.** An installer-variant StrFunc call inside `customUnInstall` broke two consecutive releases across six days before anyone noticed, because NSIS only rejects it at compile time. `build/installer.nsh` is now compile-checked by `bun run check:installer` inside `bun run check`, so it fails a pull request in seconds instead of a release in minutes. Two NSIS rules worth remembering: StrFunc helpers must be declared before use, and an uninstall section can only Call `un.`-prefixed functions, so `customUnInstall` needs the `Un` variants (`${UnStrRep}`, not `${StrRep}`).
- A GitHub release is listed as soon as it is published, about 24 s before its assets finish uploading, so the newest eligible tag can lack `<feed>-mac.yml`/`<feed>-linux.yml`/`<feed>.yml` and an update check pointed at it gets HTTP 404. `newestEligibleRelease` (`src/main/update-feed.ts`) only counts a release that already has the exact file electron-updater will request (`updaterMetadataAssetName` mirrors `Provider.getCustomChannelName`: `-mac`, `-linux` plus `-<arch>` except x64, nothing on Windows) and returns `{ type: 'no-release' }` instead of throwing when none qualifies, which is also Stable before `1.0.0`. `updater.ts` turns that into `not-available` and `update-cli.ts` into "up to date … no release is available on it yet", exit 0; never an error. `openwaggle update --check` is read-only (with `--channel` it skips the Host's `set-channel`), and `--version` refuses a tag older than `app.getVersion()` with exit 2 before any network call. `install.sh` defaults to Beta, not Alpha, without a Stable release, and quits only the Foreground app whose `LSBundlePath` equals the bundle it replaces (both paths are compared physically with `pwd -P`, so a symlinked directory such as `/var` → `/private/var` still matches); every installed copy shares one Session Host, so another open copy makes `host stop --update` report `desktop-open` and the installer asks to quit it.
- GitHub's release-asset storage (`release-assets.githubusercontent.com`) sometimes returns a transient HTTP 500 for a healthy, fully uploaded asset. `curl -f` without `--retry` aborts `scripts/install.sh`, and with it `openwaggle update`, on the first such response. Every network `curl` in the installer goes through `curl_with_retry`, which retries timeouts, 408, 429 and 5xx with exponential backoff and still fails on the first 404. `quick-installer-download-retry.unit.test.ts` runs real curl against a local server that fails once.

## Filed under "Tooling Memory"

- Native platform floor (ADR 0040 amendment 2026-10-25): native modules link against the build host's glibc and libstdc++, so a runner upgrade silently raises the Linux minimum. `1.0.0-beta.25`, built on `ubuntu-latest` (24.04), shipped a `node-pty` needing `GLIBC_2.38`/`GLIBCXX_3.4.31`, which broke the terminal and Project Actions on Ubuntu 22.04 and Debian 12 while the app still launched. The Linux release and nightly builds run on `ubuntu-22.04`, and `scripts/check-native-platform-floor.ts` parses every ELF/Mach-O/PE in the packaged app (thresholds in `scripts/supported-platform-floor.ts`) after each build and before upload. On macOS, onnxruntime needs 13.4 while Electron needs 12.0; `LSMinimumSystemVersion` stays 12.0 on purpose so auto-updated macOS 12 installs keep launching. The guard also caught orphan `recheck-*` optional dependencies (no importer since #144) whose macOS binary needs 14.0; they were removed. electron-builder copies a top-level `files` set separately from a platform block's own `files`, so exclusions in `mac.files` never apply to the top-level list (an exclusion-only platform list even adds `**/*` and packs the whole repository). The foreign-prebuild exclusions therefore sit in the top-level list and use the `${platform}` (host) and `${arch}` macros (`scripts/electron-builder-native-prebuilds.ts`). Moving the whole list into each platform block instead drops Pi's forced-in docs. The macOS release runner is arm64, and the package manager installs optional native packages for the host CPU only, so through `1.0.0-beta.25` the Intel app shipped only the arm64 builds of sharp, `@napi-rs/keyring` and `@mariozechner/clipboard` (image processing, Chromium cookie import and clipboard broke on Intel Macs). pnpm's `supportedArchitectures` (os current, cpu current+arm64+x64, libc current) in `pnpm-workspace.yaml` installed both; under Bun, `bun install --cpu=arm64 --cpu=x64` (`.github/actions/bun-install`, `release.yml`) does, and the `!node_modules/{,**/node_modules/}{*,@*/*}-${platform}-!(${arch}|${arch}-*)` exclusion (package directories only, top-level or nested) keeps only the packed arch. The guard now fails on any binary for another platform or architecture instead of skipping it, and `scripts/packaged-native-dependencies.ts` reads every package.json in `app.asar` and fails when a declared `<platform>-<arch>[-gnu|-msvc]` optional dependency for the pack is missing. That catches a build that is absent rather than present for the wrong arch. Verified by loading the x64 `.node` files under Rosetta in the packaged x64 Electron (`ELECTRON_RUN_AS_NODE=1 arch -x86_64 …/MacOS/OpenWaggle -e 'require(…)'`).
- Retired runner images fail silently (November 2026): GitHub retired `macos-14`, and a job pinned to it is cancelled within a second with only a run annotation (`The configuration 'macos-14-arm64-us-default' is not supported`), no step logs. `build-macos` never ran, so `Verify release installers` and `Create GitHub Release` were skipped and `v1.0.0-beta.33` through `beta.35` were tagged but never published; users stayed on beta.32. The release macOS build now runs on `macos-15`, guarded by `app-release-native-floor-workflow.unit.test.ts`. Re-running an old release run reuses that commit's workflow file, so recovery needs a new release from the fixed `main`. When a release tag has no GitHub Release, check the cancelled job's annotations first (`gh run view <id>`).
- macOS release signing (ADR 0040, `scripts/mac-signing.ts`): never throw from `electron-builder.ts` — `postinstall` runs `electron-builder install-app-deps`, which loads the config, and the nightly canary builds `stable` without secrets; the RC/Stable signing requirement lives in a `release.yml` step instead. electron-builder before 26.16.1 cannot sign through `CSC_LINK` because `set-key-partition-list` receives the `.p12` password instead of the temporary keychain password (upstream #10066/#10172). 26.17.0 also switched macOS zips back from native `zip` to 7za with `-snl`: zips are about 2% smaller and framework symlinks survive, but each zip takes about 40 s longer. A local `CSC_LINK` build leaves `~/Library/Caches/electron-builder/electron-builder-root-certs.keychain` in the user keychain search list; restore it with `security list-keychains -d user -s ~/Library/Keychains/login.keychain-db`. On the maintainer Mac, Gatekeeper assessment is disabled (`spctl` reports `override=security disabled`), so local `spctl` passes prove nothing; notarization is proven only by `stapler validate`. The Developer ID key, CSR, and `finish.sh` that turns a `.cer` into the release secrets live in `~/.openwaggle-signing/`, outside the repository.
- DMG trust (2026-10-25), **proven only by the next signed release run** (no signing secrets outside the release workflow; the nightly canary builds unsigned): electron-builder's `dmg.sign` only codesigns the DMG, and it notarizes only the `.app`, so `1.0.0-beta.25` shipped DMGs that were neither signed nor notarized. `patches/dmg-builder@26.17.0.patch` makes `signDmg` report whether it signed and then calls `packager.helper.notarizeIfProvided(dmg)` (the pkg target's path; `@electron/notarize` submits a `.dmg` directly and staples it) before `createBlockmap`, because stapling changes the bytes that the `.blockmap` and the `*-mac.yml` DMG entry record. Notarizing afterwards in the workflow would leave both stale. Its notarytool failures carry the same `Failed to notarize via notarytool` text, so `scripts/macos-build-failure.ts` still retries only transport errors.
- Release publication (2026-10-25): softprops/action-gh-release creates a prerelease already published and uploads afterwards (it drafts first only for non-prereleases), so update checks during the upload got a 404 for `beta-mac.yml`. The release job uploads with `draft: true`, runs `scripts/verify-release-assets.ts` (exact names, sizes, `uploaded` state, byte-identical `*.yml` and `SHA256SUMS.txt`; it lists releases because `releases/tags/<tag>` hides drafts), publishes with `gh release edit --draft=false --latest=<stable only>`, and verifies again. softprops v3 keeps an existing release's draft state when updating it, but a rerun that finds the release published skips the upload entirely so it never deletes and re-uploads live assets.
- Differential updates: GitHub release asset downloads answer single `Range` requests with 206 but multi-range requests with HTTP 501. electron-updater's `generic` provider enables multi-range for every URL except `s3.amazonaws.com`, so `src/main/update-feed.ts` must pass `useMultipleRangeRequest: false` or every differential download silently falls back to a full one. Before ADR 0040 the release workflow published no `.blockmap` files at all. To measure a plan offline, run `computeOperations` from `electron-updater/out/differentialDownloader/downloadPlanBuilder` on two gunzipped blockmaps.
- Release branch synchronization must use fetched Git ancestry, not only GitHub's `mergeStateStatus == BEHIND`: `UNKNOWN` or `BLOCKED` can conceal a stale branch immediately after a main push. Validate a stale candidate's version-only change against its unique merge base before syncing, then validate against pinned current main and recheck ancestry after CI. Otherwise legitimate main manifest changes fail the release guard before synchronization.
- GitHub can return a generic GraphQL error from `gh pr create` after a release branch has already been pushed. Release preparation must retry the mutation and re-query the exact same-repository release branch after every failure so it can adopt an ambiguously created PR instead of stranding the release or creating conflicting state.
- RC and Stable release path (2026-11-09, before `1.0.0-rc.1`): the promotion guard's base is the newest RC tag with a published (non-draft) GitHub release, read by `gh api --paginate .../releases --jq '.[] | {tag_name, draft}'` in the version job and passed to `app-release-state.ts verify-promotion --releases`; the decisions are pure functions in `scripts/app-release-promotion.ts` (`promotionBase`, `promotionGuardViolations`). An unreadable or empty list fails closed, and so does a minor or patch that has rc tags but no published RC (otherwise a failed RC train would silently drop its freeze). A tag alone proves nothing, because the tag push precedes the builds. The RC/Stable macOS signing secret check also runs in the version job before any release PR or tag, since a failure in `build-macos` strands a tag. `THIRD_PARTY_NOTICES.md` is app content for the guard (electron-builder `extraResources`); a unit test reads the imported electron-builder config and fails if any `extraResources` source or positive app.asar `files` pattern becomes an ignored path (positive `files` patterns must start with a literal path, because the guard matches prefixes). `runReleaseTrain` in `scripts/__tests__/app-release-train.test-harness.ts` (sharing the `gh` mock in `app-release-sync.test-harness.ts`) runs the version job's bump and release steps for rc/Stable fixtures with a mocked `gh`. The bump step uses bash regexes because GNU sed alternation (`\|`) fails on macOS sed.
- Releases publish a `.blockmap` beside each installer, and its name extends the installer's (`…-arm64.dmg.blockmap`). `scripts/install.sh` looked up the checksum with `grep "$FILENAME"`, got two hashes, and failed every 1.0.0-beta install with a "Checksum mismatch" that printed the correct hash. Its asset regex was also unanchored. Any lookup by artifact name must match the whole name. The installer bundled in an app (`openwaggle update`) carries the bug until the next release ships the fix.
- The first signed release (`1.0.0-beta.1`, run 36695614844) failed because the GitHub macOS runner lost its network while notarytool polled Apple (`HTTPError(statusCode: nil)` / `NSURLErrorDomain -1009`, after the upload and after x64 had notarized). It was not a signing or credentials problem. The release workflow rebuilds macOS for the runner failures that `scripts/macos-build-failure.ts` classifies as transient. Rerunning the failed jobs of a release run is safe, because the version job (which has already pushed the tag, idempotently) is reused and nothing is published until `Create GitHub Release`.
- `1.0.0-beta.36` (run 42493633669) notarized the app, then `xcrun stapler` lost its connection to api.apple-cloudkit.com while fetching the ticket (`NSURLErrorDomain Code=-1005`, `The staple and validate action failed! Error 68.`, `Failed to staple your application with code: 68`). `scripts/macos-build-failure.ts` only knew notarytool and hdiutil failures, so the job failed on attempt 1; it now retries a staple report whose own output has an NSURLErrorDomain transport error. The classifier also used to accept a notarytool rejection whenever *any* NSURLErrorDomain error appeared anywhere in the log; each failure report (marker to its `failedTask=` trailer) is now judged on its own output, and every report of a kind must be transient.
- `1.0.0-beta.8` (run 37285929256) also failed on the runner, on all three attempts. Both apps notarized, then dmgbuild failed with `hdiutil: create failed - Device not configured` (once `attach failed`). hdiutil is a known flake on hosted macOS runners under concurrent disk I/O (actions/runner-images#7522). `patches/dmg-builder@26.17.0.patch` now retries only the failed `dmgbuild` call, with its wait outside electron-builder's toolset lock so the other arch's DMG is not starved. The whole-build retry (three attempts, Spotlight off, XProtect stopped) is the backstop. Its classifier only accepts an hdiutil error inside the failing dmgbuild report, so recovered warnings do not trigger rebuilds. A rerun of a release run uses the workflow at the release commit, so a workflow fix only applies from the next release.
- To verify the dmgbuild retry locally, point `CUSTOM_DMGBUILD_PATH` at a shim that fails once with the hdiutil message and then execs the cached real `dmgbuild` (`~/Library/Caches/electron-builder/dmg-builder@*/dmgbuild-bundle-*/dmgbuild`). `scripts/__tests__/macos-build-failure.integration.test.ts` covers the patched helper with a shim and a private toolset lock.
- `scripts/package-release-validator.ts` pins `release-please` to an exact version for deterministic preflight contracts; a dependency sweep must not bump it (the unit test catches it).

## Filed under "Website documentation routing"

`prs_created` from release-please-action counts only PRs it created or updated, and release-please updates an open release PR only when its body changes. A rerun on the same UTC day with no new package release notes leaves the PR unchanged, skips the docs sync, and goes green. With `skip-github-release: true` the action never runs `createReleases`, so nothing moved merged release PRs from `autorelease: pending` to `autorelease: tagged`, and `createPullRequests` aborts while any of the 200 most recently updated merged PRs still has the pending label (run 40071078024, #136). The `mark-release-tagged` job in `package-release.yml` relabels the release PR after promotion; #136 needs a one-time manual relabel.

Package release 0.2 (Nov 2026) failed three ways that each look like a bad gate but are timing. (1) Right after the docs sync pushes its commit, `GET /pulls/<n>` can still return the previous `head.sha` (run 42181943380 read 85b6571 milliseconds after pushing cb5d539), so the job dispatched CI for a SHA the branch no longer pointed at, every dispatched job failed `Verify dispatched commit identity`, and the poll for a dispatched run with that SHA ran out. The sync step now records `git rev-parse HEAD` as `steps.docs.outputs.head_sha` and the validate step waits for the PR API to report exactly that SHA. (2) npm served each freshly published 0.2.0 version about 90 seconds after `npm publish` returned, and promotion gave up after about 60 seconds (runs 42190394047 attempts 1 and 2). A retried publish cannot succeed, so the acceptance window is now ten minutes (`ACCEPTANCE_ATTEMPTS` x `ACCEPTANCE_POLL_DELAY_MS`), and promote prints the publish output plus each "not served yet" poll. Rerunning the failed promote job resumes: versions already on npm with matching integrity are skipped. (3) The sync step's install (`pnpm install` then) ran `prepare: husky`, so its `git push` ran the full pre-push `bun run verify` (ten minutes of unit tests inside a release job); the step sets `HUSKY: "0"`. Separately, Electron 43 downloads its binary lazily with no retry on the first `require('electron')` (one GitHub 504 failed Typecheck & Lint on main, run 42042685038), so the CI jobs that need it pass `electron-binary: 'true'` to `.github/actions/bun-install`, and the apt steps tolerate a failing third-party source (packages.microsoft.com 403, run 41931267177) and then prove the tool installed (`makensis -VERSION`, `/bin/zsh --version`).

Two red checks from that investigation needed no code change. A CI run on the Release Please branch that shows `failure` with zero jobs and "likely failed because of a workflow file issue" (run 42182130445) was a bot-triggered `pull_request` run left in `action_required`: nobody approved it, and GitHub marked it failed when the PR merged. Package Release validates the release PR through its own `workflow_dispatch` run, so ignore that run. The Cloudflare Pages check can fail in 0 seconds with "Deploy failed" before any build starts (PR #413, head 0d58bf1); the same tree deployed fine from an empty commit. GitHub's check-run rerequest API answers 404 for the Cloudflare app, and its logs need a logged-in dashboard or `CLOUDFLARE_API_TOKEN`, so push an empty commit to retry it.

## Filed under "Usage statistics notice"

A long `bun run verify` pre-push (about 5 minutes) can outlast GitHub's idle SSH connection: the hook passes and `git push` then exits 141 without pushing. Push with `GIT_SSH_COMMAND="ssh -o ServerAliveInterval=20 -o ServerAliveCountMax=60"`, then confirm with `git ls-remote`.

## Bun trusts its package cache; shipping jobs install without it (November 2026)

Bun does not check files in `~/.bun/install/cache` against the integrity hashes in `bun.lock`: a file edited in the cache installs with no error under `bun install --frozen-lockfile`. A restored `actions/cache` entry is therefore code the job runs. Every job that signs, notarizes, attests or publishes installs from the registry: `release.yml` restores no cache, and `prepare-package-release` (ci.yml) and `release-please` (package-release.yml) pass `package-cache: "false"` to `.github/actions/bun-install`, which `package-release:validate` requires. Jobs whose output ships nowhere keep the cache.

## Cloudflare Pages builds the website with Bun (November 2026)

The website's Cloudflare Pages project is configured in the Cloudflare dashboard, not in this repository. After the move to Bun (ADR 0064), its build command must be `bun run build:website` (the root script runs `cd website && bun install && bun run build`), and the project must set the `BUN_VERSION` environment variable to the version in `.bun-version` so the Pages build image installs the same Bun as CI. A build command or package manager left over from pnpm fails the Pages deploy even when every GitHub check is green, and no code change fixes it. Update `BUN_VERSION` in the dashboard whenever `.bun-version` changes.

## Electron to Electrobun transition (docs/electrobun-transition.md)

A CI bench on all three OSes showed what electron-updater checks. It needs the file sha512, the size and the name pattern in the channel YAML, and it skips the blockmap when it gets a 404. It does not check the signature on unsigned bench builds. On macOS, Squirrel.Mac requires the same bundle id and a signature that satisfies the running app's designated requirement. It relaunches `Contents/Frameworks/Squirrel.framework/Resources/ShipIt` from the new bundle and names the bundle after `CFBundleExecutable`, so `macos-transition-bundle.ts` renames `launcher` and adds a relaunch shim. Zip the inner `.app`, because Electrobun's build output is a self-extracting wrapper. On Windows, Electrobun's Setup waits on an "Installation complete" dialog and treats any argument as a manager command. The NSIS wrapper therefore polls for the launcher and the `<id>.<channel>` uninstall key, then kills Setup. Keychain: a `bun` signed with the app's Team ID and identifier `com.openwaggle.app` reads "openwaggle Safe Storage" without a prompt. Stock Bun, or Bun signed with the identifier `bun`, triggers a prompt.

### Electrobun packaging (scripts/electrobun/, November 2026)

- Hutch (0.29, Electrobun 2.0.6) writes the final `Contents/Resources/version.json` (content hash, baseUrl, name) after `postBuild` and before it packs the `.tar.zst`; no hook sits between. An app signed in `postBuild` therefore ships a broken seal in the update archive (`codesign --verify`: "a sealed resource is missing or invalid"). `macos-reseal.ts` copies the final `version.json` into the kept app, re-seals only the outer bundle, notarizes, repacks (ustar, `--no-mac-metadata`, `COPYFILE_DISABLE=1`, zstd) and rewrites `tarSha256`/`tarSize` in `update-v2.json`. Hutch's content hash is deterministic for identical content, so it stays valid. Hutch's macOS patch no longer matches and is dropped.
- After `postWrap` the build folder holds only Hutch's self-extracting wrapper (`launcher` + `<hash>.tar.zst`). Keep the unwrapped app in `postBuild` (`out/electrobun/inner/`); the DMG and the transition zip ship it, not the wrapper.
- An unsealed bundle (Electrobun's linker-signed executable only) fails `codesign --verify`, so the transition zip cannot be built. Builds without an identity are signed ad hoc inside out.
- Electrobun 2.0.6 CEF remote debugging: on only in `dev` builds (scans from 9222) or for an explicit `chromiumFlags['remote-debugging-port']` of 1-65535 (no scan). Port `0` is "invalid configuration", so debugging stays off. `ELECTROBUN_CEF_REMOTE_DEBUGGING_PORT` is read by the native process at CEF init, which races the main Worker, so the main bundle cannot set it.
- A codesign identity that is not trusted (`CSSMERR_TP_NOT_TRUSTED`) is "no identity found". A CI throwaway identity must be trusted in the System keychain with sudo (`scripts/electrobun/ci/macos-throwaway-identity.sh`), which cannot be done locally without a prompt. On Windows, import a self-signed certificate into `LocalMachine\Root`; `CurrentUser\Root` shows a confirmation dialog.
- Electrobun's updater accepts HTTP only on localhost, so CI feeds are loopback (`scripts/electrobun/ci/smoke.ts serve`).
- The pre-push `verify` runs about 20 minutes on a loaded machine. An SSH push idles through it and the remote closes the connection. Push throwaway branches over HTTPS with `gh auth git-credential`.
