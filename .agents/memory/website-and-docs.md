## Website documentation routing

The user guide starts at `/docs/getting-started/first-run` with the label **Get started**; `/docs` redirects there. `website/src/data/docs-nav.ts` separates user navigation from developer/package references without moving existing content URLs. Page frontmatter still supplies section/order to the installed-docs generator, independently of the website sidebar.

Unversioned package documentation URLs navigate immediately to their current versioned pages. Static Astro `302` redirects generate a two-second meta-refresh delay; use `PackageAliasRedirect.astro` for zero-delay navigation with a canonical URL and fallback link. Preserve the query and fragment with synchronous `location.replace`; meta refresh drops fragments. Keep a zero-delay `noscript` fallback for browsers without JavaScript. Rendering a versioned guide at its unversioned alias breaks relative links such as `./api-reference` and `./components`; keep the redirect when changing package versions. Verify built-page links, including fragment IDs, after navigation or heading changes.

Before a broad documentation refresh, fetch the agreed source branch and record its commit. Trace each workflow to current UI labels and runtime behavior rather than treating old docs as authority. If the maintainer cites an unmerged implementation, record that separate source revision and do not claim it already ships on main. Model storage in the global app database can still be keyed by project; storage location and selection scope are different.

Published package API pages can intentionally lag unreleased source when `website/src/content/package-docs-next/<package>/` exists. `package-docs:check` preserves that release boundary; `api:snapshot:check` checks current exports. Correct authored prose and regenerate package READMEs with `package-docs:update`, but do not hand-backport unreleased symbols into frozen API inventories.

Every package whose next release opens a new major.minor line needs pending docs in `package-docs-next/<package>/` before that release PR exists. Release Please's sync step promotes them after merge and fails without them (run 42080386211: waggle-core reached 0.2.0 only through `feat(platform)` #144). `scripts/package-release-lines.ts`, run by `check-conventional-commits.ts` in the Commit Policy job (`fetch-depth: 0`, so tags are there) and by `bun run verify`, predicts each package's next version with the pinned release-please runtime itself (`parseConventionalCommits`, `DefaultVersioningStrategy`, and `DefaultChangelogNotes` for the "no user-facing commits" skip), not a regex: release-please splits body paragraphs that start with `type: ` into their own commits and counts `feature` and `BREAKING-CHANGE` anywhere. Per-package config overrides top-level (`scripts/package-release-rules.ts`), `release-as` applies, and an unsupported `versioning`, `release-type`, `changelog-type` or `exclude-paths` fails closed even locally. The released version is the manifest's (release-please's own rule). Tags exist only after promotion publishes to npm, so while the manifest is ahead of the newest tag the range starts at the commit that recorded the manifest version. It counts the commits since then that touch `packages/<pkg>/`, plus the PR title when the PR touches the package, and fails when the next line has neither pending nor published docs; a missing tag or shallow clone fails in CI and only warns locally. Promotion copies pending pages byte for byte, so `docs-frontmatter.unit.test.ts` and `docs-style.unit.test.ts` check them as `packages/<pkg>/next/<page>` against the content schema (`kind` is required) and the style rules. Tests must derive the current line from the package version, not hard-code `0.1`.

The docs site has no extension host, and the 0.2 extension-react stylesheet has no fallback values, so the catalogue pages need the theme projection that `website/src/styles/extension-theme.css` supplies (the SDK's `extensionThemeCssVariableDeclarations()`, checked by `extension-theme-css.unit.test.ts`). Before it, the published 0.1 catalogue rendered unstyled. The 0.2 stylesheet styles components only beneath `.ow-extension-root`, so markup that puts `ow-extension-panel` on the root itself needs the shim rules in the same file.

## Website diagrams and image zoom

Docs ```mermaid blocks render to inline SVG at build time (`website/src/lib/markdown-mermaid.ts`, a remark plugin that runs before Shiki). It uses `beautiful-mermaid` (pure JS with ELK, no DOM or browser), so a diagram page ships no diagram JavaScript and `bun run website:build` needs no Playwright. The plugin strips beautiful-mermaid's `<style>` block (a Google Fonts `@import` the CSP blocks, plus unscoped `svg`/`text` rules) and `prose.css` carries the same variables scoped to `.mermaid-svg`; it also prefixes marker ids per diagram and keeps the source in a **Diagram source** disclosure. Flowcharts, state diagrams (composite `state "Open" as open { ... }` blocks included) and sequence diagrams work. beautiful-mermaid draws nothing for `note` lines, so the plugin rejects them, and a block it cannot parse fails the build with the page path. Each SVG is `role="img"` with an `aria-label` taken from the paragraph before the block (closing colon dropped), or from a `%% alt: ...` line in the block when that paragraph is long; a block with neither fails. `markdown-mermaid.unit.test.ts` renders every block in `website/src/content/docs/**/*.md`, so `bun run test:unit` catches a broken diagram on the pull request; `website:build` runs only in the release rehearsal job. ELK breaks cycles badly: a back edge to the first node (`K --> A`) put that node mid-graph, so draw loops as a final node instead. Wide `LR` diagrams shrink to the column only to 70% of their size and then scroll, so prefer `TD` above roughly 800px. The installed docs bundle and GitHub keep the blocks as Mermaid text. `rehypeZoomableImages` (`markdown-images.ts`) wraps each Markdown image with a `/` or `http(s)` address in a link to the file (a relative image is left alone: Astro rewrites its `src` after rehype, so the link would 404); it runs before `rehype-external-links` so an external image link gets the usual `rel`. `docs-image-lightbox.ts`, run by `DocsImageLightbox.astro` and tested in jsdom, opens it in a native `<dialog>` (focus on **Close**, Escape closes, focus returns to the link); without JavaScript the link opens the image.

## Published JSON Schemas and docs examples are generated and tested

`website/public/schemas/` holds JSON Schemas for `.openwaggle/actions.json`, `.openwaggle/settings.json`, OpenWaggle's `mcp.json`, and the Waggle presets file. `bun run website:schemas` generates them (`scripts/published-json-schemas*.ts`): Effect's `JSONSchema.make` (2020-12) over the runtime schema, with Effect's refinement titles stripped and curated descriptions applied by JSON Pointer (a pointer that no longer exists fails generation). MCP has no Effect schema, so its JSON Schema is built from `mcp-server-config.ts` constants. `published-json-schemas*.unit.test.ts` fails on drift and checks each schema against the runtime reader on a corpus of valid and invalid files; `docs-config-examples.unit.test.ts` runs every JSON example in the config docs through the real reader (Pi's `ModelRuntime` for `models.json`, `buildSchedulesCliCommands('import')` plus `scheduledTasksExport` for the `scheduled-tasks` export envelope). A `"$schema"` key works only where the reader keeps unknown keys: `settings.json` and OpenWaggle's `mcp.json` keep it; `actions.json` decodes exactly and rejects it; `waggle-presets.json` reads it but Settings rewrites the file without it. The Agent definition schema stays hand-written. The unit tests are the only drift gate (there is no `--check` script). Rejection cases match the runtime reader's error through `runtimeRejection`, so a case cannot pass on an unrelated mistake. The `sourceControl` enums come from `SOURCE_CONTROL_PROVIDER_IDS` and `CHANGE_REQUEST_OPEN_DESTINATIONS`, the constants `parseProjectSourceControlConfig` checks against. Scripts must load Pi with a dynamic `import()`; a static Pi import outside `src/main/adapters/pi/` fails `main-architecture-boundaries`.

## Website landing and SEO

Pages build to `<route>/index.html`, so Cloudflare Pages serves `/docs/x/` and answers `/docs/x` with a `308`. Internal links must use the trailing-slash URL: `rehypeTrailingSlashLinks` rewrites Markdown/MDX links, `docsPath()`/`canonicalDocsPath()` build component links, and a source-scan test fails on slash-less hard-coded `href`s. Do not switch to `build.format: 'file'` to avoid this: versioned package routes such as `/docs/packages/pi-waggle/0.1` would look like file extensions to the host. Package nav slugs are noindex aliases; link and list them through `canonicalDocsPath()`, and keep redirect-only routes out of the sitemap (`website/src/lib/sitemap.ts`).

SEO metadata lives in `website/src/lib/seo.ts`. Every page emits one JSON-LD `@graph`; pages that reference the Organization or WebSite by `@id` must also define them. The default Open Graph image is `website/public/og/openwaggle.png` (1200x630), rendered from an HTML template with the logo assets; og image dimensions are emitted only for that image. `/llms.txt` indexes the docs for AI assistants.

The app repository has no LICENSE file (only the npm packages declare MIT), so the website must not call the app "open source" until one is added; a test guards the JSON-LD and default description. `logo-wordmark.svg` and `logo-lockup.svg` draw the name with SVG `<text>` in Clash Display plus a hard-coded `dx`; inside `<img>` the web font never loads, so the system fallback renders it, with "n" and "W" touching. Converting the text to outlines is the fix if the rendering must be stable.

Cloudflare Pages answers every unmatched path with the homepage and a `200` unless the build has a top-level `404.html`; `website/src/pages/404.astro` provides it (noindex, no canonical or `og:url`, absolute links because it renders at any depth). Before it existed, `https://openwaggle.ai/install.sh` returned the homepage HTML, so `curl -fsSL … | bash` would have fed HTML to bash. The documented command is `curl -fsSL https://openwaggle.ai/install | bash`, defined once in `website/src/lib/install-command.ts`; docs pages write `{{install-command}}`, `{{install-url}}` or `{{install-script-raw-url}}`, which `remarkInstallCommand` (website), `scripts/installed-docs-generator.ts` (bundled docs) and `scripts/package-documentation.ts` (npm package READMEs) fill in, and `installer-url.unit.test.ts` pins README.md and scripts/install.sh to the constant. `/install`, `/install/` and the older `/install.sh` are each an explicit `302` in `website/public/_redirects` to the raw `main` installer URL (302 so no cache keeps a permanent answer if that home moves); `installer-url.unit.test.ts` guards the rules and that no page, public asset, Pages Function or Astro redirect claims those paths first (Functions run before `_redirects`). Keep it out of Astro's `redirects`: a static Astro redirect writes a meta-refresh HTML file at that path, which is the bug again. `wrangler pages dev website/dist` reproduces the host's 404, redirect, and fallback behaviour locally. The hero's release-stage badge is derived from the root `package.json` version by `website/src/lib/release-stage.ts` (Alpha, Beta, Release candidate; none at Stable; an unknown stage fails the build), so it follows each release PR. `current-wording.unit.test.ts` scans `website/src` (without the bundled docs) and `website/public`: it fails on a stage word hard-coded in an `.astro` file, and on "unsigned", "Sessions CLI", or "openwaggle sessions" in any text file. It skips `astro.config.ts`, whose redirect comment names the Sessions CLI on purpose. The website guards that need no Astro build (`release-stage`, `installer-url`, `current-wording`) are `*.unit.test.ts` so the per-PR Unit Tests job runs them; the `website:test` suite itself runs only in the full rehearsal. `404.test.ts` also checks the built `dist/404.html` when `website/dist` exists.
