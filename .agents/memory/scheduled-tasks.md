# Scheduled tasks

Heartbeats and Launch schedules (ADR 0057, ADR 0058): Host-only task records, missed
firings, Wake checks and their approval, run outcomes, and how the GUI and CLI show tasks.
Load when touching `scheduled-task-*`, `features/scheduled-tasks` or `schedules-cli*`.

## Scheduled tasks (ADR 0057, ADR 0058, October 2026)

Heartbeats and Launch schedules are Host-only SQLite records (`scheduled_tasks`, `scheduled_task_runs`, migration 70), served by the `scheduled-tasks-v1` Local Session contract (revision 26) and handled in `application/scheduled-task-commands.ts`, never through `authorizeLocalSessionCommand`'s contract path (`classifyLocalSessionPayload` treats it as GUI-only so a probe can never pass). The scheduler (`session-host/scheduled-task-scheduler.ts`, started from `runtime-host-services.ts`) ticks every 30 s, fires due tasks one at a time, and holds a `scheduled-task` liveness owner while any task is enabled; that kind is idle-clock-neutral and is excluded from `hasBlockingDrainOwners`, so a stop or update still drains the Host. A run acts as the task's owner: `resolveScheduledTaskCaller` rebuilds the local user or refreshes a `profile:` caller, held within `authority_limits_json` when a Session agent narrower than its owner created the task (ADR 0058 amendment, migration 86; `creator_caller_id` is the runs-as caller, `creator_*` the provenance), and the request goes through `dispatchNonHostUiLocalSessionCommand` (wrapped in `dispatchScheduledTaskCommand` for typing), so authorization, ceilings and reach are the creator's own. Creating a task authorizes by probing that same request (`authorizeScheduledTaskTarget`). Provenance is Host-authored: the run row's `idempotency_key` equals the Session Control request key, and `loadRunExecutionProfile` joins `session_runs.intent_json.idempotencyKey`/`callerId` to it to add `scheduledTask` to the Run identity context; the prompt text is never wrapped. A Heartbeat fires only into an idle Session (no active Run, no Follow-ups, `pi` CLI not last writer); otherwise `markScheduledTaskWaiting` keeps `next_run_at` in the past and the scheduler rechecks every 60 s in memory. Bookkeeping writes use `updated_at` as an optimistic version (`applyWithRetry`); a user reschedule (new `anchor_at`) wins over a concurrent firing's next-time plan. `schedules:read`/`schedules:manage` are in `DEFAULT_SESSION_AGENT_CAPABILITIES` but not in `GRANTABLE_CHILD_CAPABILITIES`, so Workers never get them. A Session's execution profile `sessionCapabilities` is an allowlist intersected with the default grant, so a top-level Session that persisted the whole default of its time silently lost every capability added later (#335's schedule actions vanished for Sessions made before beta.23 and for Sessions their agents created, forked or spawned). Never widen a persisted list at read time: an agent definition, a narrower creating agent or an access profile can legitimately persist the 16 pre-#335 capabilities without `schedules:*`, and a decoder heuristic handed them `schedules:manage` (caught in review of #455). Instead `migrateLegacySessionCapabilityGrants` (`adapters/sqlite-legacy-session-capability-migration.ts`, marker `sessionCapabilityGrantsRestored`, not a ledger migration) runs once at Host start (one transaction, before the Host listens; ~0.65 s for 101k profiles and 50k spawn edges on a loaded Mac) and removes lists that only held a default grant. The decision is the pure `sessionsHoldingOnlyADefaultGrant` (`domain/session-control/default-grant-restore.ts`): local-user origin, no definition list on the Session or any Session it came from (transitively, any edge), and either the whole current default, the pre-#335 grant written before migration 70 ran, or the pre-#335 grant whose every source (`session_agent_origins`, fork operations, `session_spawn_lineage`) is restored, as a least fixpoint. A SQL recursive CTE got this wrong in review: filtering mixed-source nodes only in the final SELECT let their descendants through. The loader guards every `json_*` call with `json_valid` inside CASE, so one malformed row is skipped instead of failing every start. New Sessions persist no list when the caller holds the whole default (`callerSessionCapabilityRestriction`); parent, source and definition lists stay verbatim. The hive tool's `help` names withheld schedule capabilities under "Not available to this Session" and `help topic=<denied action>` explains the missing capability instead of "No hive action". Background start writes a LaunchAgent (macOS), XDG autostart entry (Linux, under `app.getPath('appData')`) or login item (Windows) that runs `<app> -- host start`; the OS registration is the setting.

- A scheduled task must never depend on the Session of the agent that created it (2026-11-02): resolving a deleted Session's agent threw inside `Effect.gen` (`assertLiveAuthority`), a defect that escaped `catchAll` and every tick, so no task fired for days and nothing showed attention. Tasks now run as the owner with stored `authorityLimits` (`applyAuthorityLimits`, also applied in `refreshNamedProfileCaller` so dispatch keeps them), legacy `session-agent:` tasks are adopted on their next check (`adoptAgentCreatedTask`), and every sweep step runs through `forTask` so one task's defect only logs `Scheduled task step failed`. A run's Session Control intent names the owner (`local-user`/`profile:`), so the initiator walks (`runCeilingStep`, `runReachStep`) give the agent in that Run the owner's ceiling and reach, not the limits. A launched Session is still bounded because it stores the limits as its execution ceiling and authority snapshot scope; a Heartbeat's existing Session is not, so `heartbeatBoundaryRefusal` refuses (at creation and each run) a target that reaches every project for a project-limited task, or a YOLO target for an ask-for-approval task. `callerAuthorizationCeiling` only clamps the started Run's own mode. Agent-created Launch schedules also re-check the project catalog at each run (`launchNeedsKnownProject`), since unrestricted agents store no limits.
- A Host that dies while a run is `dispatching` must not leave it to re-fire: the next tick would send the same firing again under a new idempotency key and launch a second Session. On start, `settleInterruptedRuns` joins the run's `(caller_id, idempotency_key)` to `session_operations`, which Session Control and Session lifecycle write in the same transaction as the Run or Session they start, so a row there means the request was delivered; the run settles started (or refused) and the task moves past that firing (`scheduled-task-interrupted-runs.ts`). No row means nothing was sent, and the task stays due for an ordinary catch-up.
- The GUI has no Scheduled tasks page. A task opens where the user is (`useShowScheduledTasks`): the Right panel's `scheduled-tasks` workspace index surface when a chat in its project is open, otherwise Settings › Scheduled tasks. Each container keeps its own view (`list | task | edit | new`) in `scheduled-tasks-navigation-store`, and the editor replaces the detail in place. The Session Summary's `scheduled` section lists the Session's Heartbeats or the Launch schedule that started it. The schedule math (`task-schedule`, recurrence rules) lives in `src/shared/domain/scheduled-tasks` so the editor's next-runs preview applies the Host's own rules. Components the shell renders without a QueryClient (the panel title) read the derived `scheduled-task-index-store`, not the query.
- Task times are presented to the second with the UTC offset on every surface (#355): `zonedTimestamp` (`YYYY-MM-DD HH:MM:SS ±HH:MM`, `@shared/utils/zoned-time`) backs the hive tool result (`sessions-tool-schedule-result.ts`) and `cliWallClockTime` (which appends the zone name); the renderer's `formatAbsoluteTime` uses `timeZoneName: 'shortOffset'` even on the machine's own zone. Minutes alone made a jittered 09:58:59 look 2 minutes early, and without the offset the two occurrences of a repeated DST hour read the same. `isTaskScheduleJittered` (task-schedule.ts) decides the jitter note shown wherever `nextRunAt` is (`nextRunJitter` in the tool, `(±5 min)` in `schedules` and `status`, `± up to 5 min` in the app); it anchors at `nextNominalAt ?? createdAt` because `ScheduledTask` does not expose `anchor_at`. The note's text comes from `SCHEDULED_TASK_JITTER_MINUTES`/`SCHEDULED_TASK_JITTER_TEXT`. `ScheduledTaskStatusSummary.jittered` is an additive status field. A `runs-listed` page names no zone, so human `openwaggle schedules runs` reads the task (`read`) for its zone and falls back to the machine's; `--json` sends only the `runs` request. App absolute times use the task's zone when it differs from the machine's (`differingTimeZone`), including the Session Summary tooltip. Every last-run surface names its trigger (`schedule`/`catch-up`/`run-now`), so a manual run never reads as a misfire. Enable switches are named for their checked meaning (`Task enabled`, `<name> enabled`), never an action like "Pause", which a screen reader would read as "Pause, on".
- MCP clients cannot manage Scheduled tasks: `openwaggle mcp serve` authenticates as `transient-mcp:<digest>`, an authority that ends with the process, so no run could revalidate it. The MCP adapter rejects `scheduled-tasks-v1` with an explicit message instead of exposing operations the Host would always refuse.
- `missedOccurrences` counts at most 1000 firings (about 3.5 days of a 5-minute Heartbeat), but must still return the true latest occurrence, which the catch-up run names; it finds it by an expanding look-back window from the end.
- Reading a timestamp CLI usage error by its message words mislabels it (`Missing …` became `not_found`); argument errors throw `CommandCliUsageError`, which `isCommandCliUsageError` recognizes by type.
- Heartbeat efficiency (#388, ADR 0057 amendment, migration 75 `heartbeat-efficiency`, Local Session revision 28): `scheduled_tasks` gained `stop_when`, `indefinite`, `idle_pause_after`, `consecutive_idle_runs`, `wake_check_*` and `auto_pause_*`; `scheduled_task_runs` gained `wake_check`, `outcome*` and `context_json`. Heartbeat-only state is presented as `task.heartbeat` (null for a Launch schedule) and written by `writeHeartbeatColumns` after the main insert/update, in the same transaction. The rule that every Heartbeat has a way to finish is `heartbeatHasStopCondition` (`@shared/domain/scheduled-tasks/heartbeat-rules`), checked by the Host (`stopConditionRefusal`, also on update) and early by the tool, CLI and editor; MCP cannot create tasks at all. The migration marked only Heartbeats with no `ends_at`/`max_runs` as indefinite.
- The Wake check runs inside `fireScheduledTask` after the idle-Session precheck (`scheduled-task-heartbeat-gate.ts`), before any run row, so a Host that dies mid-check just rechecks at the next tick. The runner is a hook (`ScheduledTaskHooks.runWakeCheck`, `adapters/scheduled-tasks/wake-check-process.ts`) installed by the scheduler; it reuses Project actions' `processCommand` (shell choice) and `getInteractiveTerminalEnv`, spawns without a PTY so stdout and stderr stay apart, leads its own process group (POSIX) and kills the group 500 ms after the shell exits and at the 30 s timeout (taskkill `/t` on Windows), then stops waiting 500 ms later even if a descendant holds the pipe. `decideWakeCheck` is pure: idle only for exit 0 and blank stdout; failure for a start error, timeout, signal, or 126/127. Stderr with exit 0 is idle on purpose (tools print progress there). The scheduler loop is serial, so a slow check delays later due tasks by up to 30 s.
- Approval is Host state, not a Pi Authorization request: `wake_check_approved_command` must equal the command; `pending_since` marks a hold. A local-user principal setting a command approves it; others' new commands are pending when `sessionAuthorizationMode(target, creator)` (hook over `resolveEffectiveAuthorizationMode`) is `ask-for-approval`, re-evaluated at each firing (a YOLO Session clears a stale hold). A held Heartbeat waits via `waitForSession(..., 'wake-check-unapproved')`, like a busy Session, so the scheduler rechecks every 60 s with no process spawn. `approve-wake-check` refuses profile callers; a session-agent caller is accepted because only the hive tool's post-`ctx.ui.confirm` path sends it (no tool action exposes it; precedent: export-write authorization is enforced in tool code). The editor sends `heartbeat.wakeCheck` only when the user changed it, so saving another edit never approves a pending command.
- Run outcome: `report-outcome` takes the Session Run id (`durableSessionRunId`), finds its run via `scheduled_task_runs.run_id`, and accepts only that Run's own Session (or the local user). A reported outcome replaces an earlier one; an inferred one only fills a blank. `done` auto-pauses at report time; idle/acted are applied once when the Run ends, through `ScheduledTaskHooks.heartbeatRunEnded`, which `session-control-run-dispatch.ts` calls for Heartbeat Runs with the Run's tool-call parts and the scheduler settles in a forked effect (`settleHeartbeatRunOutcome`). Inference uses `HEARTBEAT_READ_ONLY_TOOLS`/`HEARTBEAT_READ_ONLY_HIVE_ACTIONS`; `bash` and `codemode` always count as acted. A failed or aborted Run with no report changes nothing. `runCount` still counts started runs only, so skipped checks never use up `maxRuns`.
- The Run identity's Heartbeat fields and its per-task model come from the run row's `context_json` (`HeartbeatRunContext`, decoded with an exact schema; an unreadable one is dropped with a warning, the Run still starts), joined in `loadRunExecutionProfile`. The task model overrides `execution.model`; its thinking level reaches Pi as `AgentRunInput.thinkingLevel`, which `runAgentKernel` applies by overlaying `executionThinkingLevel` on the Session detail, so the Session's profile is never written. Renderer strings must not contain `#388`-style issue refs: the design-token lint reads `#388` as a raw hex color.
