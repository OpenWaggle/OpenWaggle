# Babysit

Watch one ready PR until it converges: every required check on the head commit passed, no bot review is running, and no review comment is open. Fix every correct finding and everything the branch broke; answer the rest.

`bun run pr:watch` reads GitHub and recommends the next actions. You make the judgement calls. GitHub API commands, bot details and reply formats are in `references/github.md`.

## Rules

- Stay on the PR's head branch with a clean tree. Unrelated uncommitted work: ask.
- Never merge, never toggle draft, never resolve a review thread. Resolving is the maintainer's call after they read your reply.
- Push only when the snapshot says `canPush: true`: no check is running and no bot review is working on the head. A push during a bot review wastes it on a dead commit.
- Fixes go through the normal flow: Conventional Commit subjects, plain `git push`, hooks running. Never skip a hook. When one fails, fix the cause; when the cause is outside the branch, stop and report it.
- Everything you post goes out under the maintainer's account, so it opens with `> _This was generated by AI via the babysit skill._` and ends with `<!-- babysit -->`.
- Do not ask a bot for a review (`@codex review`) unless the maintainer asks. Each request spends their quota.
- Force pushes are refused, with no prompt and no override (the `pre-push` hook and `.pi/extensions/git-guardrails.ts`), so every fix is a new commit. A rerun past the limit (`--rerun-job <id> --force`) needs the maintainer's agreement; say in chat what it does and why.

## Loop

1. Resolve the PR: a number, URL or branch from the maintainer, else the current branch's PR. Open every progress update and the final report with the PR as a Markdown link.
2. Run `bun run pr:watch -- <pr> --watch` with a shell timeout of at least 600 seconds. It polls every 45 seconds and returns once an action other than `wait` comes up, or after 9 minutes. After acting, pass the last snapshot's `--since <signature>` to return on any change.
3. Handle every action in the snapshot (table below). Collect the round's fixes and push them together once `canPush` is true.
4. Repeat from step 2. A push is progress, not the end. The loop ends at `converged`, at a `stop`, or when every open item waits on a maintainer decision.

| Action | Do |
| --- | --- |
| `wait` | Nothing; watch again. No checks after two timed-out watches: ask the maintainer whether CI runs for this branch. |
| `diagnose_ci_failure` | Classify each failed check (below), then fix or rerun. Start before `canPush` if you like; push only once it is true. |
| `handle_comments` | Work through every `openItems` entry (below). |
| `stop` `draft` | The PR is back in draft. Report and stop; `/ready` comes first. |
| `stop` `merged` or `closed` | Report and stop. |
| `stop` `checks_need_approval` | A workflow or deployment waits for the maintainer. Ask them, then watch again. |
| `converged` | Final report, stop. |

A CI failure never ends the loop. When you need the maintainer (a direction, a rerun past the limit, an approval), ask in chat with your recommendation, wait for the answer, then carry on.

## CI failures

Each entry in `checks.failed` has the job `id`, `attempts`, `retriesLeft` and a `logCommand` (`gh run view <run> --job <id> --log-failed`). Read the log and find the earliest line that names a cause.

- Branch-caused: the error points at code, tests or config this PR changed. Reproduce it locally when that is cheap, fix it, rerun the same command locally.
- Flaky or infra: runner, network, registry or timeout errors, or a test the diff does not touch that passes on `main`. Rerun with `bun run pr:watch -- <pr> --rerun-job <id>`. The watcher allows 3 attempts per job per SHA. Never edit unrelated tests, CI config or pins to get a flake through.
- Out of reruns, or the same failure survives two fix attempts: rethink the cause from the log before touching code again. If the direction is still unclear, or the cause is outside the branch, ask the maintainer (another fix, `--rerun-job <id> --force`, someone to involve).
- `warnings` lists optional check failures and bot reviews that did not happen. They do not block convergence; report them.

## Comments

Every open item gets the same treatment, person or bot. Each entry has `kind` (`thread`, `comment` or `review`), `author`, `body`, `path` and `line` for threads, `outdated`, the replies so far, and `reply`, which says how to answer it.

- Correct: fix it in this round's push, on this PR. A correct finding from a person, and any bot finding above P3, is never deferred.
- A bot's P3 or nit after the first fix push: give it a disposition instead of another push, the same rule `/ready` uses. Fix it only if it is a real defect. Otherwise reply with the disposition: accepted with a one-line reason, or tracked in a GitHub issue.
- Needs a product or design decision: ask the maintainer with your recommendation and leave the item open until they answer.
- Wrong, or already done: reply with the evidence (file, line, commit, test).
- Outdated thread: check whether the code it points at still has the problem, then fix or reply.
- A question: answer it. Nothing to do (praise, FYI): a one-line acknowledgement.
- Replies change the picture: follow the latest word from the author or a maintainer over the original request.

After the push that carries the fixes, reply to each handled item and leave it unresolved. A thread whose latest comment is your babysit reply counts as handled and moves to `answeredThreads` until the maintainer resolves it. Any later reply opens it again. Conversation comments and review bodies have no threads: your reply names them with the marker in `reply.marker`, and one reply can name several.

## Final report

- PR link, head SHA, check result
- Fix pushes and reruns used
- Each item: fixed (commit), answered, or waiting on the maintainer and why
- `answeredThreads` left for the maintainer to review and resolve, as links
- Warnings (bot reviews that did not happen, optional checks), decisions made along the way, anything still open
