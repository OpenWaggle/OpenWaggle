# Own the Project Actions model in OpenWaggle

Status: implemented; validated in Electron and independently reviewed

Date: 2026-09-21

Project Actions currently expose T3-specific configuration and terminology, as described in ADR 0030. The redesign will use OpenWaggle's own configuration and domain language, borrowing useful behavior from Codex, T3, and editors without adding tool-specific importers to this scope. Discovery of ordinary project commands, such as `package.json` scripts, remains compatible with this boundary.

We chose native behavior over a configuration-compatibility layer so the feature can evolve around OpenWaggle's needs without inheriting other tools' schemas. The redesign removes the existing T3 importer, T3-specific product wording, and automatically supplied T3 environment aliases. The native catalog, managed runs, workspace preparation, migration, and renderer now implement this design. Migration runs when the native catalog is first read and retains the previous configuration as a private recovery copy.

Existing saved actions, including actions previously imported from T3, are preserved as native local definitions for their projects. The redesign stops supplying `T3CODE_PROJECT_ROOT` and `T3CODE_WORKTREE_PATH`; `OPENWAGGLE_PROJECT_ROOT` and `OPENWAGGLE_WORKTREE_PATH` are the native equivalents. Detected references to the removed names are flagged and offered reviewed conversion. Commands or project scripts that depend on those aliases need updating; the migration does not silently rewrite arbitrary project scripts or delete saved actions. No temporary T3 alias compatibility layer is retained.

Configured setup must finish successfully before the first agent turn starts in a new worktree. A setup launch or execution failure pauses that turn and offers Retry or an explicit Continue anyway. This replaces ADR 0030's best-effort setup dispatch in the redesign: accepting a command into a terminal does not establish that the workspace is ready. Long-running development servers are explicitly launched Project Actions, separate from Workspace setup.

Workspace setup has dedicated configuration, separate from Project Actions launched on demand while working. It replaces the choice of marking one Project Action as setup, making automatic preparation and explicitly requested execution distinct in the product. Both can invoke scripts already present in the project; users do not need to save a Project Action before configuring setup.

Configured setup runs automatically when OpenWaggle creates a new managed worktree. Existing local checkouts offer an explicit Run setup operation; opening a checkout or starting its first agent turn does not trigger setup. This keeps an already prepared working directory from being changed merely by opening it in OpenWaggle.

Successful setup retains its exported environment changes locally for the workspace. Subsequent agent commands and Project action runs inherit that prepared environment, including toolchain path changes or workspace-specific variables. Failed setup does not publish a partial environment as ready. These runtime values do not enter shared project configuration, affect other workspaces, or alter already-running processes.

The redesign includes optional Workspace cleanup, configured separately from on-demand Project Actions. It runs before actual removal of a managed worktree, after the final session binding has been released. Closing or archiving one session does not run cleanup while another session still uses that workspace. This lets projects release worktree-specific resources, such as temporary databases, while the checkout is still available.

Stop setup targets one exact active attempt and waits for its process tree to terminate before releasing workspace admission. A stopped attempt exposes Retry and Continue anyway and does not publish partial environment values. Recreating a missing checkout preserves its preparation snapshot but resets execution state and exported environment for the new checkout.

If cleanup fails to launch or exits unsuccessfully, OpenWaggle retains the worktree and shows the failure, offering Retry cleanup or an explicit Delete anyway. Retaining the checkout preserves scripts and configuration needed for recovery. Delete anyway bypasses the failed cleanup and may leave external resources behind; it does not represent successful cleanup.

Project Actions default to one active run per action per workspace, including finite tasks such as Test and Build. Launching an active action opens its existing run's status and output; it does not queue another run or interrupt the current one. Restart explicitly stops that run and waits for termination before starting its replacement. Once a run has finished, Run starts a new execution. Different actions and different workspaces can run independently. An advanced per-action Allow concurrent runs option permits overlapping finite task executions, each with its own status, output, and controls. Long-running actions retain the single-instance rule.

OpenWaggle manages long-running actions with visible running status, output, and Stop/Restart controls. These actions start on an explicit user or agent request, not as part of Workspace setup.

Action runs appear in the existing Session Hub alongside the workspace's other session context. Selecting a run opens its output and controls in the right sidebar, following the Hub's established detail-view pattern. The run view provides relevant operations such as Stop, Restart, Open preview, copying output or the command, and asking the agent to investigate a failure. A narrow-screen prototype presents that same detail view at full width with a return to the session; it must remain usable by touch.

Project Actions in Settings manages saved definitions, task references, local or project storage, and execution preferences. Workspace preparation has a separate section for setup and cleanup. Settings may show a compact summary of current runs with a link back to the Session Hub, but the live run view belongs to the session. Add action first offers discovered project tasks or a custom command, then naming and storage choices, defaulting to local project-scoped storage. The maintainer accepted this UI direction on 2026-09-21 after reviewing the replacement prototype. Production implementation should use OpenWaggle's existing components and follow this interaction structure; the prototype is a design reference, not production code.

This default follows the concurrency limit in [VS Code tasks](https://code.visualstudio.com/docs/debugtest/tasks#_run-behavior) and [Zed tasks](https://zed.dev/docs/tasks), which both prevent concurrent copies by default and allow an explicit override. Their repeat-launch behavior differs: VS Code supports instance-limit policies, while Zed normally queues the next execution. [T3 Code at commit 1de563c](https://github.com/pingdotgg/t3code/blob/1de563c1491c7d82563e4553bf5bf689ce6adbb9/apps/web/src/components/ChatView.tsx#L4193-L4306) opens a new terminal when the selected terminal is busy, allowing overlap. Read-only inspection of installed Codex 26.915.31945 found an action terminal keyed by task, environment, and action slot; repeating that action replaces its terminal process. OpenWaggle keeps the common single-instance default and makes replacement explicit so a second click or agent request cannot interrupt work already in progress. This is a deliberate choice among established behaviors, not a claim that all reference tools behave identically.

Agents can discover saved actions, launch them, inspect their status and output, and stop them within their workspace under existing authorization rules. The UI and agents use the same managed executions and concurrency policy, including reuse of an already-running action by default. Saving an action does not grant an agent additional execution permissions. An agent can therefore use a development server started through the UI without creating its own duplicate server.

Long-running actions stop automatically when the last session releases their workspace, including when that final session is archived. Stopping precedes Workspace cleanup and managed worktree removal. Switching the visible session does not stop these processes, nor does releasing one session while others remain bound to the workspace. This keeps process lifetime tied to workspace use without accumulating servers for abandoned workspaces.

Deleting the workspace removes its preparation state, private environment, runs, and request receipts. A transactional cleanup queue retains failed output-file deletions for retry when the Host starts; one failed deletion does not block other cleanup or Host startup.

Long-running action processes survive a full desktop app quit while their workspace remains in use. When OpenWaggle reopens, it automatically reconnects to the existing runs, restores their current status and retained output, and resumes live output and controls. Reconnection must not rerun commands or create replacement processes. This requires background ownership and retained run state beyond the desktop-owned terminal execution described in ADR 0030 (Adopt A Single Local Session Host), so background agent work can continue using these processes.

If an action process has actually stopped, including after a computer restart, OpenWaggle shows its stopped or interrupted state, preserves available output, and offers Restart. It does not automatically relaunch the command when the app returns. Reconnecting to a live run and explicitly starting a replacement run are distinct operations.

For development-server actions, OpenWaggle detects the preview URL from server output, shows readiness, and opens the Browser preview when ready if that action's auto-open preference is enabled. A manual URL override remains available. Accepting a command for execution is not proof that its server is ready, so auto-open waits for readiness rather than terminal dispatch. The preview target belongs to the specific action run and workspace, including when a server selects a different available port.

Project Actions, Workspace setup, and Workspace cleanup default to private local storage associated with the selected project. Local storage does not make definitions global: commands for one project must not appear in unrelated projects. Users may explicitly choose to store definitions in the project for sharing through version control; creating a definition does not create shared repository configuration by default. This accommodates teams whose members use different tools. Project storage makes a definition shareable but does not itself commit or publish it, and local permissions remain private.

Storage is selected per definition: each Project Action, Workspace setup, and Workspace cleanup independently chooses local or project storage. Sharing a Test action therefore does not also share a personal debugging command or the project's setup and cleanup.

A user can customize a shared definition through a local override, leaving its repository definition unchanged. OpenWaggle uses the personal version for that project, presents one effective entry labelled Locally overridden, and offers a way to remove the override and restore the shared version. This avoids requiring a second, differently named action for personal adjustments. The override remains private and project-scoped.

Discovering shared Workspace setup or Workspace cleanup does not activate it. Users review and explicitly enable those commands for the project, and OpenWaggle remembers that enablement locally. Sharing a definition therefore offers it to teammates without enrolling them in automatic execution.

Remembered enablement covers the reviewed execution definition. Changes to its command or execution settings require review before the next automatic execution; cosmetic changes such as renaming do not. This check covers the definition, not every source file that its command might execute. When review is required, OpenWaggle must visibly explain the pending review and its effect on workspace preparation or removal, and provide a way to inspect the changed definition.

Project settings show a persistent Review required indicator beside the affected setup or cleanup. A blocked preparation or removal flow explains the pause and opens the review dialog automatically. The dialog compares the previous and current execution settings and offers Enable updated version or Keep disabled. Detecting a change without a blocked operation shows its pending state without opening the dialog; the blocked flow retains a Review changes entry point for reopening it. Closing the dialog does not enable the changed definition.

Each project has a default Preparation profile and may define additional named profiles, such as Frontend and Full stack. A profile groups optional Workspace setup and Workspace cleanup; Project Actions remain scoped to the project. Users select a profile when creating a worktree, with no extra selection required when only the default exists. The selected profile belongs to that workspace, so sessions sharing it use the same preparation. Profiles remain project-scoped and local by default, and setup and cleanup retain their independent storage choices.

A private setup or cleanup takes precedence over a shared definition occupying the same profile and phase, including when they were created independently with different IDs. The shared definition remains intact until the user explicitly stores their private version in the project; that operation replaces the destination phase. Removing the local override restores the shared definition and its own review requirement.

A worktree retains a Preparation snapshot of the selected profile's setup and cleanup definitions and execution settings from creation. Later profile edits do not silently change that worktree's preparation or cleanup: OpenWaggle shows that an update is available, and the user may explicitly adopt it. This keeps cleanup paired with the preparation chosen for the workspace until the user deliberately changes that pairing. The snapshot does not freeze project scripts called by those commands. Review requirements apply to the execution definition that will actually run; an upstream edit alone does not invalidate an unchanged, previously reviewed snapshot.

Operating-system differences belong to OpenWaggle's execution machinery. Users configure the action or preparation they want without selecting an operating system or maintaining macOS, Windows, and Linux variants. OpenWaggle handles platform-appropriate launching, shell selection, and its own path and environment handling internally, using existing project script and tool entry points where appropriate. The current shell resolver already selects platform-specific shells, but action execution currently passes command text through unchanged; shell selection alone does not make arbitrary custom commands portable.

An incompatible custom command offers Fix with agent. The user invokes this flow, which inspects the project and current machine and proposes a compatible command for review and saving. A repair proposal does not silently replace the saved definition or launch the proposed command. This provides assistance for platform-specific failures without making users maintain operating-system variants.

Action creation discovers commands from the selected project's own task definitions. For JavaScript and TypeScript, it reads `package.json` scripts; other ecosystems use readers for their supported task formats. Users pick discovered commands instead of retyping them, with custom command entry still available. Discovery alone neither saves an action nor executes a command; a saved selection uses local project-scoped storage by default. Candidates retain their source file, declared task name, runner, and required working directory so execution can invoke the project's task through its own tool. A language manifest alone does not imply that a named task exists.

Discovery includes the project root and its workspace packages, grouped by package so identically named tasks remain distinguishable. Each selected task retains its package-relative working directory, which resolves within the workspace where the action runs. For example, a website package's test task runs in that worktree's website directory, not in the root or a different checkout. Dependency and generated-output directories are not treated as project workspace packages.

Saving a discovered task creates a Project task reference rather than copying its script body into an independent command. At execution, OpenWaggle invokes that named task through the project's runner in the current workspace, so changes to the task's source definition take effect naturally. If the task is removed or unavailable in that workspace, the action shows as unavailable instead of running stale copied text. Users can still create custom actions whose command text they maintain separately. Preparation snapshots retain any task reference they contain, not the implementation of the referenced script, consistent with the snapshot boundary above.

Examples of relevant source formats include [npm package scripts](https://docs.npmjs.com/files/package.json/#scripts), [Hatch scripts in `pyproject.toml` or `hatch.toml`](https://hatch.pypa.io/latest/config/environment/overview/#scripts), [Cargo command aliases](https://doc.rust-lang.org/cargo/reference/config.html#alias), and [`justfile` recipes](https://just.systems/man/en/quick-start.html). These illustrate ecosystem-specific discovery, not a promise that every project manifest has an equivalent scripts section.

## Defaults inferred from existing tools

On 2026-09-21, the maintainer delegated the remaining process, migration, storage, and discovery decisions to established tooling patterns. The decisions below complete the design direction. They are OpenWaggle's application of those patterns, not a claim that all reference tools behave alike.

**Process ownership.** The existing per-user Session Host owns managed action executions and their control channel. Electron and the right sidebar attach to those executions. Closing a view or quitting Electron releases its attachment without releasing a session's workspace binding. The Host's keep-alive calculation must include action runs. This applies the independent client/server lifetime demonstrated by [tmux](https://man.openbsd.org/tmux.1#DESCRIPTION) to OpenWaggle's existing Host; it does not add a tmux dependency or ask users to manage a separate service. [VS Code distinguishes reconnection from process revival](https://code.visualstudio.com/docs/terminal/advanced#_persistent-sessions): window reload reconnects, while application restart can relaunch a process. OpenWaggle uses reconnection for surviving runs and retains its agreed explicit Restart behavior for stopped runs.

The Host serializes starts by workspace and action identity, allocates a run identity before launch, and deduplicates retried start requests. GUI and agent callers receive the same active run under the default concurrency policy. A run retains its resolved invocation, working directory, timestamps, result, and bounded output. Reattachment requests current status and output from a known cursor; it does not submit another start. Reconnection must verify the Host's run identity rather than trusting a stored operating-system process number. A lost transport shows reconnecting; confirmed loss of the execution shows interrupted with retained output. Restart resolves and validates the replacement first, then waits for termination of the previous owned execution before launching it. Output retention follows the existing bounded terminal-history policy, with truncation visible to the user.

**Storage and effective definitions.** Private definitions, personal overrides, selected profiles, and enablement records belong in OpenWaggle's local application storage, associated with the existing project/workspace relationship. Saving a private action creates no file in the checkout. Worktrees belonging to that project share its personal definitions; unrelated projects and independent clones are not merged by display name or remote URL. Explicitly shared definitions use a versioned `.openwaggle/actions.json` file, containing actions and preparation definitions. This is a dedicated sharing boundary; `.openwaggle/settings.json` retains its other existing responsibilities. Sharing does not export authorization grants, prepared environment values, or run history.

The reference patterns are [Codex's project configuration that users can check into Git](https://learn.chatgpt.com/docs/environments/local-environment), [Zed's separate user and worktree task definitions](https://zed.dev/docs/tasks), and [T3's project overrides with explicit source provenance](https://github.com/pingdotgg/t3code/blob/1de563c1491c7d82563e4553bf5bf689ce6adbb9/packages/shared/src/projectSettings.ts). OpenWaggle's local-by-default rule and personal-over-shared precedence remain the maintainer's chosen behavior. Resolve each stable definition ID to its complete personal override when present, otherwise to the shared definition from the current workspace. Do not silently combine execution fields from different revisions. Show the effective source and offer Restore shared version. Renaming or moving a definition between local and project storage preserves its identity and references.

**Migration and concurrent edits.** Use a versioned, repeatable migration with a completion record, following the repository's existing [canonical migration approach](0030-adopt-single-local-session-host.md). Preserve existing action IDs, commands, names, shortcuts, and preview preferences as local definitions. Map the legacy worktree-setup flag into the default preparation profile's separate setup definition, retaining the on-demand action and applying the agreed setup completion semantics. Preserve a local recovery copy; validate the destination before marking the migration complete. A failed or interrupted conversion leaves the source intact. Completed migration stops reading legacy actions as a second live source, so resetting an override cannot resurrect stale settings. This also follows the migration boundary in [T3's project settings resolver](https://github.com/pingdotgg/t3code/blob/1de563c1491c7d82563e4553bf5bf689ce6adbb9/packages/shared/src/projectSettings.ts), which stops consulting legacy fields once settings have been folded into the new record. Migration does not create a shared manifest or run any action.

Configuration writes carry the revision the editor read. A conflicting external edit produces a recoverable conflict with the user's draft retained, rather than overwriting the other change. Installed Codex 26.915.31945 uses an expected-revision check for local-environment saves; its inspected implementation returns a conflict when file content differs from that revision. OpenWaggle combines that pattern with its existing serialized, atomic configuration writes. Local database changes use transactions. A storage move writes and validates the destination before retiring the old effective entry, and can resume after interruption. Invalid configuration is shown as an error with its source; it must not masquerade as an empty action list. Existing reviewed conversion of removed `T3CODE_*` references remains unchanged.

**Task discovery.** Use an ecosystem-provider interface that separates listing candidates from resolving a saved reference, following [VS Code's Task Provider model](https://github.com/microsoft/vscode-docs/blob/main/api/extension-guides/task-provider.md). A reference identifies its provider, project-relative source file, task name, package directory, and any required environment selector. Initial declarative readers cover `package.json` scripts, Hatch environment scripts in `pyproject.toml` or `hatch.toml`, and project-local Cargo aliases in `.cargo/config.toml` or the supported legacy `.cargo/config` filename. JavaScript discovery includes declared workspace packages and uses the project's package-manager configuration, then unambiguous lockfile evidence. Conflicting evidence is surfaced instead of silently choosing another runner. Other ecosystems and unsupported task syntax retain the custom-command route; add readers when they can resolve that format faithfully.

Discovery remains read-only. In particular, VS Code's example Rake provider invokes Rake to enumerate tasks; OpenWaggle does not copy that behavior because discovery must not execute project code. It does not install dependencies or invoke build tools merely to fill the picker. Task-source changes invalidate discovery results, and each new launch resolves the reference again in the selected workspace. Missing files or tasks remain visible as unavailable saved actions with repair or removal controls. A missing runner is reported separately. Existing runs retain their launch context; editing a definition, changing branches, or refreshing discovery never restarts them. Already-running actions open their existing run even if their definition changed, while a subsequent explicit Restart resolves the current definition.

The implementation must demonstrate app-quit reconnection without an extra launch, repeated GUI/agent launch deduplication, separate runs in different workspaces, interrupted migration recovery, conflicting configuration edits, and changed or removed discovered tasks. These are validation requirements, not unresolved product questions.
