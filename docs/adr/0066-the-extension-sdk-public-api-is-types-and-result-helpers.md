# The extension SDK's public API is types and result helpers, with an Effect-free runtime

Date: 2026-11-12

Amends: [ADR 0005](0005-adopt-openwaggle-extension-contribution-host.md) and [ADR 0006](0006-adopt-federated-module-runtime-for-extension-ui.md), where "public typed schemas" for interaction primitives and broker payloads meant exported Effect Schema values. It now means published TypeScript types, plus a JSON Schema for the manifest. Supersedes the `@openwaggle/extension-sdk` paragraph of [release and versioning](../release-and-versioning.md) that made Effect Schema values the package's runtime contract.

`@openwaggle/extension-sdk` 0.2 exported 132 Effect Schema values next to the types derived from them. Every type a hover showed was `Schema.Type<typeof x>` over a chain of `Schema.Struct` generics, the published declarations were 32,795 snapshot lines, and any import from the root pulled Effect into the extension's browser bundle: 223 KB minified for the root entry, 165 KB for `./json`, which holds two types. `validateExtensionManifest` returned `{ manifest, issues: string[] }`, `validateBrokerCapabilityDeclaration` `true` or a message and `isOpenWaggleExtensionTheme` a type guard, so a caller learned three failure shapes, and only one of them said what was wrong. Extensions never needed the schemas. The host validates every broker payload and passes the broker SDK in `context.sdk`, so an extension only reads typed values. The decision, made with the maintainer, is to break the package once, in 0.3, and make its contract types and result helpers.

## Decision

- **No schemas in the public API.** The Effect schemas move to `packages/extension-sdk/src/internal/`, which no `package.json` export reaches. The host imports them through the `@openwaggle/extension-sdk/*` → `packages/extension-sdk/src/*` alias, such as `@openwaggle/extension-sdk/internal/manifest-schemas`, so it still validates with the schemas the types come from. Public types stay single-sourced. `scripts/generate-extension-sdk-types.ts` reads each `Schema.Type` alias in `src/internal/type-sources/` through the TypeScript checker and prints it as a named, readable type in `src/generated/`. A generated type test asserts each printed type equals its schema type both ways, and the `extension-sdk-types` check step fails when a printed file drifts. The build prunes declarations no export reaches, and the `api-snapshots` step fails when a published `.d.ts` imports from `effect`.
- **Result helpers only.** Every runtime check is `validate<Thing>(value: unknown)` and returns `{ success: true, value }` or `{ success: false, issues }`. Each issue is `{ path, message }`, and no helper throws on bad input. `path` is the dotted field path the host reports, with array items by index, such as `contributions.sidePanels.0.icon`, and `(root)` for the value itself. The 0.3 helpers are `validateExtensionManifest`, `validateBrokerCapabilityDeclaration` and `validateOpenWaggleExtensionTheme`, which replaces `isOpenWaggleExtensionTheme`. `defineExtensionManifest` stays, as a compile-time identity.
- **The runtime entries are Effect-free.** `.`, `./context`, `./types`, `./ui`, `./theme`, `./syntax`, `./constants`, `./json`, `./agent-loop`, `./docs` and `./runtime` hold types and plain functions only. Two tooling entries carry Effect. `./validation` holds the `validate*` helpers, for build scripts and tests. `./testing` holds `createExtensionBrokerSdk`, `createExtensionBrokerSdkFromInvoke`, `createRuntimeContributionSdk` and `toInvokeInput`, for test doubles and standalone previews. The names say who imports them. `./manifest` would have kept the 0.2 subpath with a different meaning, and `./broker` suggests extension code should build a broker. Extension code uses the host-supplied `context.sdk`. An integration test bundles each runtime entry with `bun build --minify --target=browser` and fails when the bundle contains a module from `effect`. `effect` stays a dependency, for the tooling entries.
- **The manifest has a published JSON Schema.** `website/public/schemas/openwaggle-extension-manifest-v1.schema.json` is generated with `JSONSchema.make` from the internal manifest schema, like the project file schemas, and the published-schema test fails when it drifts. A manifest names it in `$schema` for editor completion, and OpenWaggle ignores that key. The JSON Schema accepts what OpenWaggle accepts, with three differences. It allows undeclared keys, because OpenWaggle drops them instead of refusing them. The string rules, which are filters in the internal schema, reach it as the `pattern` and `maxLength` each filter names in `internal/manifest-json-schema.ts`, and a test checks both give the same verdict on the same samples. A network origin that the URL parser rewrites, such as one with a port above 65535, a port with a leading zero or an abbreviated IPv4 address, passes the pattern but not OpenWaggle. Rules across fields are not in it at all: a declared capability for each contribution's methods, `trusted.renderer` for a `trusted-renderer` contribution, a binary or command for each runtime requirement, and a Session Summary row that names a resource or an action but not both. Those need `validateExtensionManifest` or OpenWaggle's own load.

## Considered Options

- **Keep the schemas public.** Callers could compose them, but no extension did. Every public type would stay an Effect generic, Effect's version would become part of the SDK's contract, and the bundle cost would stay.
- **Put the schemas on their own entry.** A `./schemas` subpath would keep the types readable and the runtime small, but it would still publish Effect types, so an Effect upgrade could break a caller who never imports Effect. The JSON Schema covers the one case people asked for, an editor that checks the manifest.
- **Return Effect's `Either`.** It is typed, but the caller has to know Effect to read it, and `ParseError` would be in the contract again.
- **Throwing helpers.** One shape, but a caller's `catch` loses the type of the failure, and a build script that wants every issue has to parse a message.
- **Leave Effect in extension bundles.** Simplest, but a status widget that reads two constants shipped about 60 KB gzipped of validator it never ran, once per extension.

## Consequences

0.3 breaks every caller that imported a `*Schema` value, `./broker` or `./manifest`, read `validateExtensionManifest(...).manifest`, or called `isOpenWaggleExtensionTheme`. The package docs list the replacements. The API snapshot falls from 32,795 to about 7,200 lines, and the root entry from 223 KB to 23 KB minified. A schema change now needs `bun run extension-sdk-types:generate`, and a field's doc comment lives on its type source, not on the schema. The host still decodes with Effect, so a new rule is written once, in the internal schema, and reaches the types, the validators and the JSON Schema from there.
