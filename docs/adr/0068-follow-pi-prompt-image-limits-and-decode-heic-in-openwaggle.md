# Follow Pi's prompt image limits, and decode HEIC in OpenWaggle

Reported on issue `#465`: a screenshot taken with the Windows Snipping Tool cannot be pasted into the composer, and HEIC files from an iPhone cannot be attached at all. Triaging that turned up a second problem: OpenWaggle refuses images that `pi` accepts. The composer only ever reads `text/plain` off a paste, and the one place an image file could enter — the picker or a drag — drops any file without an on-disk path, so a clipboard bitmap is discarded in silence. Separately, `.heic` is not a known extension, so it fails with a message that claims images are supported, and `ATTACHMENT.MAX_SIZE_BYTES` (8 MiB per attachment, 20 MiB per message) binds images that Pi would have resized and sent. The decision is to stop having an image policy of our own: Pi normalizes every prompt image against the selected model's declared limits, so OpenWaggle hands images over and reads those limits rather than inventing a budget. HEIC is the one capability we add, because Pi's own decoder cannot read it.

## Decision

- **Pi owns prompt image normalization; OpenWaggle normalizes nothing.** Pi's agent session runs every image a prompt carries through its own resize step, against the budget the selected model declares in `inputLimits.images`, the user's `imageAutoResize` setting, and Pi's defaults when a model declares nothing (2000×2000, 4,718,592 bytes of base64, JPEG quality 80). It also emits the conversion and dimension notes the model needs to map coordinates. OpenWaggle therefore ships no resizer, no dimension note, and no megabyte budget of its own: an image that Pi could not carry must not be quietly fixed up by a second, drifting implementation. OpenWaggle's whole job is to hand the bytes over in a format Pi can read.
- **An image is accepted and shrunk, never refused for its size.** Pi reduces every image to the provider's budget before the provider sees it, so a 100 MB file never reaches a model that takes 20 MB: Pi delivers at most the model's base64 budget and it fits. The input file's size therefore decides nothing about whether a send can succeed, and a cap derived from the model's request budget would refuse files `pi` accepts — reinstating from the other side the divergence this decision removes. Images stop being bound by the per-attachment and per-message file caps; document attachments keep theirs, since nothing about inline images justifies changing them.
- **Model limits decide how many images a message carries, and what the single HEIC encode is fitted to — nothing else.** Declarations differ across the shipped catalog (`maxRequestBytes` of 20, 32 and 512 MiB, `images.maxPerMessage` of 20), so a global constant is wrong in both directions, and OpenWaggle reads `inputLimits` additively from the model metadata it already gets from Pi (`providers:get-models`) rather than keeping a parallel registry of model limits, per `CONTEXT.md`. Those numbers never bound an input file: they let the composer say early when a message carries more images than the chosen model accepts, and they are the budget the one HEIC encode targets.
- **HEIC and HEIF are decoded in OpenWaggle — the one deliberate capability beyond Pi.** Pi's decoder (Photon) aborts on HEIC and Pi falls back to a placeholder in the prompt, so `pi` cannot carry an iPhone photo at all. OpenWaggle decodes HEIC with libheif, encodes it once into an image that already sits inside Pi's default budget, and hands it to Pi, which then passes it through unchanged — one lossy encode, not two. Pi portability promises that every Pi capability is available in OpenWaggle; it does not require OpenWaggle to reproduce Pi's omissions. Nothing a `pi` user does today changes.
- **The clipboard is read through the desktop shell's clipboard port, not the renderer's paste data.** A Windows CF_DIB bitmap — what the Snipping Tool leaves on the clipboard — is not reliably exposed to the renderer as a file, which is why the reported case cannot be fixed in the paste event alone. The paste resolution order is: files on the clipboard, then an image with no accompanying text, read natively through the clipboard port, then text and today's long-text conversion. The main-process path is what fixes the reported case; the renderer path is the cheaper shortcut when the platform offers one.
- **Two dependencies are taken for HEIC, and their licences are recorded.** `heic-decode` (ISC) over `libheif-js` (LGPL-3.0), lazy-loaded the way `sharp` is, pruned in packaging, and shipped with its licence text and third-party notice. LGPL-3.0 is compatible with this GPL-3.0-only app provided the library stays a replaceable separate artifact, which the separately shipped wasm file satisfies. The wasm carries an HEVC decoder, the same component `sharp`'s prebuilt libvips excludes; that exposure is accepted deliberately, for this capability alone.

## Considered options

- **An OpenWaggle normalizer with a fixed budget.** Rejected: it duplicates work Pi already does correctly, and two implementations of one policy drift — the user would get different bytes in OpenWaggle than in `pi` for the same image, and a Pi user's `imageAutoResize` choice would silently mean nothing.
- **Converting HEIC through the operating system's codec** (macOS `sips`, Windows WIC, Linux `libheif-tools`). Rejected: three divergent code paths, a process per conversion, and silent unavailability wherever the codec is missing. Electron's own `nativeImage` is not an option — it returns an empty image for HEIC on macOS, verified.
- **Rejecting HEIC with a clear message.** Rejected by the maintainer: an iPhone photo is an ordinary thing to attach, and the current message is wrong regardless, since it advertises image support while refusing a common image.
- **A model-bound cap on the input file.** Rejected: Pi shrinks the image before the provider sees it, so this refuses files `pi` accepts — the same portability break, mirrored.
