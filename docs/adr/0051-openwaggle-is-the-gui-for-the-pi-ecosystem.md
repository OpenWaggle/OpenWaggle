# OpenWaggle Is The GUI For The Pi Ecosystem

Status: accepted

Supersedes [ADR 0014](0014-windows-mcp-stdio-sandbox.md) and [ADR 0035](0035-one-step-mcp-trust-with-a-curated-catalog.md). Supersedes the MCP ownership, model-facing surface, orchestration, activation, trust, and sandbox clauses of [ADR 0013](0013-adopt-first-party-mcp-integration.md); its `openwaggle mcp serve` server clauses stand.

Pi 1.0 made MCP, codemode, tool search, virtual models, and related features part of the Pi coding agent. OpenWaggle had built its own MCP client (about 20,000 lines) with its own gateway, `mcp_run` orchestration language, trust records, grants, and stdio sandbox. That made OpenWaggle a different MCP product from Pi, so a project configured for Pi did not work in OpenWaggle without importing and approving its servers. We decided that OpenWaggle is the GUI for the Pi ecosystem: OpenWaggle v1 supports everything the Pi coding agent supports, and everything a Pi user carries works unchanged (**Pi portability**). OpenWaggle's own choices come first wherever OpenWaggle and Pi both offer a location or a default, and users are never asked to manage trust, migration, or compatibility themselves.

## Decision

- **MCP runs on Pi's built-in MCP extension.** OpenWaggle loads `createMcpExtension()`, `createCodemodeExtension()`, and `createToolSearchExtension()` into every Pi session, because SDK sessions do not load Pi's built-ins. OpenWaggle supplies Pi's plug-in points: `loadConfig` (OpenWaggle's file set), `createTransport` (hardened HTTP, legacy SSE and WebSocket, and the MCP transport layer), `credentials` (the encrypted vault first, Pi's `mcp-auth.json` read as a fallback, never written), `openUrl` (automation-safe browser opening through the Session Host), and `updateConfig`.
- **The MCP transport layer** wraps each server's message stream to keep the OpenWaggle features Pi lacks without a second client: it adds client capabilities, answers sampling and elicitation in OpenWaggle UI, and reads MCP App `ui://` resources. It also keeps one connection per server per Session open across Runs by answering Pi's repeated `initialize` from the cached handshake. A connection is never shared between Sessions, Workers, or forks, and connecting never blocks: a Run's Pi session connects its enabled servers in the background, as Pi does, and only a server with tools declared to the model can delay a message, for at most 1.5 s; since the 2026-10 amendment below that is only a server whose MCP App tools are already known when the Run starts. A Run with no server turned on waits only for the one-time file migration of a project not yet migrated, or one retrying after a failure (Host start migrates the projects it knows; the migration shares a queue and lock with the sign-in migration's short passes), and reads no vault secret until Pi connects a server. Once per Host process, the first Run with a server on also waits until the Host has read the login shell's environment (at most 5 s per shell it tries) and moved that scope's pre-upgrade sign-ins, so servers start with the user's `PATH` and are not reported signed out while the keychain is read. Warm connections are bounded, because keeping them forever leaked memory: a measured install held 9 full copies of four `npx`-launched servers (about 700–900 MB per Session that had run a turn, about 60 GB at worst) since connections were only closed after a settings, auth, or vault change. A Session's connections close after 5 minutes without a new Run (the timer is cancelled when a Run starts), immediately when the Session is archived or deleted, including a Worker archived by cleanup, and when the Session Host stops. The number of Sessions holding warm connections is capped, and the least recently used Session's connections close first. Stdio servers launched through a package runner (`npx`, `pnpm dlx`, `bunx`, `uvx`) have their whole process tree, including the runner wrapper, terminated on close.
- **Configuration files.** Global: `~/.pi/agent/mcp.json`, then `~/.openwaggle/mcp.json`. Project: `.mcp.json`, then `.pi/mcp.json`, then `.openwaggle/mcp.json`. For the same server name, project beats global and a later file beats an earlier one. Pi's override-only entries (no `command` or `url`) work in any higher-priority file. Every file uses Pi's entry format. A vault secret reference is allowed only in `.openwaggle` files and is resolved before Pi sees the config.
- **Writes.** A change to an existing server is saved to the file that defines it. A new server goes to OpenWaggle's file for its scope unless the user picks another file of that scope. A per-project switch on a global server always goes to a project file, never a global one: the project's existing override entry for that server if it has one (for example in `.pi/mcp.json`), otherwise `.openwaggle/mcp.json`.
- **No trust layer.** Adding a project to OpenWaggle is the only trust decision, matching Pi's single project trust (OpenWaggle never sets Pi's `projectTrusted`, which defaults to trusted). Per-server trust, trust tiers, trust records, capability grants, and "MCP off globally by default" are removed. The curated catalog becomes a one-click install of an ordinary entry.
- **No stdio sandbox.** Servers launch exactly as Pi launches them. Nothing else in OpenWaggle is OS-sandboxed (the agent's `bash` runs with the user's permissions and YOLO is the default access mode), so an MCP-only sandbox protected one door while the main one stayed open, and it broke servers that work in Pi. Ask for Approval still covers every MCP and codemode child call through the `tool_call` hook. Real isolation, if wanted later, is one sandbox for `bash` and MCP together.
- **Codemode and tool search replace the gateway.** The `mcp` gateway, `mcp_run`, capability handles, and per-turn handle snapshots are removed without aliases. Codemode is on by default in every Session (not only with MCP): OpenWaggle adds it through `+codemode` in the default tools, leaves `codemode.mode` at Pi's default `on`, and the user can turn it off. This deliberately reverses ADR 0013's rule that orchestration never runs in a JavaScript VM: Pi's QuickJS sandbox has no Node, filesystem, network, or timer access, and every child call passes the same approval as a direct call.
- **Removed MCP features** that Pi does not have and that cannot be carried on the transport layer: MCP Tasks, the Event Inbox, and Remote Skills. Protocol revisions Pi's client does not negotiate, newer than `2025-11-25` or older than `2024-11-05`, are unavailable until Pi adds them.
- **One-time silent migration.** Unchanged entries previously imported from a Pi file are removed from OpenWaggle's file, so the live Pi entry takes over. `directTools: true` becomes an override-only `exposure: "direct"` entry, so the file says what it said before; since the 2026-10 amendment below, OpenWaggle runs that `direct` as `codemode`. Edited or orphaned copies stay, with OpenWaggle-only fields converted or removed. Every server stays as on or off as it was, for every project OpenWaggle knew when it upgraded (settings and Sessions' projects): where the new merge would differ, the migration writes an `enabled` override into OpenWaggle's global or project file. A backup is kept and the user is not prompted.
- **Pi sessions are discovered, not imported.** Pi sessions whose working directory is inside an OpenWaggle project appear in its sidebar, load when first opened, and continue in the same Pi session file. The file is re-read before a Run if it changed outside OpenWaggle; there is no cross-application locking. A discovered session continues the way `pi --resume` would: its Runs work in the folder the session ran in when that folder is inside the project (the Workspace stays the project), with the model Pi's branch selection names (a virtual model the branch switched to holds over the physical models that answered) and the branch's last thinking level, or, when the branch never changed it, Pi's `defaultThinkingLevel` for the session's folder (project settings over global ones), clamped to what the model offers. Its title follows the session's latest `/name` until the user renames it in OpenWaggle. Without a `/name`, it is titled like a Session started in OpenWaggle ([ADR 0043](0043-generated-session-titles-follow-t3code.md)): its first user message gives the Provisional title, and a Title model request replaces it when that message is less than a day old, so discovering years of `pi` history never sends a burst of requests. The first user message is found wherever it is in the file, since Pi records the whole system prompt, with every tool schema, before it. A discovered Session still titled "New session" takes its title from the file once the file has a first user message. OpenWaggle never rewrites a discovered file to fit its read model: because a `pi` CLI fork keeps its source's entry ids, a discovered session's nodes are its entry ids under a per-Session prefix, translated back at the Pi boundary (an amendment to [ADR 0041](0041-forked-sessions-get-their-own-pi-entry-ids.md)). Viewing a discovered file is read-only: the projection, the context meter, and snapshots read an in-memory copy of its entries, with no extensions bound, so nothing reaches the file. The first Run continues it through Pi, which upgrades an older file format as `pi` would.
- **Continuing a session the `pi` CLI wrote last.** When the desktop user sends from the composer in a Session whose Pi file's latest prompt came from outside OpenWaggle (a discovered session nobody continued in OpenWaggle yet, or one `pi` was used in after OpenWaggle's last Run), OpenWaggle asks whether to continue it in OpenWaggle or keep running it in pi, because nothing locks the file between the two programs. Keep running it in pi opens the Session's terminal in the session's folder with `pi --session <file>` typed but not run, and keeps the draft. The answer can be remembered per project; it is the user's own preference, kept in their app settings and never in `.openwaggle/settings.json`, so each person on a project chooses for themselves, and it is changed in Settings > General. Only the composer asks: agents, the CLI, and queued Follow-ups start Runs as before, since the choice is one person's.
- **Where Pi sessions are looked for.** In the directory the `pi` CLI uses for the project: `PI_CODING_AGENT_SESSION_DIR`, then the `sessionDir` setting of the project's `.pi/settings.json`, then of Pi's global settings (a relative directory is taken from the project folder, and `~` is the home directory), otherwise one folder per working directory under `<agent dir>/sessions`. Pi reads `.pi/settings.json` only in the folder it runs in, so `pi` run in a folder inside a project that names its own `sessionDir` still uses the default per-folder directory; both are searched. Sessions OpenWaggle creates go to the project's directory, so `pi --resume` finds them.
- **Deleting and removing.** Deleting a discovered Session removes it from OpenWaggle and records its file as dismissed, so it is not listed again; the file stays. Removing its project deletes the project's Sessions without dismissing their files, so they are listed again if the folder is added back. While a project is removed, discovery stays out of it: the desktop app pauses discovery for the project before it reads the Sessions it deletes, discovery checks the pause before each Session it creates and inside the transaction that attaches the file, and the removal stops if the project still has a Session after the deletions. A project being removed still owns the sessions in its folders, so a nested project's sessions are not listed under the enclosing project until the removal is done; afterwards the enclosing project lists them, as `pi` does, and the removal dialog says so. When a discovered Session's Pi file is deleted outside OpenWaggle and its folder still exists, OpenWaggle removes the Session; it keeps it, with a notice, when a fork or Worker depends on it. Sessions OpenWaggle created are deleted with their files, as before. A Session discovery created but could not attach a file to is deleted while it is still empty.
- **Everything else in the Pi coding agent is supported in v1**, including virtual models (with the routed model shown, and the context meter using the limits of the model that answered), cache warming, image and classifier models, mid-conversation system messages, and new sign-in methods. Terminal-only features count as supported when the GUI offers the same capability. `pi-waggle` supports them literally.
- **Pi Durable is outside v1.** It is a developer library with nothing for a user to carry. OpenWaggle's later relationship to it is a client that attaches to and steers Pi Durable apps, not a replacement for the Pi coding-agent kernel.
- **The UI may name Pi for Pi-owned resources**, such as Pi's files, sessions, settings, and ecosystem ("Pi, all projects", `~/.pi/agent/mcp.json`); it still never names Pi as the runtime doing something.
- **Release gate.** All of this lands on `main` before the v1 RC, delivered as beta builds. Pi versions follow the existing 7-day minimum release age, and the version on `main` at RC is the one v1 ships with.

## Considered Options

- **Keep OpenWaggle's MCP client and imitate Pi's names and exposure model.** Rejected: parity would be maintained by hand on every Pi release, and differences would creep in.
- **Run Pi's MCP with no OpenWaggle additions.** Rejected: it would lose MCP Apps, sampling, elicitation, the vault, hardened HTTP, automation-safe sign-in, and connections that survive between Runs, all of which fit Pi's plug-in points.
- **Reconnect every server on every Run.** Rejected: 10–15 s cold connects per message, and a stateful server would lose its state within one conversation.
- **Adopt Pi Durable as the kernel.** Rejected for v1: it replaces the kernel and the session format just before the v1 user-data promise, on an API marked experimental.

## Consequences

- MCP Apps, sampling, and elicitation depend on intercepting the transport underneath Pi's client. A change to Pi's client behaviour can break them; covering them with tests against Pi's real client is mandatory on every Pi upgrade.
- Parity is mostly one-way by default: everything configured for Pi works in OpenWaggle, but servers created in OpenWaggle go to OpenWaggle's files unless the user picks a Pi file.
- Tool names change to `mcp__<server>__<tool>`. They are model-facing and not a v1 Covered surface.

## Amendment (2026-10): OpenWaggle runs `direct` MCP exposure as `codemode`

Measured across real Sessions, direct MCP tool schemas were about 22k tokens on every model call (four common servers, up to 91 tools), and the model used them in 0.2% of calls. Every Worker paid it too. The decision to keep `direct` meaning direct "so behaviour does not change" is revised:

- **`direct` runs as `codemode`** in OpenWaggle, for a server's `exposure` and for every `toolExposure` entry, for every server: Pi's files, OpenWaggle's files, `.mcp.json`, servers added from the catalog or the MCP Registry, and servers Pi extensions register. `deferred` and `hidden` keep their meaning. The model reaches those tools from codemode scripts (`searchTools()`), and the `mcp_servers` section lists the server, as for any codemode server; codemode is activated for them as Pi activates it for codemode servers.
- **Exception: tools that open an MCP App** (`_meta.ui.resourceUri`) stay declared to the model, so the model calls them itself and the App shows under that call. Pi drops a tool's `_meta`, so App tools are known from the `tools/list` results the transport layer sees. Those known when a Run starts (from the Session's earlier Runs, or the last listing of the same server) are given to Pi as `direct`; one first listed during a Run is declared when Pi registers it, from the next request on. A hidden or deferred App tool keeps its exposure.
- **No file is rewritten.** Pi's files keep their meaning for Pi: the `pi` command still declares `direct` tools. The OpenWaggle and `pi` views of the same file therefore differ on this one value, deliberately.
- **Settings > MCP offers codemode or hidden.** A file-level `direct` shows as codemode, with no warning or notice; the user does nothing. A file-level `deferred`, which Settings no longer offers, is listed while it is the current value. Choosing codemode saves `codemode` (Pi's default, so a full entry drops the key).
- **Connecting.** Only servers with tools declared to the model are waited for before a message (at most 1.5 s, `MCP_STARTUP_WAIT_MS`). After this amendment that is only a server whose App tools are known when the Run starts; every other server never delays a message.
- **OpenWaggle's own rarely used tools are found on demand**, the same way and with no setting: `preview_*` (all of them, `preview_status` included), `project_actions`, `source_control` and `openwaggle_docs` are registered with Pi's `deferred` exposure in an `openwaggle` tool namespace. They are not declared until `tool_search` loads them (activated at session start) and are callable from codemode scripts at any time. One short line in the rules names each family, and loading a tool never changes the system prompt. Pi's `<docs>` section becomes one line pointing at `openwaggle_docs`, which carries Pi's documentation as source `pi`. The fail-closed browser-preview access setting still withholds the preview tools entirely.

Considered: a prompted one-time suggestion to switch (the research's first proposal), a per-server token-cost warning in Settings, and an automatic threshold like Claude Code's. Rejected: each leaves the cost in place for every user who does not act, and Workers multiply it.
