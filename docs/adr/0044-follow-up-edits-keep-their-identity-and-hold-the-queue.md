# Follow-up edits keep their identity and hold the queue

Status: accepted

Date: 2026-10-01

## Context

A queued Follow-up message could only be withdrawn, reordered, or steered. Users wanted to fix a queued message without losing its place, by reopening it in the composer with its text, attachments, and any skill or Waggle invocation. Editing in the composer takes long enough that the active Run can settle meanwhile, and the queue would then deliver the old text. A queue that had a message out for editing would no longer deliver what the user meant, in the order the user set.

Two shapes were considered:

- **Withdraw and re-queue.** The renderer withdraws the item, the composer edits it, and saving queues a new Follow-up and reorders it back into place. This needs no new Host operation, but it changes the Follow-up identity that callers, retries, and Delegations rely on, and the queue can deliver the items behind it, or the item itself, between the steps.
- **Edit in place under a Host hold.** The Host replaces the Follow-up intent snapshot while keeping its identity and position, and stops delivery at that item until the edit ends.

## Decision

A **Follow-up edit** replaces a pending Follow-up message's intent snapshot in place: same Follow-up identity, same queue position, revision-guarded like every other queue mutation. Only the user who queued a message can edit it. Message provenance never changes, so another caller's Follow-up can be reordered or withdrawn but not rewritten.

An edit runs under a **Follow-up edit hold**. Beginning an edit asks the Host to hold the item. While a hold exists, queue delivery stops at the held item, so nothing from that item onward starts, including at Run settlement and on queue resumption. The held item can still be reordered, and the hold travels with the item. Saving the edit or cancelling it releases the hold. The Host owns the hold as a lease bound to the desktop window that began it: the hold survives switching Sessions, which shows it as waiting on the user's edit, and the Host releases it when that window closes or reloads, or the app's Host connection is lost, so an abandoned edit cannot block a queue forever.

Thinking level and authorization are not part of an edit. They are Session state applied when a Run starts, like the model, and moving them off messages is a separate change.

## Consequences

The queue gains a delivery-blocking state that is neither a pause nor needs-attention. Every delivery path has to respect it: settlement scheduling, explicit resumption, idle message submission, and steering promotion of the held item, which is refused while held. A held head item means an idle Session with a non-empty queue that will not start on its own, so a new message submitted then is queued behind it, the same as with a paused queue.

Two related rules ship with this change:

- When a Steering message has been accepted but not yet incorporated (an **Undelivered steering message**) and its Run is stopped, it returns to the front of the Follow-up queue instead of being lost with Pi's cleared steering queue.
- When Pi starts incorporating a user message, the Host sends that message's display content with the event, so the transcript shows a Follow-up as soon as its Run starts and turns a steered bubble from queued to delivered at the moment the agent reads it.

## Implementation notes

The hold is lease state, so it lives where leases die with the Host: connection-scoped SQLite `TEMP` tables on the Host's single connection. That keeps holds transactional with the queue state they block without a migration, and a Host restart releases every hold; startup recovery then pauses each running queue as Host loss. A lease is counted in Host sweeps, not clock time: a hold expires after six 5-second sweeps without a renewal, and no sweep runs while the machine sleeps, so sleeping cannot expire an open edit on any platform (Windows' monotonic clock keeps counting across sleep). The desktop main process renews the holds of each window every 10 seconds and on wake through an unjournaled Local UI command, and cancels a window's holds when it closes, reloads, navigates, or crashes, or when the Host reports a hold lost. A window that re-adopts an edit this user holds first confirms it with the Host and then takes over renewing and releasing it. While the Host drains it still renews holds and accepts cancels, which release a hold without starting the next Run. When the desktop app or its Host connection is gone, renewal stops and the lease expires; an expired hold stops blocking at once, and a Host sweep then cancels it so its Session can deliver. The Follow-up edit operations need Local Session protocol revision 21 and are offered only to the desktop app; the Sessions tool, CLI, and MCP do not offer them.

An idle Session must never keep a queue that could deliver: after every accepted queue change and every Run settlement the Host starts what the queue can deliver now, and pauses the queue if it cannot admit that Run. A save names the queue revision its edit began at, because while a Follow-up is held only its editor can change it; anything else that changes it ends the hold. A Worker whose Run completes while its queue's next Follow-up is held is not done yet: its Delegation settles after the Run that Follow-up starts, or, when the edit ends without one (the held Follow-up was withdrawn, or the queue paused), right after that queue change. That deferred settlement is lease state too and is lost on a Host restart. An explicit Waggle is a run-now command with no queued outcome, so the desktop app queues a Waggle as a Follow-up while a hold waits instead of letting it overtake the held message.

Thinking level and the Run authorization override moved off messages in the same Local Session protocol revision 21. A Follow-up intent carries neither, and stored values on queued items are ignored on load. The Session thinking level lives in the Session's execution profile next to its model; a Run reads it when it starts, clamps it to the model, and Pi records it as a `thinking_level_change` entry. The desktop user changes it through `sessions:set-thinking-level`, which also persists Pi's global default. Model and thinking changes are checked in the same SQLite transaction as the Session's active Run and refused with `session_run_active` while one is starting, active, or stopping. Callers may send a thinking level on create, launch, or spawn, and an override on launch or spawn; both are also accepted on a `message` or `start` that starts a Run on an idle Session, where the level is written in the same transaction that admits the Run. Any command that would queue, steer, or replace is refused with `thinking_level_requires_idle_session` or `run_authorization_override_requires_idle_session`, including through MCP. A caller's thinking level never changes Pi's global default, and extensions cannot set it. New Sessions start from Pi's global default only: a project-level Pi `defaultThinkingLevel` is ignored, so a draft pick always sticks. When the default changes, the Host publishes a sessionless `default-thinking-level-changed` event so every window's draft picker refreshes. On the first Host start after the upgrade, the desktop pick that earlier versions kept as app state becomes Pi's global default when Pi names none, and each existing Session's stored level becomes the last `thinking_level_change` on its active path, the level its Runs had been using, so no Session changes level on its next Run.

With no override on a queued item there is nothing to re-authorize, so the `authorization_ceiling_changed` block and `queue-update-authorization` are gone. A Follow-up held as `profile_revoked` or `authority_changed` is resumed instead by the desktop-only, revision-guarded `queue-adopt`: the desktop user becomes its caller, its original writer stays as `authorCallerId` for provenance and as the owner of its attachments, and it can no longer be edited. Its Run's reach and ceiling follow the user, since adopting is the user choosing to send it as their own. Every needs-attention path also pauses the queue, so adopting the last Follow-up that needs attention resumes a queue that attention paused (no pause reason, or `profile-revoked`) in the same change, never one the user or a failed Run paused, and an idle Session then starts its head under the usual admission checks. This supersedes in part ADR 0030's re-authorization rule and ADR 0042's author-checked reach.
