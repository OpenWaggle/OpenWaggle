# Session agents reach every project, and each Session gets a private scratch directory

Status: accepted

Date: 2026-09-29

Supersedes in part: [ADR 0013](0013-adopt-first-party-mcp-integration.md), its Session Control rule that internal desktop agents discover same-workspace sessions by default and need a separate grant to read or message across projects. [ADR 0030](0030-adopt-single-local-session-host.md) is refined: its `current` launch Workspace now has a defined meaning when the target project is not the caller's.

Two concurrent gosafe Sessions both ran `git push ... > /tmp/push.log 2>&1`. Their pre-push hook output interleaved, and one Session concluded it had pushed a branch it never touched. The same Sessions kept Terraform state holding a database connection string under fixed `/tmp` names. Every tool process shared one temp directory and nothing told the model so.

The same gosafe Session then tried to hand the bug to an agent in the OpenWaggle repository. `list` with the other `projectPath`, `launch`, and `create` all returned `An error has occurred`, and `catalogScope: all` showed only gosafe Sessions. The Host had pinned a root Session agent's target scope to its own project, and the refusal was an Effect tagged error without a message, which Effect renders as that placeholder. A human had to copy the report between windows.

## Decision

### Cross-project reach

- **A root Session agent reaches every project in the catalog when both its authority and its Run allow it.** Its own authority must come from the local desktop user, or from a CLI profile whose live scope is catalog-wide (`all`), and any stored authority snapshot must be catalog-wide too. The origin is read from the caller id, never inferred from missing data. The Run must also have been started by the desktop user, by a catalog-wide profile, or by another agent whose Run passes the same check, followed back through at most eight agents. Capabilities and the Authorization ceiling still decide what it may do, exactly as inside one project. The project was never a security boundary against a same-user shell (ADR 0030), and it blocked the one thing the maintainer requires: agents in different repositories talking to each other without a human courier.
- **The Run check closes a confused-deputy path.** Without it, a CLI profile or transient MCP caller limited to project A could send a Follow-up to a desktop Session in A and have that Session list, read, steer, or archive Sessions in project B, then read the results back from A. A Queen Run that a Worker's Follow-up started does not reach every project either; a Run the desktop user starts does.
- **Input into a running Run must come from a caller with the same reach.** A steer, a promoted Follow-up, or an answer to a pending request or approval from a caller that does not reach every project is refused with `target_scope_denied` when the Run does; that caller can still send a Follow-up, which starts its own Run under its own reach. A promoted Follow-up is also judged by its author. A Follow-up re-authorized by someone else (`queue-update-authorization`) keeps its author as `authorCallerId`, and the Run it starts reaches every project only if both do. Reports and Delegation results still reach a running Run. They are content, not commands: the Host labels them as untrusted peer context that cannot direct actions beyond the reporter's own reach, and they carry the same prompt-injection risk as a file or web page the agent reads. The Host does not track information flow through content; it enforces reach on the commands a caller can issue.
- **An agent's Authorization ceiling is also bounded by its Run's initiator.** A Session agent acts under the narrowest of its Session's ceiling and the ceiling of whoever started its current Run (and wrote it, for a re-authorized Follow-up), followed through other agents. An ask-for-approval profile that messages a yolo Session therefore cannot have that Session's agent start yolo Runs. An initiator the Host cannot identify durably, such as a transient MCP caller, counts as ask-for-approval.
- **Re-authorizing a queued Follow-up is an authorization change.** `queue-update-authorization` needs `sessions:authorization` as well as `sessions:queue`, so root agents, which lack it by default, cannot clear another caller's revocation or authority pause.
- **Explicit Waggle Runs stay in their project.** They have no `session_runs` row to trace, so the Run check fails closed for them.
- **Reach follows durable rows.** The chain is read when the tool is called, not frozen when the Run started, so a narrowed or revoked profile takes effect at once. If the Session whose Run launched another root is deleted, that launched root's later Runs are judged by who started them, and its Follow-ups from the old Run stop reaching other projects.
- **Every project means every project OpenWaggle knows.** A catalog-wide Session agent may launch or create Sessions only in a project that already has a Session or a Workspace in the catalog, named by its exact absolute path. Otherwise a prompt-injected agent could start a Session in any directory on disk and load that directory's instructions and skills.
- **Narrower authority stays narrow.** A root born from a named CLI profile is pinned to its own project, even when the profile lists several. Workers keep their exact derived scope and never gain project-wide or catalog-wide reach from this rule. A root that an agent launched before this decision keeps the single-project scope stored in its authority snapshot.
- **One function decides, in both places.** The Sessions tool (when the agent calls it) and queued Follow-up delivery (when a Follow-up it sent is delivered later) both use `sessionAgentRunReachesEveryProject`, so a catalog-wide root's cross-project Follow-up is delivered rather than paused as `authority_changed`, and the two checks cannot drift apart.
- **A Worker's stored authority never reaches every project.** When a catalog-wide Queen's Worker stores an authority snapshot, it names the Worker's project instead of `all`, so a later feature that promotes or detaches a Worker does not inherit catalog-wide reach.
- **Every existing action works across projects**: discovery, read, report, Follow-up, launch, and create, and also steer, replace, interrupt, archive, unarchive, rename, hand off, fork, export, event waits, and Delegation review of another Hive's Queen. No capability is added: respond, approve, and authorization changes remain excluded from root agents by default.
- **A cross-project launch or create resolves its Workspace in the target project.** `local` and `new-worktree` work as usual. An omitted or `current` Workspace uses the target project's local checkout, because the caller's own Workspace does not exist there; this is the rule #252 gave CLI callers outside every Workspace.
- **A refusal states its reason.** Authorization refusals name the code and what is missing, for example `Session command refused (capability_denied): ... Missing capabilities: sessions:create.` A cancelled command says so. Other failures are described by #252's server describer: the message of an error that has one, or else its tag, code, operation, and cause chain, where a bare-object cause shows only its identifying fields (`reason`, `projectPath`, `sessionId`, `workspaceId`, `runId`). The result is redacted and bounded. The Sessions tool and the Host's command error frames use the same text. A failed handshake always returns one message, `Local Session authentication failed.`, throttling included, so a client without a credential cannot tell whether a profile exists or was revoked; the Host log keeps the failure code.
- **The tool schema names per-action required fields.** The provider schema must stay a flat object (issue #218), so a field such as `objective` is described as `Required for launch, spawn.` instead of being marked required at the root.

### Session scratch directory

- **Each Session gets its own scratch directory**, created owner-only (0700): `<base>/ow-scratch-<uid>/<profile>/<session>`, where `<profile>` is 8 hex characters of a hash of the Host's user-data directory and `<session>` is 12 hex characters of a hash of the Session id. Every OpenWaggle profile runs its own Host, so the profile level keeps one Host from touching another's directories. The base is the user temp directory when the resulting path fits in 56 bytes (Linux, or a short custom `TMPDIR` chosen because `/tmp` is `noexec`), and `/tmp` otherwise. macOS limits a Unix socket path to 104 bytes and tools such as `tsx` and Chromium bind sockets under `TMPDIR`; the macOS per-user temp directory plus a Session id already exceeded that. Every level is refused if it is a symlink, a non-directory, or owned by another user. On Windows the directory sits under the user temp directory, which is private to the user by default; OpenWaggle does not tighten its ACL. Workers get their own directory rather than sharing the Queen's.
- **Shell tools receive it as `TMPDIR`, `TMP`, and `TEMP`.** It is applied after any captured Workspace preparation environment, so a setup script cannot point tools back at the shared temp directory. Project action runs and MCP servers do not get it. The Host's own temp directory is exported as `OPENWAGGLE_HOST_TMPDIR`: an `openwaggle` process started from an agent shell (the CLI, or `pnpm dev`) moves its own `TMPDIR` back to it at startup, and the Session Host socket fallback path is resolved from it, so the CLI still finds its Host and a nested Host's temp files do not vanish when the Session is archived.
- **The Host-written system prompt names the absolute path** next to the visualization directory line and tells the model not to write fixed names under `/tmp`. The environment variables alone would not have prevented the incident, because the model typed a literal `/tmp/push.log`. Images the agent embeds from its scratch directory, such as `$TMPDIR/electron-qa-evidence/final.png`, are captured as Session resources like images in the workspace; the Run holds the directory until that capture finishes, and the GUI and Host derive the same profile namespace from the user-data directory.
- **Archiving or deleting a Session removes the directory.** A Run holds the directory while it runs, so archiving a Session mid-Run defers the removal until that Run ends, and unarchiving before then cancels it. A removal still in flight completes before a new Run recreates the directory, and one failed removal does not cancel the next. At startup the Host removes directories of its Sessions that were deleted or archived while no Host ran, skipping any in use by a Run or used within the last hour, and removes other profiles' namespaces that no Run has used for a week, such as those of throwaway dev profiles.
- **Failure to create it does not block the turn.** The Host logs a warning and the tools keep the Host temp directory, which is the old behaviour.

## Consequences

An agent in one repository can list, search, read, report to, send Follow-ups to, launch, and create Sessions in another repository without sharing a Hive. It can equally steer, interrupt, archive, fork, and export them, so a prompt-injected root agent in one repository can act on every project this user has. Sessions a catalog-wide root launches, creates, or forks inherit that reach through their authority snapshot, and their first Run is started by that root, so it passes the Run check; Workers it spawns do not. Users who want a project boundary for an external agent use a named CLI profile scoped to that project; messaging or steering a desktop Session does not let that agent escape it through the Sessions tool, because its Follow-ups start project-scoped Runs and its steers into catalog-wide Runs are refused. A yolo shell in that Session, or the local-user CLI credential, still reaches the whole machine, as ADR 0030 records. A Queen that a Worker's report wakes stays in its project for that Run. OpenWaggle does not warn about fixed `/tmp` paths in shell commands; the prompt instruction and `TMPDIR` cover the observed failure, and a heuristic command scanner is left for later if models keep ignoring it.
