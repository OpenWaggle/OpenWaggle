# Pinned Sessions Stored Per Pin, Not As A List

Status: accepted (design)

A **Pinned session** is stored as one database row per pin — session id, `pinnedAt`, and a `sortKey` that carries its position in **Manual order** — rather than as a single ordered array of session ids. The row-per-pin shape is chosen so a future cross-device sync can merge two devices' pins individually instead of discarding one device's ordering wholesale.

## Context

Pinning needs to persist two things: *which* sessions are pinned, and *what order* the user dragged them into. The obvious shape is one ordered array, `pinnedSessionIds: SessionId[]`, where membership is position — and OpenWaggle already has that exact pattern in `Settings.recentProjects` (an ordered array of paths, dangling entries tolerated, sanitised on read). It was the initial recommendation during design.

Two facts moved the decision.

**Pins are intended to sync across devices.** The maintainer raised remote sessions from another device as a near-term direction, and wanted pins ready for it rather than retrofitted. That makes the persisted shape a merge question, not just a storage question.

**Session identity is already portable.** `createSession` mints the local id directly from Pi: `SessionId(input.piSessionId)`, and `sessions.pi_session_id` is `NOT NULL UNIQUE`. The same Pi session on a second device therefore carries the same id, so a pin needs no new identity scheme to travel — only a mergeable representation.

An array is a single opaque value. Two devices that each reorder their pins produce two whole-list writes with no common structure to reconcile: a sync can only pick a winner, and the loser's ordering is silently destroyed. Because **Manual order** is the one part of this feature the user authors by hand, losing it is the most expensive failure the feature has.

## Considered Options

**One ordered array of session ids.** Simplest locally: membership *is* order, a reorder is one write, gaps and duplicates are impossible by construction. Rejected because it cannot merge — and because it lives outside the sessions table, so deleted sessions leave dangling ids that need sweeping.

**Per-session `pinned` boolean plus a `pinnedOrder` integer** on the existing `session_tree_ui_state` row. Gets `ON DELETE CASCADE` for free, but describes one global sequence as N independent integers: two rows can claim the same position, deleting a pin leaves a gap, and reordering five rows is five writes that must all land or the list is scrambled. It also spends a bulk write on every drag.

**One row per pin with a fractional `sortKey`** (chosen). Membership and order live together per pin, so:

- a reorder or an insert-between writes exactly **one** row, by giving it a key between its new neighbours
- position integrity needs no renumbering pass — there is nothing to keep contiguous
- `session_id` is a foreign key with `ON DELETE CASCADE`, so deleting a session removes its pin with no application code
- a future sync merges pin-by-pin, using `pinnedAt` to break ties, instead of choosing a winning device

## Consequences

`sortKey` is a string, not an integer, and must be generated by a fractional-index scheme (a key strictly between two neighbours). This is the surprising part of the schema and the reason this ADR exists: a reader expecting `position INTEGER` will be tempted to "fix" it, which would reintroduce renumbering writes and destroy the merge property.

The **Pinned sort** choice (`Manual` / `Recent` / `Oldest` / `Name`) is deliberately *not* stored here. It is a view preference with no cross-device meaning and no lifecycle, so it lives in renderer localStorage via Zustand `persist`, alongside comparable view state such as `diff-scope-store`. The split is intentional: **Manual order** is user-authored data, the **Pinned sort** is a local preference.

Sync itself is explicitly **not** built by this decision. The commitment is only that the persisted shape does not have to change when it is.
