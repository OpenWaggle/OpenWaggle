# Adopt A Single Local Session Host

Status: accepted

OpenWaggle uses one per-user local process as the authority for live agent runs and cross-session control. Electron, CLI, MCP, and internal agents share that authority instead of coordinating through renderer memory, direct database writes, or loopback MCP.

## Context

OpenWaggle currently creates live Pi `AgentSession` instances inside the Electron main process. Renderer updates work because main broadcasts agent events through Electron IPC, but a separate CLI process cannot reach those live handles or notify open windows. The existing MCP CLI can coordinate selected filesystem transactions with process locks, but locks do not provide live steering, subscriptions, ordered events, or ownership of long-running work.

OpenWaggle does not currently have Codex-style subagent tool capabilities. The existing externally served MCP `openwaggle_sessions` tool can list, create, read, message, cancel-and-restart under its current `steer` operation, wait, interrupt, and organize selected sessions through separate hosted-task and metadata paths. It is neither injected into an ordinary OpenWaggle Pi agent nor backed by a single owner for desktop and headless runs, durable Follow-up queues, or live GUI synchronization. Pi does, however, provide the native extension-tool registration point needed to add an OpenWaggle-owned tool while preserving Pi's agent-loop events.

The product requires agents and external agentic tools to create sessions, start durable work, submit follow-ups, steer specific active runs, wait, interrupt, export, and continue operating when the GUI is closed. Multiple processes independently opening persistence cannot safely provide those semantics.

OpenWaggle is still alpha, so preserving old internal schemas and mutation contracts is less valuable than completing one coherent cutover. The migration may be breaking, but it must preserve canonical user conversation data and fail without corrupting the previous database.

## Decision

Codex behavior is the normative parity baseline for session discovery, multi-agent spawning, workspace sharing and worktree isolation, lifecycle, steering, follow-up delivery, CLI coordination, and visible activity. OpenWaggle-specific capabilities may extend that surface, but they do not silently replace a Codex default. Any unavoidable Pi or existing-domain incompatibility is documented explicitly and receives a parity-focused acceptance test.

OpenWaggle introduces a single per-user **Session Host**. It owns the first-party Session Control application service, live Pi runs, durable Follow-up queues, persistence mutations, capability enforcement, and an ordered live event stream.

The Session Host ships behind a one-time full cutover migration rather than phased backfill or dual reads. Before any host client is accepted, a migration bootstrap builds the complete target database beside the current `openwaggle.db`, copies and transforms all canonical session data, and creates the required Workspace, binding, lineage, turn/item attribution, queue, operation, idempotency, authorization, lexical-search, semantic-embedding, vector-index, and audit structures and indexes. Stable Session, Pi-session, node, branch, and checkpoint identities and canonical transcript content are preserved. Existing sessions become lineage roots with empty Follow-up queues; historical runs whose exact boundaries cannot be recovered receive explicitly synthetic turn identities. Local sessions are grouped into local Workspace resources by recorded project path, sessions sharing a recorded worktree path bind to one managed Workspace resource, and each unmaterialized legacy worktree plan receives a pending resource. A missing recorded worktree remains missing and requires attention rather than being silently rebound.

The selected embedding model and vector runtime ship with OpenWaggle so migration is deterministic and works offline, accepting a larger installer and a potentially lengthy first launch for large histories. The bootstrap validates foreign keys, uniqueness, source-versus-target row counts, transcript high-water marks, exactly-one Workspace binding per migrated session, lexical index consistency, semantic coverage, model revision, and vector-index integrity. Only after validation and durable close does it atomically install the target database and retain one pre-cutover recovery copy. Failure or cancellation leaves the previous database untouched, refuses to open the partial target, and does not mark the migration complete. After success, the migration ledger records the schema, model, and vector-index revisions; ordinary launches never repeat the cutover, new or changed discovery text is embedded incrementally, and no legacy database, hosted-task, queue, or Workspace fallback remains in application code. A future model or index replacement is another explicit one-time revision migration rather than an implicit rebuild on every launch.

Implementation may use a development-only internal gate and isolated data roots while incomplete, but delivery is one integration pull request and one alpha release. The merge removes the gate and old orchestration code and includes the target schema, full migration, Session Host, Session Control core, Pi-native Sessions tool, GUI, CLI, external MCP adapter, Agent-definition authoring and import, user and developer documentation, performance validation, deterministic CI, packaged Electron QA, and live-provider release evidence. Reviewable commits and internal vertical slices may organize that pull request, but no partial slice ships, migrates user data, or remains behind a user-facing feature flag. Follow-up issues cannot defer an agreed cutover capability or parity acceptance criterion.

The pre-cutover database is retained as a recovery copy until the user explicitly removes it, but no normal runtime path reads or writes it. `openwaggle recovery status` reports active and recovery database identity, schema compatibility, timestamps, and sizes. Explicit `restore-pre-cutover` requires the Session Host to be stopped, an exclusive lock, and human confirmation or an equally explicit non-interactive confirmation flag. Before replacing the active database, recovery preserves the current Session Host database as a separate timestamped artifact and warns that post-cutover sessions and mutations will not appear in the restored database. A host crash, run failure, validation error, or application crash never triggers automatic restoration, because that could discard valid new work. OpenWaggle does not intentionally launch an older runtime against the new incompatible schema, and deleting the recovery copy is a separate explicit irreversible operation that names its exact path.

The host starts on demand when the first GUI or CLI client needs it and remains available while accepted work is active. A packaged installation and development checkout resolve separate versioned endpoints under their configured user-data roots so incompatible or unrelated runtimes do not share a host accidentally.

Out-of-process clients use an authenticated **Local Session transport**: Unix-domain sockets on macOS and Linux, named pipes on Windows, framed request-response messages, event subscriptions, protocol/version negotiation, canonical snapshot loading, and bounded recent-event cursors. Endpoint permissions, a per-user secret, bounded messages, stale-endpoint recovery, and explicit caller identity protect the boundary. WebSockets and a listening TCP port are not required.

Electron main is a Session Host client and forwards host events through the existing typed renderer IPC boundary. The CLI and MCP server adapters call the same Session Control commands. They never mutate live session persistence directly when a host owns it.

Codex parity is a behavioral contract, not an instruction to embed Codex App Server wire DTOs or storage assumptions in OpenWaggle's domain. Session Control defines versioned platform-neutral commands, results, events, errors, and negotiated capabilities. GUI, CLI, MCP, the internal Sessions tool, and Local Session transport are boundary adapters over that core. This keeps hot-path in-process calls allocation-light, permits efficient local framing for out-of-process clients, and lets persistence evolve independently. A future or bundled Codex App Server compatibility adapter may translate a declared JSON-RPC revision and method subset at the boundary, but it may claim compatibility only behind bidirectional conformance tests and must reject unsupported behavior explicitly. Exact Codex wire compatibility is therefore neither silently promised nor required to deliver full observable Codex parity.

The implementation adds one compact OpenWaggle-owned Pi-native `sessions` tool through a first-party adapter extension; it does not assume or wrap a pre-existing Pi or Codex subagent tool. The Pi adapter registers the tool through Pi's native extension surface and injects a capability-scoped OpenWaggle Session Control port. Pi-native tool-call and tool-result events remain the runtime source of truth. When Pi runs inside the Session Host, execution is an in-process application call rather than a shell invocation, CLI subprocess, or loopback call through OpenWaggle's MCP server.

The current external MCP `openwaggle_sessions` surface is migrated into another Session Control adapter. Its direct hosted-task, metadata, cancellation, and persistence paths cease to be a parallel orchestration authority. The tool name remains stable, and structured results declare Session Control contract version `2`. Compatible discovery, read, creation, and organization operations retain their meanings. Contract-v2 `steer` requires an expected run identity and delivers a true active-turn Steering message, while explicit `replace` performs interruption followed by a new run. A legacy steering payload that cannot prove v2 intent fails before mutation with `ambiguous_legacy_steer` and migration guidance. OpenWaggle never silently reinterprets the old cancel-and-start operation as steering or silently turns new steering into replacement.

The tool distinguishes session creation, launch, and spawning. `create` produces an idle independent root Session. `launch` atomically creates and starts an independent root, returning its Session and Run identities only after the start is accepted. Launch requires both `sessions:create` and `sessions:start`, validates them together before mutation, and introduces no redundant `sessions:launch` capability. `spawn` atomically creates and starts a child Worker, additionally returning its Delegation Contract and recording Spawn lineage. A failed launch or spawn never reports a successfully created but unintended idle Session.

Every spawn records immutable parent/child lineage and returns a non-escalating child-management grant derived from the spawn authorization. The parent can control only the authorized operations on that child, and the child receives no automatic authority over its parent or siblings. Matching the current Codex multi-agent backend, recursive descendant spawning has no separate product nesting-depth limit; every parent remains subject to its independently resolved concurrency limit, authorization, and Session Host resource admission.

OpenWaggle teaches the same lineage through a bee-domain vocabulary in both user and agent surfaces. A connected spawned-session family is a **Hive**, its one root is the **Queen Session**, and every descendant is a **Worker Session**. A Worker that spawns further Workers remains a Worker; parent and child continue to name the exact relationship between two Sessions. Session Control fields, filters, and commands retain root/parent/child terminology for precise interoperability, while the internal Sessions tool descriptions and agent-facing documentation explicitly map natural-language Hive, Queen, and Worker requests onto those structural operations. “Spawn a Hive of N Workers” makes an ordinary root the Queen of N direct Workers, adds N direct Workers when addressed to an existing Queen, and adds N Workers beneath an existing Worker without changing its role. “Create a separate Hive” explicitly creates a new independent root instead of extending the caller's Hive. Its initiator is recorded in operation and audit provenance but not in Spawn lineage, receives no Derived child-management grant, and may manage the new root only through pre-existing cross-session capabilities. The Queen name denotes the Hive's origin and does not imply elevated authorization or automatic command authority.

New child sessions inherit the parent's live execution profile by default, matching Codex subagent behavior. Authorized child profiles may specialize model, reasoning, instructions, and agent role, but security-sensitive sandbox, approval, filesystem, network, and credential settings may only remain equal or become more restrictive. Messaging an existing session never applies parent inheritance; the existing target resolves its own profile.

Launch uses a distinct profile-seeding rule because the new root has no parent. An internal agent launch copies the initiating Session's model, reasoning, tools, MCP, and skills when those values are omitted, but authorization resolves independently from the caller's profile and ceiling and no derived grant is transferred. GUI launch uses the selected composer execution settings. CLI launch resolves explicit flags first, then project and app-global defaults. This continuity is not Spawn profile inheritance and does not create lineage or authority.

Named Agent definitions remain optional and distinct from both Hive roles and Waggle presets. OpenWaggle does not require or prescribe implementer, explorer, reviewer, Queen, or Worker classes. Normal launch and spawn behavior is represented by an absent Agent role selection, not by resolving a built-in or stored definition named `default`: the initiating agent decides how to divide the work, records each assignment through its Delegation specification, and ordinary profile resolution supplies omitted execution defaults. Users may author project- and user-scoped definitions with arbitrary stable names, and an authorized user or agent may select one independently for each launch or spawn when a reusable specialization is useful. A selected definition contributes purpose, Agent instructions, and permitted execution-profile defaults without defining lineage or a multi-agent workflow; no definition may widen the caller's live grants.

Agents discover optional definitions on demand through bounded listing and search that returns authorized names, descriptions, and scopes rather than injecting every definition and instruction body into every Run. An explicitly requested stable name resolves directly. Definitions may narrow the exposed tool, skill, and MCP surface; narrow the existing Session Control grant through `sessionCapabilities`; select supported existing sandbox and approval modes; and supply model, reasoning, and Workspace defaults within the initiating caller's effective grants and Authorization ceiling. A definition is never an authority source and cannot make launch or spawn more permissive. Agent definitions do not introduce a second filesystem- or network-policy language: the selected existing runtime sandbox and approval mechanisms enforce those boundaries, and tool removal alone is documented as tool restriction rather than a read-only security guarantee.

Agent-definition fields have two resolution classes. Restrictions such as tool and Session-capability allowlists and sandbox or approval ceilings remain intersected with the caller and cannot be overridden by a spawn request. Preferences such as model, reasoning, and Workspace selection resolve from an explicit authorized launch or spawn value, then the selected Agent-definition default, then the configured subagent default, then parent inheritance. This deliberately differs from Codex custom-agent model precedence, where a file-set model wins over an explicit spawn value: OpenWaggle keeps reusable roles adaptable per assignment while preserving every security reduction.

The canonical custom-agent authoring format is a Markdown file with strictly validated, schema-versioned YAML frontmatter. Frontmatter carries `name`, `description`, and optional model, reasoning, tool, skill, MCP, Session capability, existing sandbox mode, existing approval mode, and Workspace specialization; the required non-empty Markdown body supplies Agent instructions. The optional `tools` field is an allowlist: omission inherits the caller's available tool surface, a non-empty list intersects named tools with that surface, and an empty list yields no tools. Agent definitions provide no denylist whose meaning could widen silently when a new tool is installed. Because session operations share one compact Pi-native `sessions` tool, optional `sessionCapabilities` supplies the equivalent operation-level reduction over the existing Session Control grant: omission inherits the caller's permitted operations, a list intersects them, and an empty list permits no Session Control operation. It never grants an operation. Definitions also have no per-definition filesystem-path or network-domain policy fields. The frontmatter name is stable identity, while a matching filename is only a discoverability convention. Parsing accepts JSON-compatible YAML only and rejects unknown fields, custom tags, aliases, includes, environment interpolation, and oversized configuration or instruction bodies. Markdown is instruction text, not executable content or trusted HTML. This follows the dominant cross-tool human-authoring convention used by Claude, Gemini CLI, GitHub Copilot, Cursor, and OpenCode while keeping Codex behavioral parity independent from Codex's TOML storage choice.

Following the cross-tool custom-agent convention, Agent instructions and the per-invocation Delegation specification are distinct inputs. The definition body supplies the reusable agent-level behavior; the Delegation specification supplies the initial task and relevant handoff context. Runtime adapters map Agent instructions to the provider's appropriate system or developer instruction mechanism and preserve the task as a separate message rather than concatenating both into one prompt. Repository instructions, skills, and platform instructions retain their normal runtime precedence, while effective tools, Session capabilities, sandbox, and approval controls remain the enforcement boundary regardless of prompt wording.

At each Run start, the Session Host adds a small authoritative Agent Session identity context. It states the Session identity; Queen, Worker, or independent-root classification; immediate parent identity and title when present; selected Resolved Agent snapshot name and scope when present; current Workspace identity, environment mode, and Working path; and the Session Control operations currently exposed to that Run. Agent-definition files and task prompts cannot forge or replace this host-authored context. It does not preload siblings, children, related transcripts, queue bodies, or Hive summaries. Agents retrieve that authorized state on demand through the compact `sessions` tool.

Matching the common subagent context model, a spawned Worker starts with a fresh conversation context containing its Agent instructions, immutable Delegation specification, explicit handoff context and resource references, repository instructions and selected skills, and host-authored Agent Session identity context. It does not inherit the Queen's message history, hidden reasoning, pending queue, or unrelated tool output. Shared Workspace state remains visible through ordinary filesystem access. Reading any additional Session history is an explicit Session Control operation subject to the Worker's own discoverability and read grants; Spawn lineage alone provides no reciprocal transcript access.

Agent-definition discovery observes file changes without requiring an app or Session Host restart. Launch and spawn resolve and validate the selected definition atomically with accepting the operation, then persist an immutable Resolved Agent snapshot containing the stable name, source scope, schema version, source digest, instructions, and effective specialization. Existing Sessions continue using that snapshot if the source is later edited, renamed, deleted, shadowed, or made invalid. A Session cannot rebind or re-resolve its own Agent role during a turn or between later turns; changing specialization requires a new launch or spawn. Later operations use the latest valid definition. An invalid current definition produces a visible diagnostic and blocks only new selections of that definition; it never mutates or disables a Session already created from an earlier snapshot.

Settings includes one Agent definitions surface for both project and user scopes. It lists definitions with scope, validity, and source provenance and supports Create, Edit, Duplicate, Import, and Delete. Editing uses schema-driven frontmatter controls and a Markdown instruction editor, but the validated Markdown document remains canonical; the GUI does not create a competing database-only representation. Agent definitions are ordinary files, like skill documents: agents may create or edit them through normal filesystem tools whenever their effective sandbox and approval settings authorize the target path. GUI and CLI mutations are convenience adapters over those files and pass through the same filesystem authorization boundary rather than a separate Agent-management grant. Editing a definition and then spawning from it still cannot escalate authority because the new Session intersects the latest definition with the spawning Session's effective grants and Authorization ceiling. Agent definitions do not create a hierarchy in the Session sidebar. Their optional selection appears only in launch and spawn controls, where it specializes the new Session without changing Hive lineage presentation.

OpenWaggle publishes the complete versioned Agent-definition JSON Schema and semantic contract with the app, CLI, repository documentation, and user-facing website. Documentation covers every field, default, inheritance and reduction rule, scope and precedence, examples, diagnostics, and version migration. Documents require `schemaVersion` and may carry a `$schema` URL for editor completion. `openwaggle agents validate` checks syntax, schema, body, model/tool/MCP/skill resolution, permission reductions, duplicate identity, and scope; `agents explain` shows the resolved source, precedence, defaults, inheritance, reductions, and diagnostics.

Foreign definitions are never auto-discovered. Canonical discovery precedence is project `.openwaggle/agents/*.md`, portable project `.agents/agents/*.md`, then user `~/.openwaggle/agents/*.md`. Duplicate names within one scope fail, and an invalid higher-priority definition produces a visible error rather than silently falling through. Explicit `openwaggle agents import` and the Settings import wizard share one application service with source-specific adapters for Codex, Claude, Cursor, Gemini CLI, GitHub Copilot, and OpenCode. Import first produces a non-mutating plan classifying every source field as mapped, defaulted, dropped, incompatible, or requiring a user choice. Foreign frontmatter is never copied into the canonical parser, and no field disappears silently. Model, tool, skill, and MCP mappings query Pi/OpenWaggle runtime catalogs; unresolved or security-sensitive fields block writing until resolved or accepted as a restrictive omission. Human and schema-versioned machine dry-run output expose the same plan. Only a completely valid target is atomically installed, and an existing destination requires explicit overwrite intent.

A successful import is a canonical snapshot, not a live foreign-file link. Its provenance records source tool, path, digest, importer version, and the canonical refresh baseline. OpenWaggle does not watch or automatically synchronize foreign agent directories. Explicit `openwaggle agents import --refresh` re-reads the source, executes the current adapter, and presents the full conversion diff. If the canonical document has changed since its baseline, refresh requires explicit conflict resolution and never overwrites local edits silently. A missing, moved, or changed-type source produces diagnostics but does not delete or disable the valid canonical snapshot.

Multi-agent capability is enabled by default, but model use of Session launch or spawn requires a direct user request or an applicable project or skill instruction that authorizes delegation. A generic request for more depth, research, investigation, or thoroughness is insufficient authorization to incur additional agent work.

Matching Codex, users may disable model multi-agent capability globally or for one project. That removes Session-launch and Session-spawn operations from the OpenWaggle-hosted agent's injected Sessions tool, while GUI, CLI, and externally authorized MCP callers retain their ordinary session discovery and management surfaces. Disabling model delegation is not a host shutdown or a revocation of unrelated external capabilities.

Execution placement uses a first-class Workspace resource rather than treating a git worktree as session-owned. Each session has one durable Workspace binding; a local-checkout or managed-worktree Workspace may have several session members. Matching Codex subagent behavior, spawn defaults to `share-parent`, binding the child to the parent's exact working path and uncommitted state. Explicit `new-worktree` creates and binds a distinct managed worktree Workspace, while explicit `local` binds to the project's primary checkout Workspace. Launch instead defaults to `current`: an internal caller resolves its initiating Session's exact Workspace, the CLI resolves its current Working path, and the GUI resolves its selected Workspace or project context. An authorized launch may explicitly choose `new-worktree`, `local`, or a specific existing Workspace. Independent-root semantics therefore change lineage and authority, not filesystem placement by themselves. Managed worktree path, branch, base provenance, recovery, and cleanup derive from Workspace identity. Releasing one session removes only its binding, and the worktree is removable only after its final binding is gone. This supersedes ADR 0010's one-session/one-worktree ownership cardinality while retaining its local-versus-worktree environment distinction.

The current shared `SessionWorkspace` type and `getSessionWorkspace` path do not represent filesystem execution placement; they combine a conversation tree, active branch and node selection, branch state, and projected transcript path for navigation. Before first-class Workspace APIs are introduced, that existing concept is renamed throughout the shared types, repository, IPC, renderer state, tests, and files to `SessionConversationView` / `getSessionConversationView` / `activeConversationView`. “Workspace” is thereafter reserved for execution working trees and bindings, preventing two incompatible meanings from entering the Session Control contract and persistence schema.

Shared Workspace membership introduces no workspace-specific concurrency cap or writer lock beyond the configured parent and host capacity controls. Parent and child runs may operate concurrently. Because OpenWaggle's Turn diff is a whole-working-tree snapshot projection, a checkpoint whose interval overlaps another run in the same Workspace is labelled `shared-concurrent` and represents changes observed during that interval rather than exclusive authorship. Users select a distinct worktree Workspace when non-interference and clean attribution matter.

The per-parent concurrent-child limit is user-configurable. Four is the product default rather than a hard ceiling, and users may select a higher or lower positive value. Resolution is project `.openwaggle/settings.json` `sessionHost.parentConcurrencyLimit`, then the user's Settings override for that project, then the app-global default. Project `sessionHost.multiAgentEnabled` follows the same precedence for model-created Workers. A spawn that would exceed the effective limit returns a structured capacity result instead of entering a hidden spawn queue.

The Session Host separately applies an app-global active-run safety ceiling so many unrelated roots or an exponentially growing descendant forest cannot exhaust one process. Its product default is sixteen active Pi runs and users may configure a higher or lower positive value in app-global SQLite settings. It counts active root and descendant runs but not idle sessions, completed runs, waits, subscriptions, semantic preparation, or exports. A run-creating command must satisfy both the parent-specific allowance and remaining host capacity. Exhaustion returns retryable `host_capacity_reached` state and never enters a hidden run queue. This is resource admission only: it adds no Workspace writer lock, session-count limit, or lineage-depth limit. Settings and capacity responses report both configured limits and the currently effective allowance.

The effective limit resolves through OpenWaggle's existing settings model: project `.openwaggle/settings.json`, then app-global SQLite settings, then the product default, with the first defined value winning. Settings UI and CLI configuration commands update those stores; Codex TOML syntax is not introduced into OpenWaggle.

Spawned children are ordinary durable sessions: searchable, readable, exportable, and directly openable under normal authorization. They remain ordinary flat entries in the existing Session sidebar without introducing a nested tree. A muted Lucide `ChessQueen` provenance glyph identifies the Queen Session, while Lucide `Pickaxe` identifies every Worker Session. A recursive Worker remains a Worker even when it coordinates further Workers; its direct-Worker count follows the `Pickaxe` rather than introducing a second parent-role icon. The same count follows `ChessQueen` for the Queen's direct Workers. Counts include active, completed, and manually archived direct Workers, exclude deeper descendants, and do not fluctuate with runtime or organizational state. Archiving never changes Hive membership or Spawn lineage. Sidebar rows gain no separate Agent-definition badge: the lineage glyph tooltip may add the selected Agent name and, for a Worker, its immediate parent. The selected Session's top identity header keeps its title primary and shows compact secondary lineage and Agent metadata such as `Worker · security-reviewer`; a non-lineage root with a selected definition shows only its Agent name. Every related Session exposes one collapsible composer-adjacent Hive activity surface: it links upward to the immediate parent when one exists and downward to direct Workers when they exist, so a recursive Worker never receives two stacked lineage blocks. Its compact header shows the current Session's `ChessQueen` or `Pickaxe`, the label `Hive`, the selected Agent name when present, a separately clickable and truncating immediate-parent shortcut when present, the durable direct-Worker count, the currently active direct-Worker count, and a disclosure chevron. Active means a direct Worker's Delegation state is `working`, `waiting`, `needs_attention`, `ready_for_review`, or `revision_requested`, even when no Run is executing; only `accepted` and `cancelled` enter Done. Only the parent shortcut and the small chevron receive interactive hover treatments; the chevron alone expands or collapses the surface, so the header never gains a misleading full-width collapse hover. A newly opened Worker with no direct Workers starts collapsed because its parent shortcut is already available in the compact header. Creating any Session's first Worker expands that Session's surface once for discoverability. From the first explicit toggle onward, expansion becomes remembered per-Session local presentation state across navigation and relaunch; later activity updates counts and attention without forcing the surface open. Active and completed Workers remain immediately visible in the expanded surface, while manually archived Workers appear under a collapsed `Archived · n` disclosure. Archiving an Active Worker remains permitted and does not interrupt or cancel it; that Worker stays in the header's active count, and the Archived disclosure reports both its active subcount and any attention colour without forcing itself open. The surface coexists with the Session's independently owned Follow-up queue and never changes the composer itself. It does not duplicate transcripts, form a second store, add a dedicated orchestration right sidebar, or turn Delegation review into a user-owned dashboard workflow. Completed children are not hidden or archived automatically.

Direct conversation in a Worker remains local to that durable Session, including after its Delegation Contract is accepted. It never reopens the contract implicitly. Explicit cross-session reporting is a separate Session Control operation. `upstream` targets the immediate parent, `queen` targets the Hive root, and downstream delivery names one or more Worker identities; broadcasts and multi-target reports are never inferred. Target resolution is deterministic: lineage aliases resolve from recorded Spawn lineage, a stable Session identity resolves directly, and a human-readable Worker reference resolves only when it uniquely identifies an authorized target. An absent or ambiguous target returns structured authorized candidates so the agent can clarify; the host never guesses or broadens ambiguity into a broadcast. A report is a durable model-visible context item that an active target receives at its next safe agent-loop boundary or an idle target receives on its next Run. Startup delivery is appended while Pi is idle; live steering is acknowledged only after a later Pi boundary observes its persisted custom-message entry. A per-Run accepted-ID set suppresses concurrent redelivery, and startup reconciliation recognizes entries persisted before an outbox acknowledgement, so a crash cannot turn an acknowledgement retry into duplicate model context. The same delivery bridge governs orchestration and Delegation-specification updates in classic and Waggle runs. The host presents its payload in a provenance-labelled peer-agent context envelope below system, developer, and user instructions. Queen or Worker lineage never changes instruction priority. The receiving agent evaluates the report under its own immutable Agent snapshot, current instructions, capabilities, and Authorization ceiling; report text cannot itself mutate authority, Agent definitions, Delegation Contracts, queues, Sessions, or Runs. A report may request a reply; the host assigns stable report and correlation identities, and the response is another authorized report that names the report it answers. The sender may wait with a bounded timeout for that correlated reply. Neither requesting a reply nor waiting starts a Run in an idle target. Immediate consultation requires a separate explicit Run-creating or messaging operation and its corresponding capability, so reporting never hides additional work, cost, or authority. Reporting is an agent capability rather than a GUI interaction mode: the user requests it in ordinary conversation, the current agent invokes the explicit Sessions report operation, and existing tool-activity and transcript projections show the resulting activity and delivered context. OpenWaggle adds no report-specific composer mode, slash command, target picker, overflow action, card, or unread workflow; CLI and MCP clients retain the structured operation required for machine interaction. Reporting never starts, steers, interrupts, replaces, or reopens a Run and never changes Delegation state. Every spawn creates only narrow write-only report routes from Worker to immediate parent or Queen and from an authorized parent to its managed child. Any sibling, other descendant, unrelated, or multi-target delivery requires `sessions:report` for every explicit target. Reporting grants no reciprocal transcript read, Run control, or Session management authority.

A report request validates every explicit target and required route before mutation and succeeds only after the report plus one per-target delivery record are committed atomically; it never leaves a partial multi-target report. Each target begins `pending`. The host marks it `delivered` in the same transaction that appends one unique report context item to the target Run, so recovery may retry pending delivery without duplicating transcript content. Multi-target status remains independent per target. A correlated reply is a separate report fact rather than a delivery status. Session wait may await target delivery or a correlated reply with a bounded timeout. OpenWaggle reports only what it can prove—durable acceptance and model-context delivery—and never claims that an agent read, understood, agreed with, or acted on the report.

Session listing and discovery are read-model operations, not session lifecycle operations. The public list API uses bounded pages and opaque keyset cursors rather than offsets. Its ordering has a deterministic identity tie-breaker, and ordinary metadata filters are backed by suitable SQLite indexes.

Matching Codex's session picker, the Sessions CLI defaults listing, discovery, and interactive selection to sessions whose recorded Working path matches the caller's resolved current working directory. `--project` explicitly broadens selection to every Workspace in the same repository project, while `--all` selects the complete authorized session catalog. Supplying a stable Session identity addresses that target directly independent of the default catalog filter, subject to ordinary authorization and discoverability. The internal Sessions tool must name a catalog scope when broadening beyond its current Working path. This preserves a focused default without weakening the requirement that external tools and authorized agents can search every session.

Default discovery searches a compact projection containing the title, initial objective, and current preview. Its lexical projection is maintained incrementally in the same SQLite transaction as its source changes and indexed with SQLite FTS5; queries do not hydrate sessions, parse node JSON, or scan transcripts. Search ranking and the cursor's identity tie-breaker produce stable pages, snippets come only from authorized indexed fields, and authorization constraints are applied inside the query rather than after a page has been selected.

Discovery uses hybrid retrieval by default. One local embedding represents each session's compact discovery text, and a replaceable vector-index adapter retrieves semantic candidates without embedding every transcript message. Lexical and semantic candidate ranks are fused, with exact session identities, titles, paths, filenames, and error tokens retaining strong lexical priority. Embeddings are created on-device after committed discovery-text changes rather than during token streaming.

Callers may explicitly select `hybrid`, `lexical`, or `semantic` discovery. Hybrid mode falls back to lexical results when the embedding model, semantic projection, or vector index is unavailable and returns structured degradation metadata; it never blocks basic discovery on a model download or index rebuild. Lexical mode does not initialize the embedding runtime. Semantic query cursors are bound to the embedding model and vector-index revision so a model replacement cannot silently reinterpret an existing result traversal.

The product pins the embedding model identity, revision, tokenizer, dimensions, and integrity metadata and bundles those artifacts with the app so the initial full cutover works offline. Normal model loading and incremental embedding remain outside the lexical query path after migration. An unavailable, incompatible, or corrupt bundled model fails the cutover before database installation; after a successful cutover, a later runtime-loading failure leaves lexical discovery operational and produces actionable structured status rather than an empty semantic result set.

The pinned model must support cross-lingual retrieval so a query may discover relevant session text written in another supported language. Model selection is gated on compatible licensing and packaging, quantized local inference, bounded memory and artifact size, stable Transformers.js execution, and retrieval-quality evaluation that includes same-language and cross-language cases. A model is not selected solely from an English benchmark.

The initial pinned model is `Xenova/multilingual-e5-small` revision `761b726dd34fb83930e26aab4e9ac3899aa1fa78`, using its Q8 ONNX weights and 384-dimensional normalized embeddings. The build verifies the SHA-256 digest of every required tokenizer, configuration, and model file, bundles one 145 MB resource directory outside `app.asar`, includes an MIT third-party notice for the `intfloat/multilingual-e5-small` source model, and disables remote model loading in packaged builds. A local smoke corpus must retain cross-language top-one matches before changing the pinned revision.

Semantic-only discovery is strict. If its pinned model and requested semantic index revision are not ready, it returns a structured `semantic_not_ready` result containing readiness, progress, failure context when applicable, and the identity of the preparation operation that is running or was started. It does not substitute lexical matches. A caller may explicitly wait on preparation with a bounded timeout; otherwise preparation continues independently and publishes status through the Session Host event stream. Hybrid discovery remains the only mode permitted to degrade to lexical retrieval.

Full-transcript semantic retrieval uses a rebuildable, target-scoped cache rather than treating embeddings as authoritative conversation data. The Session Host retains at most 5,000 recent searchable nodes per Session, 50,000 node records and 64 MiB of vectors globally, and 10,000 queued nodes. Scope access and seven-day expiry are durable; prepare, bounded wait, and search operations hold expiring operation leases, and transactional least-recently-used cleanup excludes every live lease. If an authorized scope exceeds a per-Session or global budget, readiness becomes terminal `partial` after all admitted nodes are prepared and includes its searchable, eligible, and prepared counts. A fresh wait therefore cannot remain pending for work that policy deliberately did not admit. Semantic-only search may return the available partial projection; hybrid search declares `semantic_partial_coverage` and falls back to the complete lexical transcript index. Cursor-paginated transcript reads remain complete independently of this cache.

Lexical indexing is transactionally current. Embeddings are queued only after a completed message changes the bounded discovery projection; token streaming never schedules embedding work. Semantic retrieval reads the latest atomically published semantic snapshot while newer embeddings are prepared in the background. Hybrid results therefore combine current lexical candidates with that snapshot and return its model revision, coverage, pending count, and freshness. Semantic callers that require all committed discovery text may request `requireFresh` with a bounded timeout; ordinary searches do not wait for continuously active sessions to be re-embedded.

The stable discovery-result contract explains each match with `matchKind` (`exact`, `lexical`, `semantic`, or `hybrid`), the matched discovery fields, a bounded authorized snippet, its rank, and semantic snapshot freshness. Raw BM25 values, vector distances, and fusion scores are implementation diagnostics available only through an explicit diagnostic mode. Callers cannot treat those model- and index-specific numbers as durable ordering or relevance contracts.

Discovery considers the complete authorized corpus when selecting candidates but materializes only a bounded top-ranked result window. Pages and cursors traverse that window; they do not imply that semantic relevance defines an exhaustive ordering over every session. Exhaustive automation uses the cursor-paginated session list with indexed metadata filters, or lexical retrieval where appropriate. This keeps ANN candidate collection, reranking, rank fusion, cursor state, and response size bounded independently of the total session count.

The initial vector adapter uses exact cosine search with precomputed corpus magnitudes and a bounded top-result heap. The reproducible `scripts/benchmark-session-vector-index.ts` release gate on an Apple M4 Max measured a 384-dimensional exact scan over 100,000 Sessions with a top-1,000 result window at 31.56 ms P95 and 461.6 MB process RSS. That is comfortably below the 250 ms semantic-search budget while preserving exact recall. These measurements do not justify the extra persistence, rebuild, filtered-query, and recall complexity of an approximate index yet. The adapter remains replaceable, and a materially slower supported machine or larger observed corpus can establish the crossover with the same benchmark before an ANN change.

The first discovery page creates an immutable short-lived ordering bound to the caller identity, normalized query and filters, authorization scope, and lexical and semantic index revisions. Its opaque cursor pages through that ordering even if the corpus changes. Each page rechecks current authorization and omits targets the caller may no longer discover. Cursor state is bounded in the Session Host and is not durable across host loss; expiry or missing state returns a structured `cursor_expired` result and never silently restarts against a different ranking. Ordinary session listing instead uses live keyset pagination with deterministic sort and identity tie-breakers.

Session reading is bounded but complete. `read` returns metadata, runtime state, Follow-up queue summary, lineage, semantic readiness, and an optional bounded recent-turn slice without resuming or subscribing to the session. Complete conversation access uses cursor-paginated transcript reads over an explicit branch or tree scope and a fixed node high-water mark. The CLI may offer whole-history output, but it implements that mode by streaming pages to stdout or a destination rather than hydrating or buffering the full transcript. Internal agents receive the same page contract, so they can search first, read around matches, or deliberately traverse every page without forcing the whole session into one tool result or model context.

Transcript reading defaults to the active branch captured when the read snapshot is created. A caller may select a specific branch identity, and whole-tree traversal is an explicit scope. Whole-tree pages preserve node identity and parent links and annotate branch membership, emitting a shared prefix node once rather than flattening every branch into duplicated linear transcripts.

One OpenWaggle run is one durable transcript turn. Its initial input, steering inputs, assistant messages, tool activity, agent-loop interactions, state changes, and terminal outcome are ordered transcript items under that turn identity. Delivery of a Follow-up message starts another run and therefore another turn. Session projection must persist run-to-turn and node-to-turn attribution instead of trying to infer it when reading; the current node projection does not retain ordinary run ownership. Existing sessions are backfilled with explicitly synthetic turn identities where exact historical run boundaries cannot be recovered, and the API reports that provenance.

Turn traversal defaults to newest-first, matching Codex's inspection-oriented list behavior, and accepts an explicit oldest-first order for replay or complete reading. Items inside each turn remain chronological. When `read` includes a bounded recent-turn slice, selection occurs from the newest end but the returned slice is arranged chronologically so callers can consume it directly.

Turn pages accept `none`, `summary`, and `full` item views. `none` returns turn identities, timestamps, status, outcome, and item counts. `summary`, the agent-facing default, adds bounded message previews, tool names and outcomes, interaction kinds, and attachment metadata. `full` returns complete durable item content subject to the same page and byte limits. Oversized attachment bodies, extracted document bodies, and binary content remain authorized resource references rather than being inlined implicitly; whole-history full reads stream successive bounded pages.

Transcript search uses explicit content scopes. Its default index covers visible user and assistant text, orchestration updates, tool names and compact outcomes, and attachment filenames. Tool arguments, textual tool results, extracted attachment bodies, and visible reasoning are separate opt-in scopes because their size, noise, and disclosure characteristics differ. Authorization is enforced while selecting indexed content and while returning matches; hidden reasoning and inaccessible resource content are never searchable. Search matches return turn and item identities so a caller can read bounded context around each result.

Lexical transcript search is the default incrementally maintained path. Semantic and hybrid transcript search are explicit and lazily prepare embeddings only for one selected session or a bounded authorized session set; the initial public search boundary caps that set at 1,000 Sessions, reports a truncated discovery window when exceeded, and does not embed the complete global transcript corpus by default. Semantic chunks preserve their durable node, Session, created-order, and Run attribution so each match can be expanded through the normal bounded read API. Preparation, freshness, progress, failure, and bounded waiting reuse the semantic-readiness contract, while lexical transcript search remains available throughout download, backfill, rebuild, eviction, or failure.

Session export supports three explicit formats over the same authorized transcript read snapshot. Canonical `jsonl` is schema-versioned, lossless, ordered, and streamable for agent and tool interoperability. `markdown` is a human-readable derived rendering and is intentionally not a round-trip format. A `bundle` contains a manifest, the canonical JSONL stream, and only explicitly requested authorized resources with paths, media types, sizes, and integrity hashes. Pi's runtime JSONL file is not the OpenWaggle export contract because it does not contain OpenWaggle-owned run/turn attribution, provenance, lineage, queue, orchestration, and projection state.

Exporting an active session is allowed and does not interrupt it. Export fixes a durable node high-water mark and state revision, excludes uncommitted stream-buffer content, and marks the active transcript turn incomplete in its manifest and canonical records. A caller may request bounded waiting for the session to become idle before the snapshot is fixed; timeout returns explicit current state and never converts into an indefinite wait or implicit interruption.

Export is a separately auditable capability and is non-escalating. `sessions:export` permits delivery but grants no content by itself: transcript records also require `sessions:read`, queued content requires `sessions:queue` and `sessions:read`, and bundled resources require their resource-read grants. Writing to a path additionally passes the normal filesystem authorization boundary. Streaming JSONL or Markdown to stdout is still an export because the content leaves Session Control.

The default export includes Follow-up queue state, revision, pending count, and stable item identities but not queued message bodies or attachment contents. Queue bodies require an explicit include option plus `sessions:queue` and `sessions:read`. The manifest records the selected queue scope, omitted body count, and whether omission resulted from caller choice or insufficient authorization, so a consumer never mistakes a scoped export for a complete queue transfer.

Canonical JSONL does not silently redact, summarize, or rewrite selected content that the caller is authorized to export. Redaction is an explicit named profile that produces a derived export and writes manifest entries for every omitted or replaced field and resource. Authorization exclusions still apply before redaction and cannot be overridden by a profile. This preserves lossless interoperability for the canonical scope while making share-safe transformations visible and auditable.

Export scope defaults to the active branch captured in the transcript read snapshot. A caller may select one explicit branch or request the complete session tree. Whole-tree JSONL and bundles use the same graph-preserving representation as whole-tree reads: each node is emitted once with parent links and branch membership instead of duplicating shared history. Every format's manifest or header declares the selected branch scope and active-branch identity.

File and bundle exports refuse an existing destination unless the caller provides explicit overwrite intent. They stream to a uniquely named temporary sibling, validate record framing and manifest/resource hashes, flush and close the artifact, and only then install it at the final path with an atomic rename where the platform supports it. Failure never leaves the final destination looking complete; recoverable temporary artifacts are identified separately from successful exports, and overwrite authorization does not broaden the selected export or filesystem scope.

A file or bundle export is a durable Session Host operation with its own identity, lifecycle, selected snapshot and destination, record/resource/byte progress, outcome, bounded wait, event watch, and cancellation. It continues safely if the initiating GUI or CLI disconnects. A stdout export is different: it is a foreground stream bound to the client transport and ends when that sink closes. Export operations reuse Session Host operation and event infrastructure but are not agent runs or MCP Tasks.

The lexical and semantic discovery projections are derived and rebuildable from canonical session data. They carry independent schema and model versions so migration can backfill or rebuild them after tokenizer, embedding-model, or projection changes without turning either index into a second source of truth. Full transcript search is a separate explicit operation with its own bounded query path; it is never enabled implicitly by a default discovery query.

Child completion produces an OpenWaggle-authored orchestration update rather than impersonating user steering or a queued follow-up. A matching active wait returns the result immediately; an active parent otherwise receives it at a safe agent-loop boundary. An idle parent is not restarted automatically: the activity projection shows the result, and the next parent run receives pending updates. Several completions may be batched while full results remain in their child sessions.

Parent and child run interruption are independently controlled, matching Codex's individual-subagent and explicit stop-all surfaces. Interrupting, replacing, completing, or archiving a parent does not stop its durable child sessions or active child runs. `interrupt` targets one exact Session and Run identity. `interrupt-descendants` snapshots every active recursive descendant, deepest first, and interrupts those exact Runs without interrupting the parent; the CLI exposes the same name and the native Pi tool uses `interrupt_descendants`. The idempotent outcome records every accepted Session, Run, and resulting state revision so GUI and watch clients receive updates for the actual Workers. Profile revocation and Session Host loss retain their separate cascading security and recovery semantics.

Every classic or Waggle Run appends a hidden, non-model `openwaggle-run-boundary` Pi entry before other Run context. Session projection attributes each later node to the nearest boundary in its ancestry, so attribution survives restart, compaction, branching, and full projection replacement. `items` returns the stable `runId` and accepts an exact Run filter; the target schema indexes Session, JSON-extracted Run identity, and created order for bounded retrieval.

Bounded `wait` and persistent subscriptions are distinct. An agent may wait on several session conditions from recent host-scoped event cursors and receives compact state when the first condition matches or the timeout expires. GUI clients consume persistent subscriptions, and the CLI exposes those subscriptions as `watch`; neither tails persistence files.

Codex-compatible recovery comes from canonical thread state followed by live notifications, not from a permanent notification log. A Session snapshot includes its state revision and a host-instance-scoped event cursor. A client subscribes after that cursor; the host replays events still present in a bounded in-memory window and then delivers new events in order. The replay window exists only to close snapshot-to-subscription races and short connection gaps. If a cursor belongs to another host instance, has expired, or falls behind because the client's bounded delivery buffer overflowed, the host returns structured `resync_required`; the client discards its stale projection and reloads canonical Session state and paginated history before subscribing again. Durable Session state, transcript items, and completed operation records remain authoritative. Notification consumption never applies backpressure to agent runs, Follow-up delivery, persistence, or other clients, so a slow consumer is disconnected rather than allowed to grow an unbounded buffer.

The canonical external session command family is `openwaggle sessions`. Discovery and reading use `list`, `search`, `read`, `turns`, `items`, and `export`; lifecycle uses `create`, `launch`, and `spawn`; messaging uses `message`, `start`, `follow-up`, `steer`, `promote`, `replace`, `interrupt`, and `report`; coordination uses `status`, `wait`, and `watch`; queue control nests `list`, `withdraw`, `reorder`, `pause`, and `resume` under `queue`; organization uses `rename`, `archive`, `unarchive`, `fork`, and `handoff`. `message` maps to adaptive Message submission, while `report` delivers durable context without creating or altering a Run. No ambiguous `send` command hides whether input steers, replaces, queues, starts a run, or reports across Sessions.

Run creation separates live authorization from persistent session configuration. `launch`, `spawn`, `start`, `follow-up`, and `replace` may request a per-run mode, with `--yolo` as shorthand for a YOLO Run authorization override. The host rejects a request above the initiating profile's Authorization ceiling, carries the effective ceiling into spawned descendants, and never writes that choice as a persistent session override. `create`, `steer`, and `promote` do not create runs and accept no run-mode option. Adaptive `message` also rejects one because its active-target resolution could steer the current run or create a future run depending on current state; a caller that requires a mode uses the corresponding explicit command. Persistent session mode changes use `sessions authorization set <id> yolo|ask` or `sessions authorization clear <id>` and require `sessions:authorization`.

A queued Follow-up does not retain stale authorization merely because its submission was accepted. Immediately before delivery creates its run, the host revalidates the originating client profile or derived grant and its requested Run authorization override. If the request now exceeds the current ceiling, the message remains queued in a visible `authorization_ceiling_changed` needs-attention state. OpenWaggle neither downgrades the requested mode nor discards or starts the item. An authorized caller may change the queued override, restore sufficient scoped authority, or withdraw the message.

Reducing an Authorization ceiling while its run is active takes effect at the next authorization boundary. The host re-evaluates unresolved Authorization requests, applies the reduced mode to later protected actions, and carries the reduction into every later descendant spawn. Work already completed is not undone, and a tool call already executing is not forcibly killed merely because its ceiling changed; its outcome and the revocation boundary remain visible in the audit trail.

Human-readable output is the default. Machine callers explicitly select `--json` for one schema-versioned response or `--jsonl` for streams such as watch, whole-history reads, and stdout exports. In machine mode stdout contains only response data; progress, warnings, and diagnostics use stderr. Errors have stable kinds, documented exit codes, and structured context. Output semantics never change merely because stdout or stderr is attached to a TTY, so pipelines and external agents do not depend on terminal detection.

Messaging commands require exactly one explicit input source: `--text` for short convenience input, `--stdin` for multiline or sensitive content, `--input-file <path>` for a UTF-8 body, or `--request-json <path|->` for the complete typed envelope. Ordinary attachments use repeated explicit `--attach <path>` options. Missing or conflicting sources fail before connecting to Session Control, and the CLI never opens an implicit prompt that could leave an external agent waiting indefinitely. Stdin is consumed only when `--stdin` or JSON path `-` is named; pipe detection never changes command semantics.

Every mutating command accepts an idempotency key, including create, launch, spawn, messaging, run control, queue mutation, organization, semantic preparation, and export creation. Session Control stores and replays the result under caller identity, operation kind, and target scope and rejects reuse with a different payload. When omitted, the CLI generates one before its first request, reuses it across reconnects and internal retries, and returns it in machine output. A separate invocation must provide the same key to retry an uncertain outcome; generating a new key deliberately requests a new mutation.

The local transport authenticates the desktop user with a protected per-user bearer credential over an owner-only Unix-domain socket or Windows named pipe; a machine or hardware identifier is not an authorization principal because it cannot distinguish callers on the same computer. A same-user CLI connection receives a zero-setup `local-user` identity and the user's normal OpenWaggle authority, including YOLO when the live settings permit it. Users may optionally create named revocable profiles for external agentic tools that need separate attribution or narrower capability, project, ancestry, session, or Authorization-ceiling scopes. Such profiles are selected explicitly through `--profile <name>` or `OPENWAGGLE_PROFILE`, authenticate with an additional protected credential, and default to an Ask for Approval ceiling. Repository-controlled configuration cannot select a profile. Creating one generates a random 256-bit bearer credential, stores only its cryptographic verifier in Session Host persistence, and installs the secret into the platform credential store or an explicitly chosen owner-only file. Secrets never enter command arguments, repository settings, durable logs, or ordinary command output, and rotation preserves the profile's policy and audit identity. Profile creation, grant changes, rotation, and revocation are user-authorized operations, and every request and authorization outcome records the resolved caller identity.

Revoking a CLI client profile is an emergency invalidation rather than a ceiling reduction. The host immediately rejects and disconnects that identity, interrupts active runs and descendants whose grant chains originate from it, attempts cancellation of in-flight tools where the adapter supports it, and pauses its pending Follow-up delivery with structured `profile_revoked` state. External effects that already began cannot be promised rolled back. Sessions, transcripts, lineage, queued intent, and the audit trail remain durable so the local user can inspect them or explicitly resume work under different authority.

Optional CLI profiles provide declared, auditable non-escalation for cooperative callers and for tools whose OS sandbox keeps unrelated profile credentials inaccessible. They are not presented as containment against a hostile danger-full-access process already running as the same OS user with unrestricted access to that user's files, processes, and credential material. Defending against that actor requires an external boundary such as a separate OS account, sandbox, container, or repeated user-presence authentication. The host still applies peer checks, scoped credentials, least privilege, audit, and revocation because they prevent accidental and policy-level escalation within the supported trust model.

The existing Settings → General → Agent access section contains a collapsed `Restricted CLI profiles` card for optional creation, scope editing, credential rotation, and emergency revocation. Zero-setup local-user CLI access does not require visiting this surface, and the optional controls do not become a new top-level settings tab in the initial implementation.

Headless administration mirrors that surface under `openwaggle access profiles list|create|update|rotate|revoke`. The local-user identity and callers explicitly granted `access:profiles` may invoke those operations. Creation and rotation require an explicit `--credential-store` or `--credential-file <path>` destination; command output includes profile identity and destination metadata but never the bearer secret. Credential-file delivery uses owner-only permissions, a unique temporary sibling, validation, and atomic installation where supported, and refuses an existing destination without explicit authorized replacement intent.

Delegated profile administration is non-escalating. An `access:profiles` grant carries a management envelope of capabilities, targets, and maximum Authorization ceiling; its holder may create or edit only strict subsets of that envelope and cannot change its own policy. A named profile may rotate or revoke its own credential. Only the local-user identity may grant, expand, or redelegate `access:profiles`, preventing an administrative profile from manufacturing a peer or widening an administration chain.

The first CLI distribution is bundled with the desktop application rather than published as a second runtime. A small user-installed `openwaggle` shim delegates to the exact packaged executable, preserving Session Host protocol, Electron ABI, native addon, update, and signing alignment. The existing Windows installer already creates `openwaggle.cmd` and adds the install directory to the user PATH; the sessions CLI extends that entry. macOS and Linux expose an explicit Settings action that installs or removes a user-level shim without silently editing shell startup files, and development provides an equivalent `pnpm` entry. Host subprocess launch resolves the packaged executable directly and uses OpenWaggle's controlled child environment; it does not depend on the user's shell PATH or `ELECTRON_RUN_AS_NODE`. A separately installed protocol-compatible client remains a future distribution option, not a prerequisite for external automation.

The host protocol supports the current and immediately previous revision. Every client negotiates revision and capabilities before commands or subscriptions. Compatible clients attach normally. An incompatible newer client never terminates an active older host: it receives structured `host_upgrade_pending` state with the blocking run and operation identities. When the old host becomes idle it drains, closes its listener and persistence ownership, and acknowledges handoff before the new version starts. If safe handoff cannot be proven, startup fails visibly; a second host never opens the same store as an upgrade workaround.

Unexpected host loss is not a replay boundary. On recovery, runs recorded as active become `interrupted-by-host-loss`, their pending authorization requests are denied, and their durable Follow-up queues remain present but paused. The host publishes recovery state through its next snapshot, and an authorized caller may explicitly retry from the last durable transcript point with a new run identity. OpenWaggle never automatically replays an agent run whose filesystem, process, network, MCP, or other external effects may already have happened. Derived work that is independently idempotent and rebuildable, such as semantic indexing, may restart; a destination export may resume only under its recorded snapshot, destination, temporary-artifact, and checksum contract.

Host liveness follows clients and active work. GUI and CLI connections, live runs, eligible automatic Follow-up delivery, semantic preparation, destination exports, bounded waits, and subscriptions keep the host alive. When none remain, the host starts an app-global configurable idle grace period whose default is five minutes, then shuts down cleanly and releases its endpoint and persistence ownership. A paused Follow-up queue does not keep the process resident because it cannot deliver without explicit resumption. The Settings UI updates this global value through the existing SQLite settings store.

A headless run may remain pending on an agent-loop interaction after every GUI closes. The Session Host retains that request with the live run and publishes it through subscriptions, GUI reconnection snapshots, CLI `watch`, and `sessions requests list`; `sessions requests respond` submits an authorized response. Closing a client never answers the request. A pending interaction has no automatic expiry by default and keeps both its run and the host active until it is answered or explicitly interrupted. A caller may set a bounded interaction deadline when launching, starting, or spawning a run; expiry interrupts that run with an explicit interaction-timeout outcome and never fabricates a response. `sessions:respond` covers non-approval interactions, while the separately delegated `sessions:approve` capability covers individual Authorization decisions. The stronger `sessions:authorization` capability permits setting or clearing a persistent session Authorization mode override within its granted scope. Because changing a session to YOLO may resolve the current request and authorize later requests automatically, neither interaction-response nor individual-approval authority implies authorization-mode configuration. Requesting or owning the run grants none of these native Session capabilities, so the injected Sessions tool cannot approve or persistently relax its own host-authored boundary unless its pre-existing caller profile or derived grant explicitly carries that authority for the exact scope. This is a capability boundary at the Session Host API, not an OS sandbox: a same-user Run that retains unrestricted shell or process tools can invoke another client, read owner-accessible credentials, or mutate local state outside that native-tool policy. Strong containment therefore requires removing those tools or running the agent behind a separate OS sandbox, account, or container.

## Consequences

CLI and internal-agent actions update open GUI windows immediately without WebSockets. Runs can continue headlessly, and a later GUI reconstructs current state from a canonical snapshot before joining the ordered live event stream. Recent events may bridge the snapshot boundary; an unavailable cursor causes explicit resynchronization rather than a promise of durable notification replay.

Session ownership, lifecycle, authentication, startup, version skew, crash recovery, bounded event replay, slow-consumer handling, and resynchronization become explicit infrastructure that requires unit, integration, packaged-app, and real Electron QA. The current Electron-main run registry and renderer-only message queue move behind Session Control rather than remaining parallel authorities.

Deterministic CI exercises the complete orchestration state machine with a controllable Pi provider: Session Host ownership, root and descendant spawning, shared and isolated Workspaces, true steering, durable Follow-up delivery, waits, interruption, authorization, event resynchronization, export, crash recovery, and GUI/CLI/MCP/internal-tool adapters. Paid-provider and network variability do not enter ordinary CI.

Every release candidate that claims this capability must also pass a live orchestration smoke suite using a real configured provider in the packaged Electron app. A real OpenWaggle-hosted parent spawns child sessions through the injected Sessions tool while the GUI, Sessions CLI, and external MCP adapter observe and control the same Session Host. The recorded release evidence includes the provider/model identity, app version, platform, session/run identities, workspace selections, invoked operations, expected transitions, and final outcomes, with credentials and sensitive transcript content excluded. Skipping or failing this suite blocks a Codex-parity release claim.

Session discovery stays fast as transcript volume grows because its hot path reads only indexed summary data. Hybrid retrieval adds model distribution, asynchronous embedding work, vector storage, index training or rebuilding, relevance evaluation, and explicit lexical, semantic, and degraded-mode performance tests over large synthetic session sets.

The baseline performance corpus contains 100,000 sessions and 10 million transcript messages, with at most one discovery embedding per session. On the reference performance environment, cursor-paginated session listing and lexical discovery target p95 latency below 100 ms with warm caches and below 500 ms from a cold database path. Hybrid discovery targets p95 below 250 ms when its pinned model is loaded and its semantic index is ready. At normal interactive load, a committed completed-message change targets publication in the semantic snapshot within two seconds. Standard pages contain 50 results and one discovery window contains at most 1,000; query memory remains bounded independently of transcript size. Semantic relevance, exact-match preservation, and cross-lingual recall are separate quality gates rather than being inferred from latency.

The concrete embedding model and vector-index implementation are selected through measured runtime gates rather than architecture preference. The pinned Q8 multilingual E5 model passed the checked-in cross-language relevance corpus with 1.49 seconds of cold startup plus passage embedding and 2–3.3 ms query embeddings on the reference machine. The exact index passed the complete 100,000-Session scale budget without recall loss, so introducing an approximate backend before an observed crossover would make the initial cutover slower to build and harder to recover. Candidate replacements must compare latency, memory, artifact size, embedding backfill and publication time, filtered-query behavior, same-language relevance, cross-lingual recall, and failure recovery on every supported packaged platform before changing either pinned revision.

The `scripts/benchmark-session-discovery-database.ts` release gate builds 100,000 Sessions and 10 million transcript messages, closes and reopens the 2.86 GB database before measuring, and fails the process when a budget is exceeded. On the same reference machine it measured a 1.30 ms cold catalog page, 0.035 ms warm list P95, 24.68 ms lexical-search P95, and 0.054 ms transcript-page P95. The scripts emit machine-readable evidence and return a nonzero exit status on performance or relevance failure.

Read-only offline inspection may use a deliberately defined snapshot path, but mutations and all live-run operations require the Session Host. A client must fail clearly when it cannot authenticate, negotiate, or start a compatible host.

## Alternatives Considered

**Keep Electron main as the only runtime owner.** Rejected because external CLI agents could not start durable work while the GUI is closed and could not reliably reach live steering handles.

**Let each CLI invocation open persistence and run its own agents.** Rejected because process locks serialize files but do not establish one owner for active runs, queues, approvals, or ordered events.

**Use OpenWaggle's MCP server as the internal control plane.** Rejected because Session Control is a first-party domain service used by more than MCP, and internal agents must not depend on loopback protocol configuration or server grants.

**Expose a loopback WebSocket or HTTP service.** Rejected as the default local path because a filesystem-scoped socket or named pipe provides full-duplex commands and subscriptions without opening a TCP listener. Remote control can remain an explicit separately authenticated adapter.
