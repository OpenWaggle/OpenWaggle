# Pi runtime upgrades

Pi publishes its runtime as one matched release: seven packages (`pi-agent-core`, `pi-ai`, `pi-codemode`, `pi-coding-agent`, `pi-mcp`, `pi-telemetry`, `pi-tui`). Pi 1.2.0 removed `pi-client` and `pi-protocol` (and the unreleased `pi-server`) and no longer depends on `@earendil-works/chord`; `check:pi-runtime` reports any of them left in the catalog or the lockfile. OpenWaggle keeps its direct Pi dependencies in the `pi-runtime` catalog (`workspaces.catalogs` in the root `package.json`), patches `pi-ai` and `pi-coding-agent`, and bundles Pi into the Electron main process. `bun run check:pi-runtime` (`scripts/check-pi-runtime-alignment.ts`) enforces the matched set, the direct pins, the patch registrations, and the release-age exceptions described below.

## What the patches carry

The patches are larger than ADR 0025's compaction behaviour. Re-port every part on each upgrade, and keep every change additive to Pi's public contracts.

- **Native Responses compaction (ADR 0025).** `compactResponses` in pi-ai, the compaction-capable model id lists in `openai.models.js` and `openai-codex.models.js` (audit them against the new catalog; drop ids the catalog no longer has), the Native endpoint fallback (404/405/501, and 400/401/403 under Sign in with ChatGPT), credential fingerprinting, request-model refresh, reconstruction fit, compaction threshold injection (`compaction.thresholdPercent`, declared in Pi's settings schema since 1.2.0 moved the settings types there), and the retry policy and callbacks. The compaction request fails at once on the Native endpoint statuses through Pi's own `noRetryStatuses` (added in 1.2.0, replacing the patch's `nonRetryableStatuses`). The compat fields `supportsCompaction` and `compactionBaseUrl` live on `OpenAIResponsesCompat` in `providers/compat-schema.d.ts` since 1.2.0. Pi 1.6.0 carries the system prompt as the leading `developer` item of `input`, as Codex does, and `convertResponsesMessages` no longer takes `includeSystemPrompt`, so `compactResponses` sends no top-level `instructions` and never the same instructions twice.
- **Native compaction replay.** `openai-responses-shared.js` replays a `compaction` reasoning item only to the model that produced it (`reasoningItem.type !== "compaction" || isSameModel`).
- **Native compaction credentials.** Pi 1.6.0 marks the agent's stream function with its ModelRuntime (`markRuntimeStreamFunction` in `sdk.js`), so `_getSummarizationRequestAuth` returns no credentials and the runtime resolves them per request — Pi's fix for summaries handing a stored OAuth token back as an explicit API key (#11520). Native compaction bypasses ModelRuntime, so the patch resolves the credential-resolved endpoint, API key and headers itself in `_prepareCompactionRequestAuth` (`prepareModelRequest`, gated on `_usesModelRuntimeStream` and the Native mechanism); without it manual compaction fails with `No API key for provider` and loses opencode's `x-opencode-session` header. Branch summaries, bug reports and the Portable mechanism keep Pi's unresolved behaviour, and `_refreshRequestModelContext` already resolves the same way for automatic compaction.
- **Streaming tool arguments.** Since 1.6.0 Pi parses streamed tool-call arguments with `StreamingJsonParser` (`utils/streaming-json.js`): each delta is read once, a snapshot copies only the containers still open, and `ToolCallArgumentsStream.finish()` parses the complete text once when the provider closes the block. That replaces the patch's own rate limiter, so the patch keeps only what Pi's close events miss: the full parse when a stream fails or ends without its close event — `flushOpenBlocks` on Bedrock, `finishOpenToolCalls` before Anthropic's `done` and in its catch, the same helper at each throw and after the unfinished-call refusal in `openai-responses-shared.js`, and `finishToolArguments` on a `done` or `error` event in the `pi-messages` client (`pi-streaming-tool-arguments-terminal-paths.unit.test.ts`, `pi-bedrock-streaming-tool-arguments.unit.test.ts`). OpenWaggle's own transport no longer depends on Pi's parse rate: `assistant-events.ts` batches raw deltas past 8 KiB, because 1.6.0 refreshes a large call's arguments object on every delta and every event carries the whole input.
- **Session projection.** `buildSessionProjection(targetModel)` and the reconstruction entries in the session manager.
- **Provider attribution.** Prepared provider headers for Native compaction requests (`withPreparedProviderHeaders`), which start from opencode's `x-opencode-session` and the auth headers, as ModelRuntime merges them for every other request (`withOpenCodeSessionHeaders`, for automatic and manual compaction; `pi-native-compaction-opencode-session.integration.test.ts`). Since 1.4.0 Pi derives the attribution headers (OpenRouter, NVIDIA NIM, opencode) from the client identity of each request (`core/client-identity.js`) instead of handing them to `before_provider_headers`, so the patch adds `setClientIdentityTransform` there and exports it from `dist/index.js`; `provider-attribution.ts` installs OpenWaggle's attribution through it. Check on each upgrade that `sdk.js` still builds every request's identity with `getClientIdentity`.
- **Prompt and steer.** The input hook runs before extension-command dispatch, `PromptOptions.transformExpandedText` rewrites the expanded text, `prompt()` resolves to the text it queued while streaming, and `steer(text, images, transform)` resolves to the exact queued text (or undefined when an input handler consumed it). The options form of `steer()` keeps Pi's `queued`/`handled` disposition. `PromptOptions.streamingOnly` makes `prompt()` reject with code `agent_not_streaming` instead of starting a new turn when the active turn ended while input handlers ran.
- **Run preparation.** Pi 1.2.0 prepares every run in `_prepareRun`, for a prompt and for `sendCustomMessage(message, { triggerTurn: true })` alike, so a Waggle turn (which Pi starts that way) gets `before_agent_start`, its prompt sections, and its tool loadout, on its later tool-loop requests too; OpenWaggle's 1.0.4 `_runCustomMessageTurn` hunk is gone. The patch keeps two things on top. Pi 1.6.0 split its `prompt()` into `prompt()` and `_preparePrompt` and dropped its own `_prepareNewTurn`, so the patch reintroduces `_prepareNewTurn`, called from `_prepareRun` after `before_agent_start`, to refresh request auth and run the pre-prompt compaction check against the final request model instead of Pi's check before it; the patched `_preparePrompt` keeps the extension-command dispatch after the input hooks. And when a custom message's preparation throws, such as request auth that no longer resolves, `_startRun` still runs the message as a turn whose first request fails (`PreparedRunError` carries the turn's messages once `before_agent_start` has run), so the turn ends with an error turn and `agent_end` instead of rejecting a `pi.sendMessage` nobody awaits, and Pi's automatic retry of a retryable failure sends the turn's own prompt. Pi 1.4.0 still rethrows there; drop that hunk once Pi ends such a run itself.
- **Model selection.** `setModel`/`cycleModel` check Pi's provider auth first and accept providers whose auth resolves without an API key (Amazon Bedrock through `AWS_PROFILE`, an ECS task role, web identity).
- **Virtual models.** A virtual selection stays unresolved in agent state, its compactions always use the Portable mechanism, and a routed native-capable model never reaches the Native endpoint.
- **Before-settle abort.** `agent_before_settle` handlers run after Pi's agent loop returned, where `ctx.signal` (Pi's `agent.signal`, the loop's abort signal) is undefined, and `abort()` only set `_abortDuringBeforeSettle`, so a handler running a slow check could neither see Stop nor be stopped. `_runBeforeSettleBoundary` now holds a `_beforeSettleAbortController` for the boundary, the extension context's `getSignal` falls back to its signal when the loop has none, and `abort()` aborts it. Turn-end handlers need nothing: they run inside the loop, whose signal Pi already aborts. `pi-before-settle-abort.integration.test.ts` checks it with real Pi; drop the hunk once Pi gives before-settle handlers an abortable signal itself. The Host still settles a stopped Run whose post-loop work ignores the signal after `PI_ABORTED_RUN_SETTLE_GRACE_MS` (`pi-run-abort.ts`).
- **MCP exports.** pi-coding-agent's `dist/index.js` and `dist/index.d.ts` also export Pi's MCP sign-in (`createMcpAuthProvider`, `McpOAuthCredentialStore`, `McpSignInCancelledError`, `signInMcpServer`), validation (`getMcpToolExposure`, `isMcpToolName`, `validateMcpServerConfig`), the pi-mcp OAuth types (`McpAuthProvider`, `McpOAuthServerStore`, `McpOAuthSettings`), and value resolution (`resolveConfigValueOrThrow`, `resolveHeadersOrThrow`) for ADR 0051. Exports only, no behaviour change, but re-add them on every upgrade: the hunk sits at the end of `dist/index.js` and does not apply with git's default context, so check the module paths still exist in the new release. Pi 1.6.0 moved `mcpNamespace` (and `createMcpToolName`, `limitMcpContent`, `MCP_OUTPUT_MAX_BYTES`, `McpOutputSaver`) out of pi-coding-agent into pi-mcp, so the re-export drops it and OpenWaggle imports it from `@earendil-works/pi-mcp` (`mcp-tool-server.ts`).

## Bundled main process

Pi resolves several files from `import.meta.url`, which in the bundle is OpenWaggle's `out/main`. Check each of these still works after an upgrade; `bun run pi-main-bundle:smoke` (part of `bun run check`) and `bun run packaged-app:smoke` cover them.

- `scripts/vite/pi-worker-bundles.ts` emits Pi's codemode sandbox worker (`codemode-worker.js`, an ES module run from a `data:` URL) and image-resize worker (`image-resize-worker.js`) beside the main bundle. A new Pi worker entry needs an entry there.
- QuickJS (`quickjs-wasi`) and Photon (`@silvia-odwyer/photon-node`) are root dependencies pinned to the exact versions Pi depends on, because their wasm is read from the installed package. On each upgrade, set both root pins to the versions in the new `pi-codemode` and `pi-coding-agent` package.json files; `check:pi-runtime` fails when a pin drifts or the lockfile resolves more than one version.
- `src/main/apply-pi-package-directory.ts` sets Pi's `PI_PACKAGE_DIR` to Pi's installed package before any Pi module loads, so Pi's README, docs, themes, export templates, and `VERSION` come from Pi and not from OpenWaggle's package.json. Shells OpenWaggle starts get the user's own value back.
- electron-builder keeps Pi's README, docs, and examples (`scripts/electron-builder-pi-assets.ts`), and `asarUnpack` keeps both workers and both wasm packages unpacked. `packaged-app:smoke` copies Pi's package directory out of `app.asar` and runs Pi's HTML export in the dark and light themes on it (`scripts/pi-package-assets-probe.ts`), so a Pi upgrade that reads a new file from its package directory fails there until `BUNDLED_PACKAGE_ASSETS` (`scripts/packaged-runtime-packages.ts`) ships it.
- Bundler-opaque lazy loaders (OAuth flows, the Bedrock implementation) need static registration (`pi-bundled-oauth.ts`, `pi-bundled-bedrock.ts`).

## Update procedure

1. Check that every package publishes the same newest version:

   ```bash
   for package in pi-agent-core pi-ai pi-codemode pi-coding-agent pi-mcp pi-telemetry pi-tui; do
     bun pm view "@earendil-works/$package" version
   done
   ```

2. Review every Pi changelog section since the pinned release. Pay special attention to provider context, compaction, retry, queue, prompt, steering, model selection, virtual models, MCP, codemode, session-format changes, and provider renames (stored provider references need an OpenWaggle migration, as for Azure in 1.0.3).
3. Update every entry in `catalogs.pi-runtime`, and set `catalogs.pi-extension-host` to the versions of the host packages the new `pi-coding-agent` depends on (today `typebox`; `check:pi-runtime` compares them). If the release is younger than the seven-day `minimumReleaseAge` in `bunfig.toml`, add exact `minimumReleaseAgeExcludes` entries for exactly the matched-release packages the lockfile resolves (`check:pi-runtime` rejects missing and unneeded entries) and a `# pi-runtime-release-age-exclusions-expire: YYYY-MM-DDTHH:MM:SSZ` line naming a UTC time at or after the moment the last-published package of the release is seven days old (`bun pm view <package> time`; a bare `YYYY-MM-DD` means midnight UTC). `check:pi-runtime` fails from then until the entries and the line are removed, and also when the line outlives its entries. Pi packages the release pulls in without a catalog pin (`@earendil-works/pi-schema` since 1.5.0) take an entry too, and `PI_RELEASE_COMPANION_PACKAGES` in `scripts/check-pi-runtime-alignment.ts` accepts exactly the versions the lockfile resolves; a dependency the release repins at an exact version (1.6.0 repinned `openai`) needs its own entry while it is younger than seven days.
4. Remove the two old `patchedDependencies` registrations and install the unpatched target release with `bun install --ignore-scripts`.
5. Port the patches by hand rather than with `bun patch`, which edits whichever installed copy it finds: copy the pristine target tarball into a scratch git repository, apply the old patch with `git apply --reject`, resolve every rejected hunk by reading the target release's code (never by fuzz), and write the new patch with `git diff --full-index --src-prefix=a/ --dst-prefix=b/` restricted to the changed `dist` files. Save it as `patches/@earendil-works__<package>@VERSION.patch` and register it in `patchedDependencies`.
6. Delete the superseded patch files, run `bun install --ignore-scripts` to refresh `bun.lock` and the patch hashes, and verify alignment with `bun run check:pi-runtime`. Then check that the install did not split a Pi package into two copies: `ls node_modules/.bun | grep '@earendil-works+pi-ai@'` must list one version. A release that repins a transitive dependency can make Bun install two, which fails `tsc` with TS2883 and splits module-level state; 1.6.0 did, through `openai`'s optional `undici` peer, and the fix is to move the root pin of that dependency to the version `pi-coding-agent` pins.
7. Run the focused Pi compaction, reconstruction, retry, prompt, steering, model-switch, virtual-model, scheduling, and settlement tests, then `bun run pi-main-bundle:smoke`, before the repository verification matrix. For packaging changes, also run `bun run build:unpack` and `bun run packaged-app:smoke`.
